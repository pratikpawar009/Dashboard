# dashboard

AI SDLC monitoring dashboard. Next.js frontend, FastAPI backend, Postgres datastore. See `docs/adr/0001-tech-stack.md` and `docs/adr/0002-system-architecture.md` for decisions.

## Layout

- `apps/web` — Next.js 15 (TypeScript, pnpm, vitest)
- `services/api` — FastAPI 0.115 (Pydantic, Alembic, uv, pytest)
- `services/mcp-server` — Standalone MCP server exposing `push_activity` and `push_artifacts` tools for AI clients (Claude Code, Cursor). Run: `cd services/mcp-server && pip install -e . && AGENTRISE_INGEST_TOKEN=... agentrise-mcp`. Separately deployed sibling to `services/api`, NOT wired into the API preflight (ADR-0014, ING-04 D-01 / D-07). Details: [`services/mcp-server/README.md`](services/mcp-server/README.md).
- `docker-compose.yml` — web + api + postgres, local orchestration

## Getting started

```bash
# frontend
cd apps/web && pnpm install && pnpm dev

# backend
cd services/api && uv sync && uv run uvicorn app.main:app --reload --port 8000

# or everything via Docker
docker compose up --build
```

Commands: `docs/config/project-commands.yaml`. Stack idioms: `.claude/skills/<framework>-patterns/SKILL.md`.

FastAPI's generated OpenAPI docs (`/docs`) cover every route in full; this table is a quick orientation for the `/auth/*` surface added by AUTH-01, plus `/api/programs` (AUTH-04), `/api/overview/program-detail/{program_id}` (PGD-01), `/api/overview/program-detail/{program_id}/token-trend` (PGD-02), `/api/overview/program-detail/{program_id}/releases` (PGD-03), `/api/overview/program-detail/{program_id}/commands` (PGD-04), `/api/overview/program-detail/{program_id}/team` and `/api/overview/program-detail/{program_id}/team/{member_id}/usage` (PGD-05), `/api/overview/program-detail/{program_id}/session-time-series` (PGD-06), `/api/personal-usage/{user_id}` (SHP-02), `/api/ingest/manifest` (ING-10), `/api/overview/summary` (OVW-01), `/api/overview/program-board` (OVW-04), and `/api/me` plus `/auth/logout` (AUTH-07).

A roster pushed through `POST /api/ingest/manifest` does **not** take effect immediately for sessions already being served. `session.programs` is resolved from `program_roster` behind a per-worker, per-process cache with a `300s` TTL, and **TTL expiry is the only invalidating event** — the ingest endpoint deliberately signals nothing (no cross-worker coherence, no Redis). So a re-push becomes visible to an already-warm worker only after its own next expiry, up to `300s` later, and each worker expires on its own schedule. **An app restart is the only faster lever.** Budget for that when onboarding or removing someone in a hurry.

`/auth/dev-bypass` only exists — is registered at all — when `ENVIRONMENT` resolves to one of `local`, `development`, `dev`, `test`, `ci`; every other value, including `production`, `prod`, `staging`, and any typo, gets a `404` because the route was never registered. This is fail-closed by allow-list, not a "disabled in production" deny-check — nothing named `production` needs to be checked for it to be unreachable. In an allow-listed environment a dev-bypass token is fully usable against protected routes (it's signed by an ephemeral, process-local key that the JWKS cache resolves only there) — that's the point of the feature — but it is never usable outside one, by design.

`/login` (`apps/web/src/app/login/page.tsx`, OVW-05) is a Server Component — the dashboard-owned sign-in page an unauthenticated visitor lands on, carrying the brand-bar identity (logo tile, "AgentRise Harness", "AI SDLC Governance") and a single SSO action; a visitor who already holds a valid `dashboard_session` is redirected server-side to `/overview` before any sign-in markup renders, so the page is never shown twice.

`/login/start`, `/callback`, `/api/proxy/programs`, `/api/proxy/program-detail/{program_id}` (AUTH-05), and `/logout` (AUTH-07) are Next.js Route Handlers in `apps/web`, not FastAPI routes — they will not show up in `/docs` above. `/login/start` is the OAuth relay Route Handler that previously lived at `/login` (OVW-05 moved it one segment down, body unchanged) and relays to FastAPI's `GET /auth/login`; the sign-in page's SSO action targets it. The two `/api/proxy/*` routes are full server-to-server proxies: the browser never calls FastAPI directly through them, and no route hands an access token to client-side JavaScript (`docs/adr/0008-client-side-auth-route-handler-proxy.md`).

Every existing `redirect("/login")` call site keeps working unchanged and improves: an expired session now lands on the branded sign-in page above instead of a silent bounce to the identity provider. `FRONTEND_LOGIN_URL` (the `post_logout_redirect_uri` registered with Keycloak — see Environment variables below) still points at `/login`, which is now the branded page — exactly the surface a user should see after signing out.

## Keycloak client requirements

The API is a confidential, PKCE-enforcing client. Its Keycloak client must have:

- **Client authentication** ON (the code exchange sends `client_secret`).
- **Valid redirect URIs** containing the API's own callback — `http://localhost:8000/auth/callback` locally. A frontend-style URI (`.../api/auth/callback/keycloak`) is not interchangeable: this integration exchanges the code server-side, so the browser must be sent back to the API.
- An **additional** Valid Redirect URI for the frontend's own callback — `http://localhost:3000/callback` locally (AUTH-05, `OIDC_REDIRECT_URI`). This extends the bullet above, it does not replace it: the browser now lands on the frontend's callback first, but the API still exchanges the code server-side, so both URIs must stay registered.
- A **Valid post logout redirect URI** for the frontend's own `/login` route — `http://localhost:3000/login` locally (AUTH-07, `FRONTEND_LOGIN_URL`). Additive alongside the Valid Redirect URIs bullets above, not a replacement.
- An **Audience mapper** putting the client's own id into the access token's `aud` claim — *Client scopes → `<client-id>`-dedicated → Add mapper → By configuration → Audience*, with *Included Client Audience* set to `OIDC_CLIENT_ID` and *Add to access token* ON. Without it **every protected route returns 401 while login itself appears to succeed**, which is the confusing part: `/auth/login` redirects, `/auth/callback` returns `200` with tokens, and `/auth/refresh` keeps working, because none of those validate `aud`. Only `_claims_options` (`services/api/app/core/auth.py`) enforces `aud == OIDC_CLIENT_ID`, and by default Keycloak does not put the client id there — it puts it in `azp` and leaves `aud` as `["account"]` or absent entirely. Verified against this realm: a real token arrived with `aud = None` and `azp = 'harness-dashboard'`, and `authlib` raised `MissingClaimError: Missing "aud" claim`. Put the mapper on the **dedicated** client scope, not a shared one, so the change is scoped to this client on a shared realm. `aud` is the claim naming the resource server that should accept a token (RFC 9068); accepting `azp` instead would weaken the check AUTH-01's review finding F-1 added, since `azp` names the client that *requested* the token rather than who it is *for*.

PKCE (S256) is sent on every authorization request per OAuth 2.1, so a client with *Proof Key for Code Exchange* required works as-is.

No Keycloak **group** is required for any program. Program membership is read from `program_roster` (AUTH-06), populated from each program's own committed roster file via `POST /api/ingest/manifest` — onboarding a program's dashboard access is a roster file change, never realm administration.

`OIDC_CLIENT_ID` / `OIDC_CLIENT_SECRET` / `OIDC_ISSUER` together are the feature flag: while any one is unset, `/auth/login` and `/auth/callback` return `501` and only `/auth/dev-bypass` is reachable; set all three to go live against Keycloak, unset any one to back out without a redeploy.
