## Idioms

This is the concrete, pinned instantiation of `next-patterns` for `apps/web/**` — Next.js **15.5.24**, React **19.1.0**, pnpm, vitest. See `next-patterns` for the framework-level rules (App Router, Server Components by default, `next/image`, `next/font`); this file records exactly how `apps/web/` is wired.

- Turbopack is enabled for both dev and build: `"dev": "next dev --turbopack"`, `"build": "next build --turbopack"` (`apps/web/package.json:6-7`) — do not silently drop `--turbopack` when adding/editing scripts.
- React 19 + Next 15: no `use()`/Server Actions/`useFormState` usage exists yet in the codebase — nothing to follow, don't assume patterns from older Next/React versions.
- TypeScript plugin wired via `tsconfig.json`'s `"plugins": [{ "name": "next" }]` (`apps/web/tsconfig.json:16-20`) — gives route-aware type errors (e.g. invalid `page.tsx` export shape) in editors/tsc.

## Project structure

```
apps/web/
  src/app/          # routes: layout.tsx, page.tsx, page.module.css, globals.css
  public/           # static assets (svgs)
  next.config.ts    # empty NextConfig — no custom config yet
  next-env.d.ts     # generated, do not edit
```
Entry points: `src/app/layout.tsx` (root layout, required), `src/app/page.tsx` (`/` route). No nested route segments, route groups, or parallel/intercepting routes exist yet.

## Layering & dependency rules

Same direction as `next-patterns`: shared code (once it exists under `src/lib/`, `src/components/`) is imported into `src/app/**` via `@/*`, never the reverse. Nothing in `apps/web` currently imports across a `services/api` boundary directly — cross-service calls must go over REST per `docs/adr/0002-system-architecture.md`, never a direct Python/Node import.

## Error handling

No `error.tsx` / `global-error.tsx` exists in `apps/web/src/app/` — unhandled render errors currently fall through to Next's default dev/prod error overlay. Add a segment `error.tsx` (Client Component boundary, per Next's own convention) when a route gets real fallible logic; do not add ad hoc `try/catch` + local error state in a Server Component page instead.

## Anti-patterns

- Don't add `pages/` — App Router only, confirmed by `next-patterns`.
- Don't drop `--turbopack` from `dev`/`build` scripts without an explicit decision — it's the scaffolded default for this exact Next 15 pin.
- Don't hand-edit `next-env.d.ts` — it's regenerated by `next dev`/`next build`.

## Examples

BAD — editing the generated env file:
```ts
// apps/web/next-env.d.ts
/// <reference types="my-custom-types" />
```

GOOD — add custom ambient types in a new file instead:
```ts
// apps/web/src/types/global.d.ts
export {};
declare global { /* ... */ }
```

## Design system + visual conventions

Same as `next-patterns`: CSS Modules per route + `globals.css` tokens (`--background`, `--foreground`), OS-driven dark mode via `prefers-color-scheme`, no CSS framework installed. Concrete instance: `apps/web/src/app/page.module.css` defines route-local tokens (`--gray-rgb`, `--button-primary-hover`, etc.) inside `.page`, redefined under the same dark-mode media query rather than a `[data-theme]` attribute — there is no manual theme toggle in this app.

## Dependency, build & CI

- pnpm via corepack: `Dockerfile` runs `corepack enable` then `pnpm install --frozen-lockfile=false` (`apps/web/Dockerfile:3,8`) — lockfile drift is tolerated at image-build time by design, not an error to "fix" by pinning `--frozen-lockfile=true` without checking with the team first.
- Container: `node:22-slim` base, `pnpm build` then `pnpm start`, exposes port `3000` (`apps/web/Dockerfile`).
- Local run: `docs/config/stack-smoke.md` § `nextjs` — `cd apps/web && pnpm dev --port 3000`; Docker Compose: `docker compose up web`.
- `docs/config/project-commands.yaml`: `typecheck_for_ts`, `format_for_ts`, and `build: "pnpm -C apps/web build"` are the authoritative commands — do not invent alternate invocations.
