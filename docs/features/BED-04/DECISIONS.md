# BED-04 — Decisions

Non-trivial technical choices made while planning BED-04's ingestion-freshness accessor. Header slugs (`blast:`/`rev:`/`adr:`) are machine-greppable per the `decide` skill.

### D-01: `FreshnessAccessor` is a stateful class mirroring `PersonaResolver`'s cache shape, not an inline module-level function+dict · blast:feature · rev:mechanical · adr:—

**Context**: `docs/research/BED-04.md` § Pattern Map names `PersonaResolver` (`app/core/persona_resolver.py`) as "the precise model to follow" for the cache (asyncio.Lock double-check, `time.monotonic()` TTL, warm fast path), and its own Recommendation #3 leaves the class-vs-inline-function choice open ("Either works; inline is recommended for BED-04's minimal scope"). `docs/test-cases/BED-04.json`'s preconditions for all three cases each require "a fresh accessor instance" — language that presumes object-identity-scoped state a test can construct fresh, not a shared module-level global a test would have to reset by hand.

**Decision**: `app/services/freshness.py` defines `class FreshnessAccessor` with `__init__(self, *, session_factory: async_sessionmaker[AsyncSession] | None = None)`, an internal `_cached_value: datetime | None` / `_expiry: float` pair, and an `asyncio.Lock`-guarded double-check `async def get_last_successful_run(self) -> datetime` — the same warm-fast-path-without-lock, re-check-inside-lock shape as `PersonaResolver.resolve()`. This story constructs no shared instance and does not wire one onto `app.state` (no route consumes it yet, per REQUIREMENTS.md § Scope/Rollout plan); each downstream consumer story owns constructing/sharing its own instance.

### D-02: `_CACHE_TTL_SECONDS = 300.0` is a private constant local to `freshness.py`, not imported from `persona_resolver.py` · blast:feature · rev:mechanical · adr:—

**Context**: REQUIREMENTS.md § Constraints pins the TTL to 300s specifically "matching `services/api/app/core/persona_resolver.py` `_CACHE_TTL_SECONDS = 300.0`, so the API has one cache duration to reason about" — but that name is module-private (single leading underscore) in its own module. `.claude/rules/reusability-baseline.md` treats implementation details as private until a second caller needs the concrete symbol, and separately warns against coupling unrelated modules to share code; persona resolution and ingestion freshness share no domain concept beyond an incidentally-equal cache duration.

**Decision**: duplicate the literal as `freshness.py`'s own `_CACHE_TTL_SECONDS = 300.0`, with a comment citing `persona_resolver.py` as the source of the matching value, rather than `from app.core.persona_resolver import _CACHE_TTL_SECONDS`. If the two constants ever need to diverge, each module already owns its value independently — no coordinated cross-module edit is required.

### D-03: A row-absent raise is never negative-cached — every call re-queries while the row stays absent · blast:feature · rev:mechanical · adr:—

**Context**: `PersonaResolver`'s docstring establishes "a raise is never negative-cached" for an unmapped role, but that resolver's failure mode returns nothing cacheable in the first place (`PersonaNotFoundError` propagates with no successful value to store). BED-04's row-absent path is different in kind, not just a precedent to copy silently: REQUIREMENTS.md's Solution sketch calls it "a first-class outcome, not an incidental failure," which leaves open whether "known-absent" itself should be cached for the TTL window to reduce load during a genuinely never-ingested database.

**Decision**: no negative-caching. `get_last_successful_run()` re-queries `system_metadata` on every call while no cache entry is warm, including every call during a chronic row-absent state. A fresh ingestion write can land at any moment (out-of-process, so nothing can push an invalidation into the cache), and a dashboard-load-frequency query volume against one indexed primary-key lookup stays well within `.claude/rules/performance-baseline.md`'s no-unbounded-fan-out bar regardless of how often the row-absent path is hit.

### D-04: The `system_metadata` read is bounded by an explicit 3.0s `asyncio.wait_for` timeout, matching `persona_resolver`'s Tier-3 bound · blast:feature · rev:mechanical · adr:—

**Context**: Review finding F-1 (HIGH) found the read had no explicit timeout — `app.core.db`'s `create_async_engine(settings.database_url)` sets no `connect_args`, no `command_timeout`, and no statement timeout, so REQUIREMENTS.md's claim that "the single read inherits the session factory's timeout" was false; `.claude/rules/performance-baseline.md` requires "I/O has explicit timeouts. No silent infinite waits." The read also runs inside `self._lock`, so an unbounded wait would hang every concurrent caller sharing one `FreshnessAccessor` instance, not just the slow one.

**Decision**: `_QUERY_TIMEOUT_SECONDS = 3.0`, matching `app.core.persona_resolver._TIER3_TIMEOUT_SECONDS` exactly, duplicated locally per the same rationale as D-02 (module-private name, no coordinated cross-module edit required if the two ever diverge). On timeout: `HTTPException(status_code=500, detail=_QUERY_TIMEOUT_MESSAGE)` — 500, not 503 or a bare `TimeoutError`, for the same consistency-with-`app/core/errors.py` reason `BED-04-FR-1` already gives the row-absent path; `_QUERY_TIMEOUT_MESSAGE` is a distinct constant from `_NOT_RUN_MESSAGE` since "the DB did not answer" is a different outcome from "ingestion has never run," and five downstream consumers may match on either. Never negative-cached, same invariant as D-03: the timeout outcome is not written to `self._cached_value`/`self._expiry`, so the next call re-queries. `app/core/db.py` is deliberately untouched — an engine-wide timeout was considered and rejected as out of scope (repo-wide blast radius across every merged story; would need its own ADR and story).
