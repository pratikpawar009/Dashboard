## Manual OWASP checklist + stack-pattern pass

**Input.** `program_id` (path param, `str`) flows into `select(ProgramArtifact.type, ProgramArtifact.count).where(ProgramArtifact.program_id == program_id)` (`app/services/artifacts.py:52-54`) — SQLAlchemy Core `.where()` with a bound column comparison, fully parameterized, no string interpolation. No file upload, no `eval`, no shell surface in this diff.

**Authentication and authorization (core focus).**
- `governance_visibility(current_user, program_id)` is called as the **first statement** in the route handler (`app/api/artifacts.py:56`), before any DB read — confirmed by test `test_cio_and_engineering_manager_both_403_no_body_no_select_tc03`, which asserts a 403 with **zero SELECTs** issued against `program_artifacts` for both denied personas.
- Exclusion set is real, not just asserted: `governance_visibility` (`app/core/rbac.py:196-243`) resolves persona then checks `persona not in _GOVERNANCE_PERSONAS` where `_GOVERNANCE_PERSONAS = {architect, product-manager, developer}` — `cio` and `engineering-manager` both raise `HTTPException(403)` before any cascade. `test_artifacts_route.py` exercises all 5 personas end-to-end through the live route (dev-bypass tokens), including both excluded ones explicitly, not just unit-level mocks.
- Denial leaks nothing: 403 has no response body (`HTTPException(status_code=403)` with no `detail`), and `response_model=ArtifactsResponse` never executes on the denied path since the exception raises before `return`.
- Design-intent match confirmed: `governance_visibility`'s persona set (architect/PM/developer) is the same set the mockups show the "Artifacts generated" panel on (ARC-01/DEV-01/PMD-01 per `ArtifactsPanel.tsx` docstring), CIO/EM excluded on both the design and code side — no drift.
- No new dependency injection bypass: the gate is a bare `await` inside the handler body (matches `personal_usage.py`/`overview.py` precedent), not a `Depends()` that could be omitted or shadowed by a route-level override; single call site, single router.

**IDOR / gate cascade.** After the persona gate passes, `governance_visibility` cascades into `program_visibility`, which is intentionally open-aggregate (any authenticated session, no per-program membership scoping) — this is an established, already-reviewed precedent across every sibling `program-detail` route (README.md documents this exhaustively: token-trend, releases, commands, team, session-time-series all share it). SHP-04 does not introduce new exposure here; it inherits the existing org-wide-visibility model verbatim. An authorized persona (architect/PM/developer) can read any `program_id`'s artifact counts, and an unknown `program_id` returns `200` all-zero rather than `404` — enumerable existence signal is limited to "this program has produced artifacts or not," which is materially the same disclosure shape as `/token-trend`/`/commands`/`/team` (also 200-all-zero-on-unknown-id). Not a new finding; acceptable under the established precedent and consistent with the codebase's chosen trust boundary (any authenticated employee-facing persona, not per-tenant isolation). No `ADR` exception needed since this matches, not deviates from, existing sibling routes.

**Proxy 403→502 collapse (code-review F-1, re-assessed for security).** `apps/web/.../proxy/artifacts/[program_id]/route.ts` maps a FastAPI 403 (governance denial) into the same generic `{error: "upstream_error"}` 502 used for any other backend failure, since `ArtifactsResult` has no `forbidden` variant. From a security angle this is **favorable, not a weakness**: it does not create a new authz bypass (the 403 still occurred and no data crossed the wire — verified by `route.test.ts`'s explicit test asserting body-less 502, not 403, on governance denial), and collapsing a permission denial into an opaque error actually **reduces** the information a client-side attacker can extract (no distinguishable "you don't have access to this specific thing" signal vs. a generic transient failure). The cost is operational (a legitimate engineering-manager/cio user sees an unhelpful generic error instead of a clear "not permitted" message), not a security defect. No finding raised; this is UX/observability debt, already correctly captured as code-review Medium F-1, not a security gate item.

**Token handling.** `artifactsApi.ts` (server-only) is the only module that ever holds `opts.accessToken`, attached as `Authorization: Bearer` only when present (never sent empty). `artifactsApi.client.ts` has no `accessToken` parameter, no `Authorization` header, no `next/headers`/`tokenStore` import — grep-confirmed absent. The proxy route resolves the token via `callWithAuth()` server-side and calls `fetchProgramArtifacts` directly (function call, not a nested HTTP hop) — the token never serializes into a response. Proxy responses (`NextResponse.json(result.data)`, `{error: "session_expired"}`, `{error: "upstream_error"}`) contain no token/bearer field on any path. `ArtifactsPanel.tsx` (`"use client"`) only imports `artifactsApi.client.ts` and calls the same-origin `/api/proxy/artifacts/{id}` with no credentials attached client-side beyond the browser's own session cookie. Matches ADR-0008 exactly; no leak path found.

**Injection / data exposure.** Confirmed above: parameterized ORM `.where()` clause, no raw SQL. Log lines: `rbac_check_governance_visibility` logs only `user_id` + `persona` (`_ALLOWED_FIELDS` allowlist at `rbac.py:317,323`) — no PII, no program_id, no artifact counts. The route itself (`app/api/artifacts.py`) adds zero logging of its own, per its own docstring and confirmed by reading the file — no new log surface to audit beyond the existing, already-reviewed `rbac.py` event.

**Errors.** 403 has no body; 200-path errors don't leak stack traces; FastAPI's standard exception handlers apply (no custom handler added by this diff).

**Stack-pattern pass (fastapi-patterns / nextjs-patterns).** `response_model=ArtifactsResponse` with `extra="forbid"` on `ArtifactItem` (`schemas/artifacts.py:27`) enforces the 5-field contract at the response boundary — no accidental extra-field leak possible. `Depends(get_current_user)`/`Depends(get_db)` used correctly for auth/db wiring; the governance check itself is intentionally a bare `await`, matching the established sibling-route idiom, not a `Depends()` — consistent with `fastapi-patterns` (no anti-pattern). Frontend: no `dangerouslySetInnerHTML`, all dynamic values (`item.tag`, `item.name`, `item.count`) rendered as text content, not `innerHTML`; secrets never in the client component (confirmed above).
