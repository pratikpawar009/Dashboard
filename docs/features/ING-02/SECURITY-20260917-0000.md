## Medium findings

### F-001 — No request body size cap ahead of JSON parse / auth (pre-auth resource exhaustion)

- Source: checklist/input
- Severity: Medium
- File: `services/api/app/api/ingest.py` (generic handler, activity branch)
- Issue: `payload = await request.json()` runs before any auth check
  (`get_ingest_token`) and before the 5000-row cap. There is no
  `Content-Length`/body-size limit configured anywhere in
  `app/main.py` or an ASGI middleware. An unauthenticated caller can send an
  arbitrarily large JSON body and force the server to buffer + parse it
  before the 401 is raised. This is a DoS vector distinct from — and
  upstream of — the already-accepted F-1 perf finding (which is about
  *authenticated, valid* large batches).
- Fix: add a request-size-limiting ASGI middleware (e.g. cap at a few MB,
  comfortably above a legitimate 5000-row batch) or a reverse-proxy-level
  cap, per `.claude/rules/performance-baseline.md` ("I/O has explicit
  timeouts... no silent infinite waits") and OWASP API4:2023 (Unrestricted
  Resource Consumption). Not unique to ING-02's own code — no route in this
  codebase has this control yet — but ING-02 is the first bulk-untrusted-input
  surface where it matters, so it is raised here rather than silently
  inherited.
- Note: this is a pre-existing platform gap ING-02 did not introduce and
  does not worsen relative to sibling ingest endpoints (`/api/ingest/manifest`,
  `/api/ingest/artifacts` have the identical exposure). Not blocking; flagged
  for a follow-up hardening story (e.g. as part of a future rate-limiting /
  API-gateway story) rather than an ING-02-specific fix.

### F-002 — Synchronous per-request `rebuild_program_rollups` has a security-relevant DoS dimension on the accepted F-1 perf finding

- Source: checklist/input (defense-in-depth read of the accepted HIGH F-1)
- Severity: Medium
- File: `services/api/app/services/activity_ingest.py:243`
- Issue: F-1 (accepted per D-04, non-security HIGH) is that p95 exceeds the
  3s NFR budget on a program with a large accumulated `usage_events` table
  (perf suite reproduces 3.67–3.98s at 20k/40k/160k accumulated rows).
  Assessed for a security dimension per this review's brief: the rebuild is
  scoped to `program_id` (bounded to that program's own row count via
  `GROUP BY`/aggregate queries — BED-05 already replaced the old full-table
  Python materialisation), so a single request cannot force an org-wide or
  cross-tenant scan. However, a token scoped to (or holding wildcard access
  to) a program with a very large event history can still be repeatedly
  hammered with minimal-row-count batches to keep triggering the ~4s
  synchronous rebuild — a low-effort, authenticated self-service DoS lever
  against that program's own ingest latency (and indirectly, worker
  availability, since FastAPI's async workers block for the duration).
  No rate limiting exists on this endpoint today.
- Fix: track under the same follow-up as F-1 (CI-provisioned perf gate) plus
  consider a per-token rate limit on `/api/ingest/{kind}` as a hardening
  item. Does not change the F-1 verdict (still a performance finding, not
  independently security-Critical/High) but is real enough to record.
- Relationship to F-1: this is NOT double-counting F-1 as a security finding
  — F-1 itself stays a performance finding accepted per D-04. This Medium
  captures only the incremental "authenticated caller can self-trigger it
  repeatedly with no rate limit" angle, which F-1's review did not evaluate.

## Low findings

### F-003 — `IngestToken.allowed_program_ids` empty-list means allow-all (fail-open by design)

- Source: checklist/auth
- Severity: Low
- File: `services/api/app/core/ingest_auth.py::_check_program_scope`
- Issue: An empty `allowed_program_ids` list (the default produced by
  minting a token without `--program-ids`) grants access to every program,
  identical in effect to the explicit `"*"` wildcard. This inverts the
  fail-closed convention used everywhere else in this codebase (dev-bypass
  allow-list, persona gating, resolver-failure 403).
- Verified: this is a **documented, deliberate** accepted risk — ADR-0006 §
  Consequences and the module docstring both call it out explicitly as
  "DELIBERATE, NOT A BUG." Not re-litigated here; recorded as Low per the
  skill's instruction not to reclassify an ADR-backed decision, and because
  operator error at mint time (omitting `--program-ids`) is the realistic
  trigger, not a code defect.
- Fix (optional hardening, non-blocking): a mint-time warning/confirmation
  when `--program-ids` is omitted would reduce operator-error risk without
  changing the documented contract.

## Item-by-item conclusions (per task brief's 5 scrutiny points)

1. **Ingest-token auth (ADR-0006).** Only `token_hash` (SHA-256 hex digest)
   is persisted (`IngestToken.token_hash`, unique index) — no raw/plaintext
   token column exists on the model (enforced by the model's own docstring:
   "SECURITY CRITICAL... must never gain a column"). Lookup is
   `SELECT ... WHERE token_hash == :hash` — a DB unique-index equality
   lookup, not an application-level string comparison, so there is no
   Python-level (`==`/`hmac.compare_digest`) timing-oracle surface to
   evaluate; the timing characteristics are the DB index lookup's, which is
   not a meaningfully exploitable channel for guessing a 256-bit hash
   pre-image. `unknown`/`revoked`/`expired`/`scope` are returned as
   **distinguishable** HTTP details (`401 unknown`, `401 revoked`,
   `401 expired`, `403 scope`) — this does leak token *lifecycle* state
   (e.g. "this token exists but is revoked" vs "no such token") to a caller
   who doesn't hold a valid token, which is a mild information disclosure,
   but requires already possessing/guessing a real (if revoked/expired)
   token string to observe the distinction between `unknown` and
   `revoked`/`expired` — not exploitable for token enumeration since the
   comparison key is a SHA-256 hash, not a sequential/short ID. Consistent
   with `ingest_files.md`'s frozen contract (`missing`/`unknown`/`revoked`/
   `expired`/`scope` is the documented 401/403 vocabulary in README.md) —
   not a defect to fix, an intentional contract. `"*"` wildcard scope is
   reachable exactly as documented (F-004 above) — no unintended path found.

2. **Scope enforcement.** Confirmed: `program_id` is read from the parsed
   JSON body (`payload.get("program_id")`) BEFORE `get_ingest_token()` is
   called, and that same `program_id` value is passed into
   `get_ingest_token(program_id=program_id, ...)`, which runs
   `_check_program_scope(token.allowed_program_ids, program_id)` and raises
   403 on failure. The service layer (`ingest_files()`) then uses the
   router-resolved `program_id` parameter — never re-reading
   `payload.get("program_id")` — for the write, and additionally rejects
   any individual row whose own `program_id` field disagrees
   (`program_id_mismatch`). No IDOR/cross-tenant-write path found: a
   token cannot write to a program outside its `allowed_program_ids` by
   manipulating the body, and a row cannot smuggle a different scope past
   the envelope-level check either.

3. **Injection + resource exhaustion.** No string-built SQL anywhere in the
   diff — the write path is exclusively
   `sqlalchemy.dialects.postgresql.insert(UsageEvent).values(chunk)
   .on_conflict_do_update(...)`, fully parameterised via SQLAlchemy Core
   bind params; the pre-read is a `select(...).where(tuple_(...).in_(...))`,
   also parameterised. SAST grep pass found zero hits for any Critical/High
   injection pattern in the ING-02 diff. The 5000-row cap IS enforced before
   row parsing/materialisation is passed to the service (router checks
   `len(raw_rows) > 5000` → 413, before calling `ingest_files`), but it runs
   AFTER JSON body parsing and AFTER auth — see F-001 (Medium): no
   byte-size cap exists ahead of `await request.json()`, which is a
   pre-auth resource-exhaustion gap shared by every route on this router,
   not unique to ING-02. Chunking at `_MAX_ROWS_PER_INSERT = 2_730` keeps
   any single INSERT under Postgres's 65,535 bind-parameter ceiling
   (asserted by `test_ingest_bind_param_ceiling.py`, which passed). The
   synchronous `rebuild_program_rollups` call is bounded to the target
   program's own aggregate queries (not a full-table scan — BED-05 already
   fixed that), so it is not an *unbounded* self-inflicted DoS, but see F-002
   (Medium) for the "no rate limit lets an authenticated caller repeatedly
   trigger the ~4s worst case" angle, which has a real (if modest) security
   dimension beyond the already-accepted pure-perf F-1.

4. **PII discipline (C-7).** Verified by reading
   `log_ingest_write_completed()` (keyword-only signature, cannot accept
   `**kwargs`, allowlists exactly `{program_id, rows_received,
   rows_inserted, rows_updated, rows_rejected, duration_ms}`) and by
   re-running `tests/unit/test_ingest_write_completed_pii.py` (passed) and
   `tests/unit/test_ingest_files_auth_denial.py` (passed — auth-denial log
   `ingest_token_auth_failed` allowlists `{token_id, reason, program_id}`
   only, never a raw token or `token_hash`). `RejectionEntry` is
   schema-enforced to `{index: int, reason: str}` — `_classify_row_error()`
   inspects only `err["type"]`/`err["loc"]`, explicitly never `err["input"]`/
   `err["ctx"]` (which would carry the raw offending value), per its own
   docstring. `ActivityRowIn.user` (email) is never referenced by any log
   call or reason string in the reviewed diff. No SAST hit for PII-in-logs
   patterns. Confirmed exhaustively enforced.

5. **Idempotency / data integrity.** Dedup key
   `(model.program_id, model.session_id, model.cmd_ts)` runs on
   `scope_ok` — i.e., only AFTER the program_id-mismatch filter — so a
   crafted batch mixing rows for a foreign `program_id` cannot enter the
   dedup map or the upsert at all (they're rejected first). The DB-level
   `ON CONFLICT` target (`program_id, session_id, cmd_ts`) is the same
   3-column composite as the Python dedup key and matches the table's real
   `UniqueConstraint`, so the DB and the pre-upsert Python dedup agree —
   `ON CONFLICT DO UPDATE` can only ever match a row within the SAME
   program_id, session_id, cmd_ts tuple; it cannot overwrite a different
   program's row. Re-verified by re-running
   `tests/unit/test_ingest_intra_batch_dedup.py` and
   `tests/unit/test_ingest_files_idempotency.py` (both passed). No
   cross-program corruption path found (also see F-005, Low, informational).
