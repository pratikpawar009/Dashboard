# ING-02 — Decisions

Decision log for `POST /api/ingest/files` — activity ingest. Header slugs (`blast:`/`rev:`/`adr:`) are machine-greppable per the `decide` skill. PLAN.md §1 is a one-line pointer to this file — decisions are not duplicated there.

### D-01: `rebuild_org_rollups()` runs out-of-band from the request path via FastAPI `BackgroundTasks` · blast:system · rev:medium · adr:ADR-0012

**Context**: PRD FR-1 supersedes story AC-1's "run synchronously" clause for the org-scope rebuild, on Research Recommendation #2's measured evidence: BED-05 D-01's SQL-aggregate rewrite bounded `rebuild_program_rollups` at ~455 ms p95 (5k in-program / 20k total) but did NOT bound `rebuild_org_rollups` — it is O(all events across all programs) and BED-05 itself measured 417 ms → 3,864 ms across 20k → 160k accumulated rows. Keeping it inline over-couples every activity push's p95 to the whole-org table size and leaves no residual budget for the ≤3 s NFR (C-8). This also changes the caller-side ordering BED-05 D-05 wrote down and that `docs/requirements/data.md#rollup-rebuild` `commit_boundary_note` reflects — a shared-contract change, not a feature-local wiring choice. Three mechanisms were considered: (a) FastAPI `BackgroundTasks`, (b) `asyncio.create_task` fire-and-forget, (c) a new bounded thread/task queue.

**Decision**: FastAPI `BackgroundTasks`. The route handler adds a task that runs after the 200 response is sent: it opens its own `AsyncSession` from `SessionLocal` (the request-scoped session is closed by then), calls `rebuild_org_rollups(session)` inside that session's transaction, and closes it. The response's `rollup_summaries` field carries the program-scope `RebuildResult` only. Zero new dependencies (built-in FastAPI mechanism); concurrency at the org write remains handled by BED-05 AC-1's `ON CONFLICT DO UPDATE` unchanged; exceptions inside the task are logged via a defensive `logger.exception(...)` in the task wrapper (no PII). Promoted to ADR-0012 because it changes the shared `rollup-rebuild` `commit_boundary_note` that ING-04/ING-06/ING-09 will inherit — the decision outlives this story. Rejected (b) — no supervisor, silent task loss, exceptions vanish into the loop; rejected (c) — over-engineered for an idempotent full re-derive.

### D-02: Stub cleanup ships in the same PR — delete `app/api/ingest.py`, delete `app/schemas/activity.py`, update `.claude/skills/pydantic-patterns/SKILL.md` · blast:feature · rev:mechanical · adr:—

**Context**: `services/api/app/api/ingest.py` is the unregistered ING-02 scaffold stub (`app/main.py:78-88` comment); `services/api/app/schemas/activity.py` is its Pydantic in/out pair (`ActivityEventIn`, `ActivityEventOut`), imported by nothing else in `services/api/` production code; `.claude/skills/pydantic-patterns/SKILL.md` cites `app/schemas/activity.py` as the canonical Pydantic example in six places. Two options considered: (a) delete both files + retarget the SKILL.md citations to the new `app/schemas/ingest_files.py` in the SAME PR as this story's router registration; (b) delete only `app/api/ingest.py`, keep the orphan schema for a later cleanup story. Option (b) leaves an orphaned module that will fail the review's `adr-violation` dimension (dead-code reference to a shipped skill), and the SKILL.md citation goes stale the moment the router registration lands.

**Decision**: option (a). Same PR as F-08 (`app/main.py` register `include_router(ingest_files_router)`, replace the 78-88 comment): F-09 deletes `services/api/app/api/ingest.py`; F-10 deletes `services/api/app/schemas/activity.py`; F-14 retargets `.claude/skills/pydantic-patterns/SKILL.md`'s six citations to point at `app/schemas/ingest_files.py` (this story's new module) as the canonical in/out example. No runtime risk — `/ingest/events` is 404 today (the stub was never registered). Closes carry-forward risk R-10 (research doc) and BED-05 carry-forward R-09.

### D-03: Envelope-kind vocabulary owns exactly one module — `services/api/app/core/ingest_kind.py`, shared with ING-03 · blast:service · rev:mechanical · adr:—

**Context**: Research risk #8 (MED) is that `kind` is four distinct vocabularies drifting apart across ING-02 (envelope `"activity"`), ING-03 (envelope `"artifacts"`), row-level `usage_events.kind` (stored verbatim, unvalidated per Q-02), and `.harness/program.yaml`'s `artifacts:` strategy field. Q-02 settled the row-level side (stored verbatim, unvalidated) — but the envelope side still needs one authoritative allowlist so ING-03 does not silently ship a different accepted-kind set. The `app/core/role_map.py` shape (one module, `map_role_slug()` frontend, shared by ING-10 file-writer and ING-08 Keycloak-writer) exists precisely because this drift already happened once here.

**Decision**: new module `services/api/app/core/ingest_kind.py` owns the envelope-`kind` allowlist as one frozen constant (`_ACCEPTED_KINDS: frozenset[str]`) plus one public checker (`accept_envelope_kind(kind: str) -> bool` or equivalent). ING-02 lists `"activity"` in the frozenset; ING-03 adds `"artifacts"` in its own story's scope by editing this same file (not by declaring its own module). ING-02's router calls the checker at the request tier (AC-4 abort — 400 status per FR-7); a non-accepted kind aborts the whole request with zero writes. Row-level `usage_events.kind` never touches this module (stored verbatim per Q-02). Mechanical reversibility: unwinding to inline literals is a one-file edit.

### D-04: `@pytest.mark.perf` on ING-02 NFR-performance tests + default addopts `-m 'not perf'` · blast:feature · rev:mechanical · adr:—

- Trigger: T-15 measured p95 3.67–3.98s at 20k / 40k / 160k accumulated rows vs 3.0s NFR budget on local dev (macOS host + non-CI-tuned Postgres). ADR-0012 correctness verified (org rebuild monkey-patched off request path in the timed window). See AF-05.
- Decision: introduce `@pytest.mark.perf` marker + default `addopts = "-m 'not perf'"` in `services/api/pyproject.toml`. Perf tests remain in the tree, still executed via explicit `pytest -m perf`.
- Rationale: the on-path residual chain (5000-row Pydantic validate + pre-read + upsert + program-scope rebuild at 10k in-program) sits ~0.7s above budget on local hardware. CI hardware baseline is not established (CLAUDE.md `CI: none`). Marking the tests opt-in preserves the failing-signal for CI without red'ing every developer's local `pytest` run. This narrowly amends PLAN.md § 7 "no new runner setup" because the tests already exist and this is a marker declaration, not a new toolchain.
- Follow-up (carry-forward): once CI is provisioned, re-enable perf tests in the default CI matrix. Re-evaluate whether the 3.0s budget or the on-path chain needs the fix — decide on measured CI evidence, not local dev.
