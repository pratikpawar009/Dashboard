## Manual OWASP checklist + stack-pattern pass

### 1. RBAC / broken access control

`program_visibility(current_user, program_id)` (`services/api/app/api/overview.py`, new route
`get_program_commands`) is called once, before the DB read, with the real `program_id` —
confirmed identical call shape to `get_program_detail`, `get_program_token_trend`,
`get_program_releases` on the same router. By contract (AUTH-03 D-03) it is an open-aggregate
veto gate: it validates session authenticity only and never reads `current_user.programs` or
branches on `program_id`. Any authenticated user (any persona) can therefore fetch any
program's command-usage breakdown.

Compared this against the three sibling security reviews:
- PGD-01 `SECURITY-2026-09-15.md` F-1: same finding, rated **Low**, tracked as an architectural
  acceptance (product/architecture-owned) rather than blocking.
- PGD-02 `SECURITY-20260916-1330.md`: confirms the same gate, "consistent, not an enumeration
  oracle," no severity escalation.
- PGD-03 `SECURITY-20260916-1526.md` F-002: same pattern applied to a *new resource type*
  (release identifiers), still rated Low/non-blocking, but flagged for product re-affirmation
  since release data carries more competitive-signal value than aggregate counts.

Judgment for PGD-04: command-usage breakdown (which slash-commands a program runs, and how
often) is comparable in sensitivity to PGD-01's aggregate cards and PGD-02's token-trend
series — it is operational-usage metadata, not PII, not a security credential, and not
per-user (no `usage_events.user` column is read or returned — see point 4 below). It does not
introduce a *new* class of sensitive data the way PGD-03's release identifiers arguably did.
No escalation beyond the established Low is warranted; this review does **not** find grounds to
diverge from the sibling pattern. Recorded as a finding for completeness and continuity of the
existing architectural-acceptance trail — not new information for the product/architecture
owner, who has already accepted this model three times running on this router.

### 2. Enumeration oracle (no-404 on unknown program_id)

`fetch_program_commands()` performs no `program_summary` existence lookup (D-02); an unknown
`program_id` and a known-but-quiet `program_id` both produce a zero-row `GROUP BY` result and
resolve to the identical `200 {total_runs: "0", items: []}`. Verified in
`services/api/app/services/program_commands.py::_build_commands_panel` — `rows=[]` → the same
code path regardless of *why* rows is empty.

This is the same reasoning PGD-02's security review already cleared for `/token-trend`'s
no-404 zero-fill pattern (README.md documents PGD-02 returning 200 for any `program_id`,
including unknown ones, for the same "true empty state" reasoning). Since the response shape
for "exists, no activity" and "does not exist" is byte-identical and the response never varies
in latency-observable ways tied to existence (single aggregate query either way, confirmed no
conditional branch or early return in the service function), an attacker cannot distinguish
"program exists but is quiet" from "program does not exist" via this endpoint. Verdict: **not
a distinguishing oracle** — the reasoning holds, same as PGD-02's precedent. No finding raised.

### 3. Injection

`program_id` flows as a FastAPI path parameter directly into
`select(UsageEvent.command, func.count(UsageEvent.id)).where(UsageEvent.program_id ==
program_id, UsageEvent.ts >= range_start)` — a SQLAlchemy Core `select()`/`.where()` construct.
No f-string, no `%`-formatting, no raw string concatenation anywhere in
`program_commands.py`; SQLAlchemy binds `program_id` and `range_start` as parameters at
execute time. `range` never reaches the query as a raw string — it is first resolved by
`_range_with_default` → `validate_range()` (shared, unedited dependency) to one of exactly
`{"7d", "30d", "90d"}`, raising `HTTPException(400, "invalid_range")` for anything else, and
only the resulting `range_start` datetime (computed via `range_to_start()`) is bound into the
query. No injection surface. No finding raised.

### 4. PII / log hygiene

Route emits exactly one structured log call:
```python
logger.info(
    "program_commands_fetched",
    extra={"method": "GET", "path": ..., "program_id": program_id, "range": range,
           "status": status.HTTP_200_OK, "latency_ms": int(...)},
)
```
Allowlist keys: `method, path, program_id, range, status, latency_ms` — matches the
`program_releases_fetched` precedent exactly and the README's documented allowlist discipline
(ING-02/ING-03's `ingest_write_completed`/`ingest_artifacts_write` pattern). Confirmed the
underlying SQL query (`fetch_program_commands`) selects only `UsageEvent.command` and
`func.count(UsageEvent.id)` — `usage_events.user` (which holds real email addresses per
README) is never selected, never touches `rows`, and cannot reach the log call even
transitively. No email, user identifier, or raw command payload reaches any log line. No
finding raised.

### 5. Token handling on the frontend proxy

`apps/web/src/app/api/proxy/program-detail/[program_id]/commands/route.ts` follows the ADR-0008
full-proxy pattern exactly: resolves the access token server-side via
`callWithAuth((accessToken) => fetchProgramCommands(...), isUnauthorized)`, never accepts or
forwards a token from the incoming `Request`, and the token is passed only as a function
argument into `fetchProgramCommands()` (`apps/web/src/lib/programCommandsApi.ts`), which uses
it solely to set an outbound `Authorization: Bearer <token>` header to FastAPI — never echoed
into the `NextResponse.json(...)` body or any response header. The route's own test suite
(`route.test.ts`) includes an explicit assertion for this: `"never lets the access token reach
the browser"` checks `response.headers.get("authorization")` is null and that the JSON body
string never contains the sentinel token. Verified this test exists and asserts the correct
thing. No finding raised.

### 6. DoS / unbounded work (no pagination)

`fetch_program_commands()` returns every distinct `command` value found for `program_id` within
the range window — no `LIMIT`/`OFFSET`, no page size cap. `.claude/rules/performance-baseline.md`
requires pagination on every list endpoint.

Mitigating context: (a) this is a `GROUP BY` aggregate over a *bounded input alphabet* in
practice — `usage_events.command` values originate from a fixed, closed set of Harness CLI
slash-commands (`/deploy`, `/plan`, etc.), not free-form user text, so cardinality per program
per range is small (tens, not thousands); (b) the identical unpaginated shape already exists
and shipped in SHP-02's `fetch_commands_breakdown` (`app/services/personal_usage.py`), which
this module explicitly mirrors line-for-line (`WHERE "user"` → `WHERE program_id`) — PGD-04
does not introduce a new unpaginated pattern, it reuses an already-accepted one; (c) response
size is bounded by index-backed grouped aggregation (`ix_usage_events_program_id_command`), not
a raw row scan returned to the client — the perf test suite
(`tests/perf/test_program_commands_perf.py`) asserts the NFR-002 ≤2s budget at 7d/30d/90d and
passed (3/3). However, the `command` column has no DB-level or schema-level closed-vocabulary
constraint (it's a free-text `String`) — if a future ingest source ever emits high-cardinality
or adversarial command strings, this endpoint's response size grows unbounded with no cap. This
is a real, if currently low-probability, divergence from the pagination rule, consistent with an
already-accepted precedent rather than a new regression.

```
  rule_id:   performance-baseline.md (pagination)
```
