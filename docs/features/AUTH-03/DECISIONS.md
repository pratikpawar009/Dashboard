# AUTH-03 — Decisions

Story-level decision log. One `### D-NN` entry per non-trivial technical choice made while planning AUTH-03. `blast:`/`rev:` are greppable slugs (see skill `decide`); `adr:` names the full ADR when promoted.

### D-01: `PersonaResolutionError` and `PersonaNotFoundError` both deny with HTTP 403, at distinct log levels · blast:service · rev:mechanical · adr:—

**Context**: research condition C-1 (risk #2, HIGH) flagged that the story did not prescribe how a check should react to the persona resolver's two failure modes — a Tier-3 timeout/connectivity failure (`PersonaResolutionError`) versus an ordinary unmapped role (`PersonaNotFoundError`). Getting this wrong either locks out users on a transient DB hiccup (if treated as a 500) or blurs an operational failure into routine deny traffic (if logged identically). Because every one of the five checks' persona-resolving branches follows this same call-site pattern, the choice governs authorization behavior across the whole API service, not just one function.

**Decision**: both exceptions raise `HTTPException(status_code=403)` — zero default-permit, ever. They are caught in two separate `except` clauses (never a bare `except Exception`) at every call site that resolves persona (`org_access`, `individual_usage_visibility`'s non-self branch, `member_in_program_visibility`'s non-self branch, `governance_visibility`). `PersonaResolutionError` additionally logs the calling check's own `rbac_check_*`/`*_view_denied` event at `logging.ERROR` (an operational failure); `PersonaNotFoundError` logs at the check's normal `logging.INFO` level (a routine deny). The resolver's own `persona_mapping_loaded` event (AUTH-02) is unaffected either way.

### D-02: Per-event log field allowlists are fixed, no `reason` field · blast:feature · rev:mechanical · adr:—

**Context**: research condition C-2 (risk #3, HIGH) flagged that the exact payload per log event was unspecified, including whether an enriched `reason` field (e.g. `"role is not in {architect, product-manager, developer}"`) should ride along for audit-trail readability (research recommendation 9a floated this as optional).

**Decision**: four fixed allowlists, no `reason` field and no other addition: `rbac_check_org_access`/`rbac_check_governance_visibility` → `{user_id, persona, outcome, timestamp}` (both outcomes); `individual_view_denied` → `{user_id, target_user_id, outcome, timestamp}` (denials only); `member_view_denied` → `{user_id, program_id, target_member_id, outcome, timestamp}` (denials only). `outcome` is always the literal string `"authorized"` or `"denied"` — never a boolean, never a free-text substitute. A PII-audit test per event asserts the payload key set equals its allowlist exactly (AUTH-03-TC-20..23), mirroring AUTH-02-TC-15's pattern. No `email`, `groups`, JWT claim, or session context in any event.

### D-03: `program_visibility`'s open-aggregate model ships exactly as specified; R-003 stays OPEN, not tightened · blast:feature · rev:mechanical · adr:—

**Context**: research condition C-3 (risk #1, HIGH) asked whether AUTH-03 should implement `program_visibility` as a genuine pass-through (any authenticated session passes, `program_id` unused for gating) or add membership scoping. This model is inherited from the parent PRD's assumption A-004 and tracked there as risk R-003 (`docs/prd/ai-sdlc-adoption-dashboards.md` §Assumptions/§Risks, open question Q-001) — it is not a new architectural choice this story is making, only a decision about whether to implement the inherited model faithfully or unilaterally tighten it.

**Decision**: `program_visibility` implements AC3 exactly as specified — it never reads `current_user.programs` (AUTH-03-TC-27 asserts this structurally, not just behaviorally) and never rejects on any `program_id` value (AUTH-03-TC-04). R-003 is **not** accepted or closed by this decision; it remains OPEN at the parent-PRD level and is explicitly flagged for `/arh-security-review` re-examination, per the Product Gate approval (`REQUIREMENTS.md` § Approvals, 2026-08-31). Downstream consumers must read `CurrentUser.programs` directly for roster questions — a passing `program_visibility` call is a veto gate, not an affirmative membership signal (module docstring makes this explicit, per Documentation requirements).

### D-04: Governance persona set is a hardcoded module constant, not config-driven · blast:feature · rev:mechanical · adr:—

**Context**: research risk #8 (MEDIUM) noted the contrast with AUTH-02's fully data-driven resolver: a hardcoded list means adding a persona to governance access needs a code change and redeploy, and could silently mis-deny a newly introduced persona if someone forgets to update it. `REQUIREMENTS.md` AUTH-03-FR-3 already settles this in scope, but the trade-off is worth recording since a competent reviewer could reasonably ask why this constant isn't promoted to `Settings` alongside AUTH-02's env/YAML tiers.

**Decision**: `_GOVERNANCE_PERSONAS: tuple[str, ...] = ("architect", "product-manager", "developer")` is a plain module-level constant in `rbac.py`, with a docstring/comment noting the deliberate contrast with AUTH-02's data-driven resolver. `cio` and `engineering-manager` are excluded (AC6). Promoting this to `Settings` + an env var is out of scope for this story (`REQUIREMENTS.md` § Scope, Out) and left for a future story if ops needs to change the set without a redeploy.

### D-05: No request-scoped persona-resolution memoization added · blast:feature · rev:mechanical · adr:—

**Context**: research risk #4 (HIGH) flagged that a route applying multiple RBAC checks in one request (e.g. `org_access` + `governance_visibility`) calls `persona_resolver.resolve(role)` once per check; AUTH-02's per-role 300s cache bounds each individual call to a warm dict lookup, but does not deduplicate the call itself across checks within a single request. Adding a request-scoped memo layer here would touch this story's public contract (an extra parameter or context object every one of the 16 downstream consumers would need to thread through).

**Decision**: no request-scoped memoization is added in this story (`REQUIREMENTS.md` § Scope, Out). AUTH-02's per-role cache is relied on as-is — a warm hit is already <1ms (AUTH-02-TC-12), so the worst case for N checks in one request is N warm cache reads, not N Tier-3 queries. Deferred to a post-launch optimization story if cache-hit-rate/latency monitoring shows it is actually needed, per the story's own Scope note.

### D-06: `rbac.py` reaches `PersonaResolver` via a module-level `configure()` seam, not a `Request` parameter · blast:service · rev:mechanical · adr:—

**Context**: the `rbac-checks` contract locks all five signatures to `current_user: CurrentUser` first, plus only `program_id`/`target_user_id`/`target_member_id` where a check needs one (`docs/requirements/auth.md#rbac-checks`, mirrored in `REQUIREMENTS.md` § Solution sketch) — "names, parameter order, and count are locked". `org_access`, `individual_usage_visibility`, `member_in_program_visibility`, and `governance_visibility` all resolve persona via AUTH-02's `PersonaResolver`, which today lives only on `app.state.persona_resolver` (`app/main.py:43`) and is otherwise reached exclusively through a FastAPI `Request`-scoped dependency (the `get_jwks_cache(request: Request)` pattern in `app/auth/jwks.py:216`). Since the locked contract has no `request`/`resolver` parameter, none of the five checks can reach `app.state` the way every other stateful dependency in this codebase does — a real gap the file/task plan must close, not leave implicit.

**Decision**: `app/core/rbac.py` exposes a module-level `_persona_resolver: PersonaResolver | None = None` plus a public `configure(persona_resolver: PersonaResolver) -> None` setter; every persona-resolving check reads it through a private `_resolver()` accessor that raises `RuntimeError` (loud, not a silent default-permit) if `configure()` was never called. `app/main.py`'s `create_app()` calls `rbac.configure(app.state.persona_resolver)` immediately after constructing the resolver (F-05). This is a deliberate, scoped exception to D-07's "never a module singleton" rule for `Settings`/`JwksCache`: those must support several independently-configured `create_app()` instances coexisting in one test process, while `rbac.py`'s own unit tests never build a FastAPI app at all — they call `rbac.configure(stub_resolver)` directly before exercising a check, the same direct-module-attribute-assignment idiom `tests/unit/test_persona_resolver.py` already uses (`monkeypatch.setattr(persona_resolver, "_TIER3_TIMEOUT_SECONDS", 0.05)`). Downstream consumers (AUTH-04, OVW-01..04, PGD-01..06, SHP-02..06) are unaffected — they still just `from app.core.rbac import org_access` and call it; the wiring is invisible plumbing already satisfied by the one `create_app()` their routes run under.
