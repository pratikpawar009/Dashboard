## Scrutiny — the 5 specified points

### 1. Open-aggregate design (D-03) — safe as designed, and clearly documented at every call site

`program_visibility` (`rbac.py:100-113`) is a one-line `return None` — it
takes `program_id` as a parameter but never reads it, and never touches
`current_user.programs`. This is provably true, not just documented: TC-27
uses a `CurrentUser` test double whose `.programs` property raises
`AssertionError` if accessed, and TC-04 asserts the function's outcome is
identical across a set of dummy/nonexistent `program_id` values. This is a
structural test, not a behavioral coincidence that could regress silently.

**Documentation at the call site — verified, not merely claimed:** every one
of the 6+ downstream call sites carries an explicit, non-generic inline
comment naming it a "veto gate, not a roster source" and pointing at the real
scoping mechanism:
- `services/api/app/api/programs.py:9-16` — names `_VETO_GATE_SENTINEL_PROGRAM_ID`
  as a value chosen specifically to make "this is never consulted for scoping"
  visible at the call site; the real scoping is the `WHERE program_id IN
  current_user.programs` clause immediately below.
- `services/api/app/api/overview.py:18,39,51,201,239,292` — each of the five
  `program_visibility(current_user, program_id)` call sites carries its own
  "byte-identical response across every persona" / "never filters by
  current_user.programs" comment, not a single shared comment referenced by
  proxy.
- `docs/requirements/api.md`'s `rbac-checks` contract table repeats the same
  language for `program-detail-api`, `program-token-trend-api`,
  `program-releases-api`, `program-commands-api`.
- `README.md`'s public API table states the same thing at the product-doc
  level: "A 200 is not proof of program membership."

This is about as hard as the pattern can be made not to be misread: the
sentinel constant, the module docstring, the per-call-site comment, the
contract doc, and the public README all restate the same invariant in
different words a future engineer would have to actively ignore four
independent artifacts to miss. This is a defensible design choice given the
inherited PRD assumption A-004 — not something AUTH-03 introduced — and R-003
is correctly tracked as an OPEN risk rather than silently accepted. **No
finding raised; this is the review this risk was flagged for, and the
conclusion is that the mitigation (radical, redundant documentation at every
consumption point) is adequate, though the underlying architectural choice
(no per-resource authorization on 6 GET endpoints) remains a standing product
risk that only a future roster-membership-check story can close.** This
review does not close R-003 — it is a design risk, not a code defect, and
closing it is a product decision, not a security-review verdict.

### 2. Checks that DO gate — verified enforcing, no bypass found

- **`individual_usage_visibility`**: self path short-circuits on exact string
  equality (`target_user_id == current_user.user_id`); no persona resolution,
  no wildcard, no case-folding that could be exploited (both sides are the
  same `sub`-derived opaque `user_id`, not attacker-formattable). Non-self
  path requires persona `== "cio"` exactly — no substring/prefix match, no
  `in` check that could be tricked by a crafted role string. Fail-closed via
  `_resolve_persona_or_deny` (see point 3).
- **`member_in_program_visibility`**: cascades through `program_visibility`
  first (open-aggregate, cannot deny — see point 1), then self-or-cio exactly
  as above. TC-10 proves the call *order* with a spy, so a future change that
  silently reorders (e.g. moving the data read before the gate) would be
  caught by this test, not just an end-to-end assertion that could pass by
  coincidence.
- **No role spoofing / missing-claim default-open path found**: `persona` is
  always the return value of `_resolver().resolve(current_user.role)` — never
  a caller-supplied argument, never defaulted to a placeholder. Comparisons
  are all exact string equality against `"cio"` or membership in the 3-entry
  `_GOVERNANCE_PERSONAS` tuple. No code path returns/treats `None`/empty
  string as authorized — an empty or unmapped role raises `PersonaNotFoundError`
  before a persona value ever exists to compare (see point 3).
- **Fail-closed on resolution errors**: confirmed — both `PersonaNotFoundError`
  and `PersonaResolutionError` raise `HTTPException(403)` in every one of the
  four persona-resolving checks, exclusively through the shared
  `_resolve_persona_or_deny` helper. No call site has its own separate
  error-handling logic that could diverge.

### 3. Persona resolution — fail-closed on unmapped role, fail-open (safely) on Tier-1 JSON parse only

Traced the full resolution chain in `persona_resolver.py`:
- **Unmapped role (all 3 tiers miss)**: `_lookup_tiers` returns `None` →
  `_resolve_uncached` raises `PersonaNotFoundError(role)` (`persona_resolver.py:382-387`)
  → every call site (both in `rbac.py` and `programs.py`) catches this and
  returns `HTTPException(403)`. **Fail-closed, confirmed in code**, matching
  README's documented behavior.
- **Tier-3 timeout / connectivity failure**: `wait_for(..., timeout=3.0)` on
  `TimeoutError` raises `PersonaResolutionError` (`persona_resolver.py:447-450`,
  `521-524`) → same 403 fail-closed path. **Fail-closed, confirmed in code.**
- **Tier-1 env var parse error** (`PERSONA_ROLE_MAP` malformed JSON): this
  behavior lives in `app/core/config.py` (Settings), not `persona_resolver.py`
  — not part of AUTH-03's diff, but checked for consistency per the task's
  explicit ask. README documents this as fail-open-on-parse (falls through
  to Tier-2/3, not an outright authorization bypass) — a malformed override
  degrading to the next tier, rather than to an unauthenticated default-permit,
  is a safe degradation: the ultimate fallback is still Tier-3 Postgres or,
  failing that, the fail-closed `PersonaNotFoundError` path above. Not a
  vulnerability; consistent with the documented contract.
- **Tier-2 YAML malformed**: raises uncaught at `PersonaResolver.__init__`
  (`FileNotFoundError`/`yaml.YAMLError`/`ValueError`) — a startup failure, not
  a runtime fail-open. Confirmed by module docstring and constructor code
  (`persona_resolver.py:186-220`). This is the correct posture: a bad config
  file should never let the app boot into a default-permit state.

**Conclusion: both the fail-open PARSE behavior (Tier-1 only, degrades to the
next tier) and fail-closed UNMAPPED behavior (403) are confirmed in code, not
just documentation.**

### 4. Audit logging — no PII, contract honored

Confirmed via `_EVENT_REQUIRED_FIELDS`/`_EVENT_OPTIONAL_FIELDS` (structurally
enforced, see Data section above) that only `org_access`,
`rbac_check_governance_visibility`, `individual_view_denied`, and
`member_view_denied` emit events, and `program_visibility` — the open-aggregate
check — emits none (`rbac.py:113`, a bare `return None`, no `_log_event` call
anywhere in the function body). No email, token, session id, JWT claim, or raw
user-supplied string reaches any log line in either `rbac.py` or
`persona_resolver.py`. `user_id` is the JWT `sub` — an opaque identifier
permitted under `security-baseline.md`.

### 5. Privilege escalation — no path found

- No missing check: every one of the 5 exported functions in `rbac-checks`
  performs its comparison before returning; there is no code path that
  returns `None` (authorized) without first either (a) confirming `persona ==
  "cio"`/`persona in _GOVERNANCE_PERSONAS`, (b) confirming self-target
  equality, or (c) being the deliberately-always-passing `program_visibility`
  (which is a documented veto gate, not a data-access authorization —
  addressed in point 1, and it is never the *sole* gate any consumer route
  relies on for a per-resource decision beyond "session is valid").
- No default-argument bypass: `governance_visibility`'s `program_id:
  str | None = None` default only widens the check when a route *doesn't*
  pass a `program_id` (skips the cascade, matching AC7's documented behavior
  for governance-only routes with no program dimension) — it never weakens
  the persona gate itself, which always runs first and unconditionally
  (`rbac.py:224-232`).
- No ordering bug found in the 6 downstream call sites inspected
  (`programs.py`, `overview.py`, `personal_usage.py`): the RBAC check is
  always awaited before the response body is constructed/queried
  (`await program_visibility(...)` / `await org_access(...)` /
  `await individual_usage_visibility(...)` precede any data fetch in each
  handler body inspected).
- A `developer` persona cannot reach `cio`-only data (`org_access`,
  non-self `individual_usage_visibility`, non-self `member_in_program_visibility`)
  through any path in this module — all three require exact-match `persona ==
  "cio"`, and persona is server-resolved, never client-suppliable.
