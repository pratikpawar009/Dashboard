## Scope verified

### 1. AuthZ / IDOR — gate-before-query ordering

`GET /api/overview/program-detail/{program_id}/session-time-series` (`services/api/app/api/overview.py:445-493`):

- `program_visibility(current_user, program_id)` runs first (open-aggregate veto per AUTH-03 D-03 — confirmed non-scoping: never reads `current_user.programs`, never branches on `program_id`).
- When `member_id` is present, `member_in_program_visibility(current_user, program_id, member_id)` (`app/core/rbac.py:144-184`) runs next, **before** `fetch_program_session_series` is called (line 481) — structurally, not just in sequence: the gate raises `HTTPException(403)` inline, so the line invoking the service function is never reached on a denial.
- Confirmed by `test_non_self_non_cio_member_filter_denied_before_query_tc08` (`services/api/tests/unit/test_program_session_series_route.py:301-354`), which asserts (a) a SQLAlchemy query-count spy sees **zero** `session_series`-matching queries on the denied path, and (b) `resp.json().keys() == {"error"}` — no `points`/`period_total_seconds`/`avg_seconds_per_day` leak on 403. This is a stronger proof than a bare status-code assertion.
- `program_drilldown` (the success-path log) only fires after `fetch_program_session_series` returns (line 483), never on the 403 path.
- No path found for an unauthenticated or cross-program caller to read another member's session data: `member_id` flows only into a bound SQL parameter (`SessionSeries.member_id == member_id`, `program_session_series.py:97`), never into string-built SQL, and the self-or-cio branch is the sole access control once `program_visibility` passes.

### 2. 403-vs-404 — reasoned position (concur with the review agent)

`.claude/rules/security-baseline.md`'s "return 404, never 403" clause is scoped explicitly to the **per-resource mutation ownership** pattern it defines alongside it: a `_load_owned(id, user_id) -> Resource | None` helper backing PATCH/PUT/DELETE, where 403 would confirm a *specific resource id* exists under someone else's ownership. `GET .../session-time-series` is not that shape:

- It is a read-only, org-scoped aggregate. `program_id` existence is never gated at all — an unknown `program_id` returns `200` with an all-zero, zero-padded series (D-04), matching every non-`releases` PGD sibling. There is no ownership predicate and nothing about a 403 confirms `program_id` exists (it already doesn't gate that).
- The 403 in question gates `member_id`, not `program_id`, and only fires when `member_id` is supplied and is neither the caller nor is the caller `cio`. This is a **persona/role check on an already-open aggregate resource**, not a per-record ownership check — closer to "you don't have the CIO role" than "this record isn't yours." It also predates this diff: `member_in_program_visibility` is AUTH-03 code, already applied identically at PGD-05's `/team/{member_id}/usage` route and passed that security review with the same reasoning.
- No enumeration oracle exists: varying `member_id` while denied always returns the same `403 {error:"denied"}` shape regardless of whether that `member_id` corresponds to a real roster member, a real-but-inactive member, or a nonexistent string — the gate never differentiates "member doesn't exist" from "member exists but you can't see it." An attacker learns nothing about roster membership from the response.
- Conclusion: no real IDOR/enumeration finding here. Flagging this would be reclassifying a persona gate as a resource-ownership check the rule doesn't intend to cover, and would contradict PGD-05's own settled precedent. Not raised as a finding.

### 4. Logging / PII — reasoned position

Grepped every new/changed `logger.*`/`console.*`/`print(...)` call in the diff:

- The new route's own log event, `program_drilldown` (`overview.py:483-493`), carries `{method, path, program_id, range, status, latency_ms}` only — **no `member_id`, no email, no name**. This is the only logging PGD-06 itself introduces.
- `member_view_denied` — logged by `member_in_program_visibility` with `{program_id, target_member_id}` (plus `_resolve_persona_or_deny`'s own fields) — is **pre-existing AUTH-03 code**, unmodified by this diff (`app/core/rbac.py:180-184`, no changed lines in `git diff origin/main...HEAD` for `rbac.py`). `target_member_id` in this system is a git-config email (per README.md), so this is technically PII-in-logs under `.claude/rules/security-baseline.md`'s literal wording ("never log PII... email").
- This exact pattern was already scrutinized and accepted at PGD-05's security review (`docs/features/PGD-05/SECURITY-20260917-1500.md`, Scope item 1: "no email, no name... on the denial path" — that review characterized the field as an opaque identifier, not PII, since `user_id`/`target_member_id` in this system's identity model *is* the canonical resource identifier, structurally equivalent to `user_id` in the rule's own example). I concur with that precedent but flag it explicitly rather than silently inheriting it: **this project's canonical user identifier is itself an email address** (`git config user.email`), which sits in genuine tension with the rule's "opaque identifiers only" guidance. It is a pre-existing, system-wide design decision (every `usage_events.user`, `program_roster` entry, and RBAC log field carries this same identifier) — not something PGD-06 introduces or could fix by itself.
- Recorded as **Low, carry-forward, not blocking**: this is not new to PGD-06 and re-litigating AUTH-03's identity model inside a single downstream story's security review would be scope creep. If this is to change, it needs a dedicated ADR (e.g., introduce an opaque internal user id separate from the git-email identity) applied system-wide, not a per-route patch.

### 5. Input validation

- `range` — validated via `_range_with_default` → `validate_range` (`app/dependencies/range.py:45-63`, unmodified in this diff) against `{7d, 30d, 90d}`, explicit `400 invalid_range` before the route body runs; a rejected value is logged capped/redacted (`_capped_rejected_value`), not raw.
- `member_id: str | None = Query(None)` — no format/length validation. Assessed as acceptable: it flows only into a bound SQL equality predicate (`SessionSeries.member_id == member_id`), so a malformed or over-long value produces an empty-result query (zero rows, all-zero series), never a crash, injection, or resource-exhaustion vector. Matches the sibling `/team/{member_id}/usage` route's identical lack of format validation on the same field type — not a new gap introduced here.
- `program_id` — path param, unvalidated format, but never used for existence checks (D-04) and only ever bound into the same parameterized query — no different risk than the identical pattern on every other PGD sibling route.

### 6. Proxy / token handling

`apps/web/src/app/api/proxy/program-detail/[program_id]/session-time-series/route.ts` + `apps/web/src/lib/programSessionSeriesApi.ts`:

- Access token is read server-side via `callWithAuth()`/`tokenStore` and attached only as `Authorization: Bearer <token>` on the outbound FastAPI call (`programSessionSeriesApi.ts:50-51`) — never placed in a response body, header, or any client-reachable value. Matches ADR-0008.
- `403` → `{error:"denied"}`, `401` → `{error:"session_expired"}`, any other failure → `{error:"upstream_error"}` (502) — no upstream response body is ever forwarded verbatim on any path. AF-01 (proxy previously collapsed 403→502) was triaged, accepted, and fixed this session; verified fixed in the shipped code (`route.ts:63-64`, `programSessionSeriesApi.ts:65-67`).
- `FETCH_TIMEOUT_MS = 5000` via `AbortSignal.timeout(FETCH_TIMEOUT_MS)` (`programSessionSeriesApi.ts:11,62`) — bounded I/O timeout present, satisfying `.claude/rules/performance-baseline.md`'s "I/O has explicit timeouts" requirement. Matches every sibling fetcher's budget.

### 7. DoS / resource exhaustion — reasoned position

- D-02 is an explicit, documented, accepted decision: no new index for the org-wide (unfiltered) `session_series` scan; guarded instead by `tests/perf/test_program_session_series_perf.py`, which seeds ≥5,000 rows / ≥50 members over 90 days and asserts (a) exactly one query (no N+1/per-day loop) and (b) wall-clock stays within a 2000ms budget (observed 4–11ms per the story's own evidence). This is "profile, then change" done correctly, not silently ignored — matches `.claude/rules/performance-baseline.md`.
- No pagination applies (the response is a fixed-length 7/30/90-point series, not an open-ended list — pagination doesn't apply to this shape, consistent with the `/token-trend` sibling it mirrors).
- No rate limit exists on this endpoint. Assessed: this is **not a divergence PGD-06 introduces** — none of the eight sibling routes on this `overview` router (`program-detail`, `token-trend`, `releases`, `commands`, `team`, `team/{member_id}/usage`) have a rate limit either; there is no rate-limiting middleware anywhere in `services/api` today. An authenticated caller could request `?range=90d` repeatedly as a cheap amplification vector (single indexed-adjacent scan, sub-15ms per the perf test, so "cheap" for the caller but also cheap for the server at current volume) — this is a real, generic gap in the API's operational posture, but it is system-wide and pre-existing, not specific to or worsened by this story. Recording as a Low carry-forward rather than blocking this story on a system-wide rate-limiting gap it did not create.
