### F-002 — Open-aggregate `program_visibility` exposes release data org-wide (design-accepted, flagged for awareness)

- Source: checklist/auth
- Severity: Low
- File: `services/api/app/api/overview.py:220-260` (`get_program_releases`)
- Detail: `program_visibility(current_user, program_id)` is confirmed genuinely server-side (called before the DB read, `await`ed, raises on failure) and the response is byte-identical across personas — no persona branching found anywhere in `program_releases.py` or the route. This matches the established PGD-01/PGD-02 contract and is not a new regression. However, this is a new resource type: release version strings, story/PR counts, and release dates for *any* program in the org become readable by *any* authenticated user, regardless of `session.programs`. Unlike aggregate token/summary counts (PGD-01/PGD-02), release version identifiers can be a meaningful competitive/scheduling signal across program boundaries. This is the same open-aggregate pattern already accepted for two prior endpoints, so it is not blocking, but it is worth the product/architecture owner explicitly re-affirming the scope decision for this specific data type rather than inheriting it silently.
- Fix (if scope is reconsidered): none required for this gate; if the team later wants program-scoped access to releases specifically, that is a product decision, not a code defect.

### F-003 — Unbounded `offset` query parameter

- Source: checklist/input
- Severity: Low
- File: `services/api/app/api/overview.py:196-201` (`_releases_offset_limit`)
- Detail: `offset: int = Query(0, ge=0)` has no upper bound; `limit` is clamped via `min(limit, MAX_OFFSET_LIMIT)` but a client can request `offset=999999999`. This mirrors the pre-existing shared `get_offset_limit` dependency's shape (`app/dependencies/pagination.py`) — not a pattern invented by this story. Practical impact is low: `program_releases` rows are release events (naturally low-cardinality per program per range), so a large offset costs at most a bounded index scan/skip over that program's release rows, not an unbounded table scan (confirmed compound index `ix_program_releases_program_id_date` is used per the perf test `EXPLAIN ANALYZE` assertions). Not a practical DoS vector at current data shape, but same caveat as the shared dependency — no cap exists if `program_releases` volume ever grows unboundedly per program.
- Fix: none required now; if `MAX_OFFSET_LIMIT`-style capping is ever extended to `offset` project-wide, apply it here symmetrically (do not fix unilaterally in this PR — cross-cutting change).

### F-004 — `ValueError` on unmapped release `type` propagates to generic 500 (verified safe, recorded as a Low observation)

- Source: checklist/logs
- Severity: Low
- File: `services/api/app/services/program_releases.py:73-80`
- Detail: An unmapped `program_releases.type` raises `ValueError(f"... {release_type!r}")`. This *does* embed the raw value in the exception message/args, but verified the FastAPI catch-all handler (`app/core/errors.py:29-33`) never surfaces `str(exc)` to the client — it returns the fixed body `{"error": {"code": "internal_error", "message": "An unexpected error occurred"}}`. Confirmed the paired `logger.error("program_release_unmapped_type", extra={"program_id": ..., "release_id": ...})` call omits the raw `release_type` value entirely, as claimed — no PII/internal-data leak via structured logs. The raw value only ever reaches an in-process exception traceback (stdout/uncaught-exception path), not the structured JSON log line or the HTTP response. Recorded as Low rather than clear because a future refactor that logs `exc` directly (e.g. `logger.exception(...)`) would silently reintroduce the raw value into logs — worth a comment anchor, not a blocking fix today.
- Fix: none required; if the exception is ever logged via `logger.exception`/`logging.error(..., exc_info=True)` elsewhere upstream, redact `str(exc)` before logging.

### F-005 — Frontend proxy forwards unvalidated `offset`/`limit` numeric coercion

- Source: stack-pattern/nextjs
- Severity: Low
- File: `apps/web/src/app/api/proxy/program-detail/[program_id]/releases/route.ts:36-38`
- Detail: `Number(offsetParam)` / `Number(limitParam)` can produce `NaN` for a malformed query string (e.g. `?offset=abc`), which is then forwarded to `fetchProgramReleases` and ultimately to the FastAPI query string. FastAPI/Pydantic's own `Query(..., ge=0)` int coercion will reject a non-numeric value with a 422, and the proxy's generic `error` branch maps any non-2xx/404/401 response to a `502 upstream_error` — so no invalid state reaches the browser, no injection risk (values go into `URLSearchParams`-style template interpolation as component-appropriate strings, not into an HTML/script sink). Confirmed no header injection is possible since `range`/`offset`/`limit` are placed into a URL query string, not raw header values. Low-severity code-quality note rather than a security defect: the proxy could reject `NaN` earlier for a cleaner error, but this is not exploitable.
- Fix: none required for this gate; optional follow-up: validate `offsetParam`/`limitParam` as finite non-negative integers before forwarding, for a cleaner 400 instead of relying on the backend's 422→502 remap.
