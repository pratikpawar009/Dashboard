## Manual OWASP checklist + stack-pattern pass

Scoped to the risk surface OVW-01 introduces — a new cio-only aggregate GET endpoint returning org-wide counts, a Server-Component route that composes two server-side fetches, and four presentational React components. No writes, no schema change, no new env var, no new dependency.

### Input

- No untrusted input reaches the backend handler: the FastAPI route takes only `Depends(get_current_user)` + `Depends(get_db)` + `Depends(get_freshness_accessor)` — no path, query, body, or header parameter is read. Nothing to validate at the boundary that Pydantic/FastAPI hasn't already handled.
- No string-built SQL. The single rollup read uses SQLAlchemy `select(OrgSummaryRollup).where(OrgSummaryRollup.org_id == _ORG_ID)` with a module-level literal (`"org-1"`); `FreshnessAccessor.get_last_successful_run()` (BED-04) is an ORM read as well.
- Frontend components render every server-supplied field as a JSX text child (`{card.glyph}`, `{card.value}`, `{card.label}`, `{card.sub}`, `count`, `total`, subtitle) — React auto-escapes text children; no `dangerouslySetInnerHTML`, `innerHTML=`, `document.write` used anywhere in the diff. Verified per file.
- The one place a server-supplied value crosses into a `style` prop (`AdoptionIndicator.tsx:169-181`, bar-segment `width: \`${adoption_percent}%\``) reads a `number` that Pydantic has already validated as `float | None`; React sets it via `element.style.width`, which is a CSS property assignment, not a JS eval sink. Not a script-injection vector even under a compromised backend.

### Authentication and authorization

- Every protected endpoint enforces authn AND authz. `get_org_summary` calls `Depends(get_current_user)` and then, unconditionally before any read, `await org_access(current_user)` — cio-only per AC-3, denying every other persona with `HTTPException(403)` and no data body. Two independent tests pin this: `test_overview.py`'s TC-05 covers all 4 non-CIO personas + the `rbac_check_org_access` audit-log emission (AC-8), and the runtime-fastapi evidence log confirms `GET /api/overview/summary` returns 401 unauthenticated with the route present in `/openapi.json`.
- Cross-program view surface (per the assignment): there is no per-program or per-tenant scoping to leak — `org_summary_rollup` is a singleton row (`org_id == "org-1"`, unique key), `system_metadata.key == "ingestion"` is a singleton row, and both are org-wide aggregates by design (DATA-DESIGN.md § 3). The RBAC check is the *entire* enforcement mechanism because there is no narrower scope to leak across; a non-CIO persona cannot reach the aggregate at all, and the response body is byte-identical for every CIO-authenticated caller.
- Tokens scoped, no session lifecycle change: OVW-01 introduces no new session/token surface. Both concurrent fetches go through `tokenStore.callWithAuth()` — the existing single-flight refresh + retry-once-on-401 primitive; the access token is attached server-side via `Authorization: Bearer ${accessToken}` in `overviewApi.ts::fetchOverviewSummary` and never crosses to the client (ADR-0008, confirmed in the docstring and enforced by `overviewApi.ts` being a server-only module).
- `SessionExpiredError` from either concurrent fetch redirects to `/login` from inside the `catch` block (`page.tsx:98`); `redirect()` throws `NEXT_REDIRECT`, so its placement inside `catch` (not `try`) is required to prevent the function's own catch from swallowing the redirect. Any other error re-throws — no error is silently mapped to a redirect.
- **AUTH-03 upstream caveat (research Condition 1, PLAN.md R-01, `pending_carry_forward.auth-03-security-review-open-caveat`).** `org_access()`'s implementation is complete and validated (`impl: complete`, `review: PASS`) but its own security review is `security: null`. OVW-01 accepts this per the plan; the route docstring documents it (`overview.py:296-299`) and it is carried into the PR body. Not a security defect *of this diff* — a later AUTH-03 finding is triaged against AUTH-03, not re-litigated here, and the `security-baseline`/`security-assessment` verdict rule does not flip on a carry-forward `risk` under the `standard` profile.
