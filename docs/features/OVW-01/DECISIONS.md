# OVW-01 — Decisions

Decision log for the org-summary-cards + adoption-indicator page. D-01/D-02 fill the
`overview-summary-api` glyph/label/value literals (direct mockup extraction, going one layer
deeper than DESIGN.md's decode — the embedded sample-data script — the same way ADR-0007 sourced
Program Detail's literals). D-03/D-04 settle the frontend composition seam. D-05/D-06 fill the
Adoption Level region's undocumented literal copy and colors. D-07 covers the undesigned error
states.

### D-01: ORG SUMMARY card glyph/label constants, sourced from the mockup's embedded sample-data script · blast:feature · rev:mechanical · adr:—

**Context**: `DESIGN.md` Region 1 documents that `k.glyph`/`k.label` exist and are bound per card,
but — unlike Program Detail's `ADR-0007` precedent, which quotes literal characters (`⬡ ✦ ⤴ ❯ ›_
</> ≡`) — it does not quote resolved glyph/label text for this region; the decoded markup only
shows the `{{ k.glyph }}`/`{{ k.label }}` bindings themselves. `OVW-01-FR-1` fixes field order and
value-formatting rules but leaves the literal presentation text unspecified, the same gap
`ADR-0007` filled for Program Detail.

**Decision**: Extracted directly from `dashboards/CIO Portfolio Dashboard.html`'s embedded
`<script type="text/x-dc">` sample-data block (`const orgKpis = [...]`, ~L717–723) — the same class
of script `ADR-0007`'s glyphs were sourced from. Five `(glyph, label)` pairs, mockup order:
`("▦", "Programs using AI SDLC")`, `("⬡", "Total token consumption")`,
`("</>", "Lines of code generated by Harness")`, `("⤴", "Releases using Harness")`,
`("❯", "Repos with Harness installed")`. Two glyphs (`</>`, `⤴`) match Program Detail's own icon
vocabulary for the same metric concepts, cross-confirming the extraction. Labels differ slightly
from `docs/test-cases/OVW-01.json`'s illustrative placeholders (e.g. "Programs using AI SDLC", not
"Programs using AI") — that file's own `generation_note` already disclaims those as non-authoritative;
these values supersede them. `docs/requirements/api.md#overview-summary-api` now carries this shape.

### D-02: Card 1's `value`/`sub` and card 5's `value` corrected in FR-1 to match the mockup's sample data — three discrepancies, all fixed before implementation · blast:feature · rev:mechanical · adr:—

**Context**: the mockup's embedded `<script type="text/x-dc">` sample-data block (the same one D-01
sourced the glyph/label literals from, and the same class of block `ADR-0007` used for Program
Detail) computes:

```js
{ glyph: '▦', label: 'Programs using AI SDLC', value: adoptingPrograms + ' / ' + totalPrograms,
  sub: Math.round((adoptingPrograms / totalPrograms) * 100) + '% adoption' },
{ glyph: '⬡', label: 'Total token consumption',            value: orgTotalTokens, sub: '' },
{ glyph: '</>', label: 'Lines of code generated by Harness', value: '366K',        sub: '' },
{ glyph: '⤴', label: 'Releases using Harness',              value: '128',          sub: '' },
{ glyph: '❯', label: 'Repos with Harness installed',        value: '54',           sub: '' },
```

The Product-Gate-approved `OVW-01-FR-1` disagreed with this in **three** respects, not two:

| # | Card | Mockup | FR-1 as approved |
|---|---|---|---|
| 1 | card 1 `value` | ratio `"7 / 10"` | `format_number(count)` → `"7"` |
| 2 | card 1 `sub` | `"70% adoption"` | `null` |
| 3 | **card 5 `value`** | plain `'54'` | ratio `"{count} / {total}"` |

The third is the one an earlier revision of this entry missed: **the ratio treatment was on the
wrong card.** FR-1 had put it on card 5 (repos) and `format_number()` on card 1; the mockup does the
reverse. `docs/test-cases/OVW-01.json` TC-01 encoded the same error
(`expected_repos_ratio_value = '18 / 25'`).

**Root cause**, recorded because it is instructive: the `sub` field was added to FR-1 during
`/arh-plan-requirements` Phase 2 by reading the mockup's **template bindings only**, and concluding
the mockup "says nothing about what any card's `sub` should contain". The bindings indeed say
nothing — the sample-data block does, and `ADR-0007`'s precedent already established that block as
where these literals live. One layer of extraction was done where two were needed.

**Decision**: **corrected, not carried forward.** `OVW-01-FR-1`, `docs/test-cases/OVW-01.json`
TC-01, and this plan now match the mockup on all three points. `CLAUDE.md` § Design system is
explicit that "the mockup, not the PRD prose, settles response shape", so a Product Gate approval of
a PRD containing a factual error *about the design contract* does not convert that error into a
requirement — and shipping it would have produced a page visibly differing from the design in three
places. Re-approved by Pratik Pawar 2026-09-10; see `REQUIREMENTS.md` § Approvals. The superseded
`pending_carry_forward` item `org-summary-card1-mockup-sample-mismatch` is removed, since there is
no longer a mismatch to revisit.

Consequential detail for implementation: card 1's `sub` is `null` when `programs_total == 0`
(`adoption_percent` is `None` per `OVW-01-FR-4`, so there is no percentage to render and the
`sc-if` omits the element) — consistent with FR-4's `0/0` flat-bar empty state.

### D-03: `AdoptionOverview` is a plain component with one server-side fetch; no `/api/proxy/*` route added · blast:feature · rev:mechanical · adr:—

**Context**: `ADR-0008`/AUTH-05 mandate a same-origin proxy for CLIENT-SIDE FastAPI calls; the
research pattern map cites `ProgramDetailView.tsx` (a `"use client"` orchestrator with a
switch-reload fetch) as the template. But `REQUIREMENTS.md`'s own Screen inventory pins both
regions as "server (initial load, no client refetch)" — there is no interactive re-fetch this story
needs, so `ADR-0008`'s proxy requirement (which governs client-side calls only) never fires.

**Decision**: `page.tsx` performs one server-side fetch via a new server-only `overviewApi.ts`
(mirrors `programDetailApi.ts`: hits FastAPI directly, attaches the bearer token, `callWithAuth`'s
retry-once), and hands the resolved `OverviewSummaryResult` to `AdoptionOverview` — a plain
component (no `"use client"`, no hooks), tested directly via Testing Library with a fixture prop,
matching `ProgramSummaryCards.tsx`'s (not `ProgramDetailView.tsx`'s) precedent. No
`/api/proxy/overview-summary` route is added; a future OVW story adds one only if it needs a
client-side refetch.

### D-04: `PersonaDashboardShell` reused for shared brand-bar chrome only — `program` widened to optional, `children` added, persona/program both omitted by this story · blast:service · rev:mechanical · adr:—

**Context**: `REQUIREMENTS.md`'s Solution sketch calls for wrapping the new client component "in
`PersonaDashboardShell`." Today that component (a) requires `program: ProgramContextData` with no
optional marker and has no `children` slot, and (b) `apps/web/src/lib/formatPersonaTag.ts`'s own
docstring states "the shell never composes the CIO dashboard" — the locked `SHP-01-TC-02` test in
`PersonaDashboardShell.test.tsx` proves a defined `persona="cio"` renders a "Persona unavailable"
neutral badge, which would be materially wrong, confusing UI on a real, successfully-authenticated
CIO's own overview page.

**Decision**: `AdoptionOverview` renders `<PersonaDashboardShell>{...}</PersonaDashboardShell>` with
`persona`/`program`/`signedInUser` all omitted (`undefined`) — this keeps the shell in its own
already-implemented `isLoading` branch (brand bar only; identity/header suppressed), never invoking
`PersonaHeader`/`formatPersonaTag('cio')`, so the "shell never composes the CIO dashboard" invariant
holds exactly and the locked `SHP-01-TC-02` behavior is unchanged (it always passes a defined
`program`). `PersonaDashboardShell` gets two additive changes: `program?: ProgramContextData`
(optional — a caller with no single-program concept, like this one, can omit it; the header
block's render guard becomes `!isLoading && program !== undefined`, so an undefined `program` never
reaches `ProgramContext`) and a new `children?: React.ReactNode`, rendered as the shell's last
element. Zero existing (future) consumers are affected — `ARC-01`/`DEV-01`/`PMD-01`/`EMD-01` all
pass a defined `program` and none pass `children` yet.

### D-05: Adoption headline/subtitle composed client-side from raw `count`/`total`/`adoption_percent`; zero-state text follows `OVW-01-FR-4` verbatim · blast:feature · rev:mechanical · adr:—

**Context**: Direct extraction of the mockup's embedded script shows "Adoption Level" is actually
TWO lines, not the single `"<count>/<total> — <adoption_percent>% of the org"` line
`OVW-01-AC-4`'s prose (and `OVW-01-TC-06`'s illustrative `expected_headline`) describe: a bold
headline computed as `` `${count} / ${total}` `` (spaced) and a separate subtitle,
`"programs using AI SDLC · {{ adoptionPct }} of the org"`. `DESIGN.md`'s Region 2 write-up captured
the two binding names (`adoptionHeadline`, `adoptionPct`) but not this literal second-line copy or
the populated-case spacing.

**Decision**: `AdoptionIndicator` composes both lines client-side from the raw wire fields
(extending `OVW-01-FR-2`'s "client derives presentation" pattern from bar/legend to text).
Populated: headline `` `${count} / ${total}` `` (spaced, matching the mockup script); subtitle
`` `programs using AI SDLC · ${Math.round(adoption_percent)}% of the org` ``. Zero/undesigned state
(`total === 0`, already-approved `OVW-01-FR-4`, not reopened): headline literal `"0/0"` (no
spaces, per FR-4's exact text); subtitle `"programs using AI SDLC"` with the percent clause omitted
entirely — satisfies `OVW-01-TC-07`'s "no percent suffix" assertion without a divide-by-zero or
`null%` render.

### D-06: Adoption bar/legend colors — `#2a6fdb` (adopted, existing token) / `#c3c9d2` legend + `#dfe3e9` bar segment (new); zero-state bar is one flat `#dfe3e9` segment · blast:feature · rev:mechanical · adr:—

**Context**: `OVW-01-FR-2` already decided the wire ships no color/style field; the client must
supply the palette. `docs/design/tokens.md`'s existing ramp doesn't include the mockup's actual
"not-yet-adopted" legend swatch (`#c3c9d2`) or bar-segment background (`#dfe3e9`) — both extracted
directly from the same embedded script (`adoptionLegend`/`adoptionBarNot`, ~L761–766).

**Decision**: `AdoptionIndicator` uses `#2a6fdb` (already `tokens.md`'s Primary/brand) for the
"Using AI SDLC" segment/legend swatch, and the two newly-extracted values — `#c3c9d2` (legend),
`#dfe3e9` (bar background) — for "Not yet adopted." Both new hex values are added to `tokens.md`'s
Color table in the same task that builds the component (T-11), matching `SHP-01` D-04's precedent
of extracting new per-mockup colors into `tokens.md` inline with the consuming component's task,
not as a standalone docs task. The zero-state bar (`OVW-01-FR-4`) renders as one flat segment in
`#dfe3e9` (the neutral/not-yet-adopted color, not the brand blue) — `OVW-01-TC-07` requires only
"no adopted/not-adopted split," not a specific color, and the neutral choice best matches "zero
programs have adopted anything."

### D-07: One generic `OverviewErrorPanel` for 403 / unauthorized-survives-retry / 500 alike — no per-status copy · blast:feature · rev:mechanical · adr:—

**Context**: `DESIGN.md` states the mockup shows no error region for any path (`OVW-01-AC-3`'s 403
is the only one the Screen inventory names). `ProgramDetailView`'s own D-10 precedent establishes
that an `{status:"unauthorized"}` result surviving `callWithAuth`'s retry-once falls through to the
page's own error panel rather than forcing a redirect — the same applies here, so `AdoptionOverview`
must render some panel for `forbidden`/`unauthorized`/`error` alike, not only the named 403 case.

**Decision**: One `OverviewErrorPanel` component, reusing the card-recipe tokens
`ProgramDetailErrorPanel` already established (`docs/design/tokens.md` § Card recipe), with the
single message "You don't have access to this view." for all three non-ok statuses — mirrors
`PGD-01` D-03's minimalism (one panel, one message, no per-status text, no new screen invented).
