### Authentication and authorization (A01: Broken Access Control, A07: Auth Failures)

- **Authn on the new endpoint** — `services/api/app/api/overview.py:104` binds `current_user: CurrentUser = Depends(get_current_user)`; unauthenticated requests are rejected before any DB read. Confirmed by TC-01's runtime evidence (`docs/features/PGD-01/state.json` `impl_evidence.runtime`: "401 with no bearer"). ✓
- **Authz scoping — accepted open-aggregate model** — see finding F-1 (Low) below. `program_visibility(current_user, program_id)` is called once with the real `program_id` but by contract (AUTH-03 D-03, `services/api/app/core/rbac.py:100–113`) it is a session-validity veto gate that never reads `current_user.programs` and never branches on `program_id`. ## Findings

### Low

#### F-1 — Broken Access Control (open-aggregate): any authenticated user can fetch any `program_id`'s detail

- Source: `checklist/auth` (OWASP A01), `stack-pattern/fastapi`
- Severity: **Low** (see rationale below)
- File: `services/api/app/api/overview.py:100–142` (invocation) + `services/api/app/core/rbac.py:100–113` (contract)
- Issue: `program_visibility(current_user, program_id)` is called with the real path parameter, but is by contract an open-aggregate veto gate — it deliberately never reads `current_user.programs` and never branches on `program_id`. The endpoint therefore returns any program's `header` + 7 summary cards to any authenticated persona, regardless of program membership. This is an IDOR-shaped surface by construction.
- Why Low, not High:
  - Response body contains **no PII and no sensitive data** — `header.{icon,name,type,description}` is program metadata and the 7 cards are aggregate integer counts formatted via `format_number()` (DATA-DESIGN.md § 4).
  - Authentication is enforced (bearer JWT required, 401 without one — runtime-evidenced in `state.json`).
  - The model is not an oversight: `docs/features/PGD-01/DATA-DESIGN.md § 3` and `DECISIONS.md` inherit `program_visibility`'s open-aggregate contract (AUTH-03 D-03) verbatim, with research Clarification C-3 explicitly ruling per-resource membership scoping out of scope for this endpoint. Product Gate 2026-09-03 accepted this posture on a `PASS` review. R-003 was recorded as "owned by `/arh-security-review`" — this record closes that routing.
- Fix / posture: no code change required for merge. Blocking condition would be a future story adding PII or member-identifying data to `ProgramDetailResponse` — at that point this finding must be re-evaluated against `security-baseline.md`'s "every protected endpoint enforces authn AND authz" invariant and per-program scoping added. Add an ADR when that boundary changes.
- Override: n/a (no `// SECURITY-OK` present; this is a product-gate acceptance, not an in-code suppression).

#### F-2 — No rate limiting on `GET /api/overview/program-detail/{program_id}`

- Source: `checklist/input` (A04: Insecure Design — abuse-case), `stack-pattern/fastapi`
- Severity: **Low**
- File: `services/api/app/api/overview.py` (endpoint), `services/api/app/main.py` (middleware chain)
- Issue: the endpoint (and every other `services/api/app/api/*` route in the tree) has no request-rate cap. An authenticated user can enumerate `program_id`s cheaply (single-row point-lookup per call, `impl_evidence` records the query budget as 1 SELECT/req). Coupled with F-1's open-aggregate model, a session token is enough to walk every program's aggregate metrics.
- Why Low: this is a repo-wide infrastructure gap, not something PGD-01 introduced or is uniquely responsible for. No other endpoint on the codebase has rate limiting today either, and the wider platform posture (`docs/adr/0002-system-architecture.md`) has no cache/queue/rate-limit layer defined yet.
- Fix / posture: track as carry-forward for an infrastructure story that adds a global rate-limit middleware (`slowapi`-style, per-authenticated-user quota) — not a PGD-01 fix.
