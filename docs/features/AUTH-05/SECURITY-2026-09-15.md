## Manual OWASP checklist + stack-pattern walk

Focused on the OIDC login flow, token lifecycle, and proxy surface introduced by AUTH-05.

### Authentication and authorization

- **State parameter + PKCE**: OAuth `state` and PKCE `code_verifier` live in FastAPI's
  in-memory `state_store.py` (DECISIONS.md D-13/D-14, REQUIREMENTS.md Constraints). AUTH-05's
  `/callback/route.ts` forwards only the allow-listed `code`, `state`, `error` query params
  verbatim to FastAPI, which validates state (single-use, expiry, unknown-state → 400).
  Frontend never trusts or introspects `state`. Contract correctly delegated to AUTH-01.
- **Authorization code flow**: Only `code` + `state` + optional `error` forwarded. No
  `id_token` echoed back to the browser. FastAPI performs the code-for-token exchange
  server-side; frontend only ever sees the resulting `{access_token, refresh_token,
  expires_in}` JSON, which never leaves the Node process except as the httpOnly cookie.
- **redirect_uri validation**: `/callback/route.ts` redirects only to fixed constants — `/`
  on success, `/login` on any error (D-04). `/login/route.ts` redirects the browser using
  the `Location` header returned by FastAPI's `/auth/login`, which is Keycloak's authorize
  URL derived from server-side config (`OIDC_ISSUER`, `OIDC_REDIRECT_URI`) — not a
  user-controlled value. No open-redirect surface. `redirect: "manual"` is set on the login
  fetch so `fetch` cannot follow the 302 server-side.
- **Session fixation**: `writeSession()` overwrites the `dashboard_session` cookie on every
  successful callback (`cookies().set(SESSION_COOKIE_NAME, …)`). No pre-auth session id is
  preserved across authentication. Fresh cookie per sign-in.
- **Replay**: OAuth `code` and `state` are one-shot at FastAPI. Refresh single-flight guard
  (`refreshPromise`) collapses concurrent refresh calls to one `POST /auth/refresh` per
  Node process; per-process caveat is accepted (D-07, mirrors `OAuthStateStore`'s own
  documented caveat). Multi-process races cost at most one extra harmless refresh, never a
  torn token — the cookie write is the serialization point.
- **CSRF**: The only state-changing surface AUTH-05 introduces is `GET /callback`, protected
  by the OAuth `state` parameter (OWASP's canonical CSRF defence for OAuth callbacks). The
  four other new routes (`/login`, `/api/proxy/programs`, `/api/proxy/program-detail/[id]`)
  are read-only GETs — CSRF exempt per the baseline.
- **Ownership / authorization**: FastAPI enforces `rbac.program_visibility` on the underlying
  `/api/overview/program-detail/{id}` endpoint (AUTH-03). The proxy Route Handler forwards
  the authenticated bearer token but adds no bypass path — a 401 from FastAPI surfaces as
  `401 {error: "session_expired"}`, never as unauthenticated data. `X-Program-Switch-From`
  is forwarded verbatim server-to-server; CORS never applies (D-11).

### Token storage + refresh

- **Cookie flags**: `httpOnly: true`, `sameSite: "lax"`, `secure: process.env.NODE_ENV === "production"`,
  `path: "/"`, no `maxAge` (session-scoped) — matches REQUIREMENTS.md FR-4 verbatim and the
  security-baseline session-cookie rule. `Lax` is correct here: the cookie is set from the
  `/callback` GET (same-origin redirect target), and only sent on same-origin requests to
  the frontend's own routes. `Strict` would gratuitously drop the cookie on the very first
  top-level navigation after Keycloak returns the browser to `/callback`.
- **Client-JS reachability**: verified by three independent mechanisms:
  1. Static — `ProgramDetailView.tsx` and `programDetailApi.client.ts` import neither
     `tokenStore` nor `next/headers` (confirmed by REVIEW.md and re-verified by grep of the
     shipped source).
  2. Structural test — `ProgramDetailView.authFlow.test.tsx` greps the on-disk client
     module for token-shaped identifiers.
  3. Runtime negative-assertion test — serializes every client-side `fetch` mock call arg
     and asserts no `Authorization`, `accessToken`, or JWT-shaped substring appears.
  Token never enters a JS-reachable scope in a browser. ADR-0008 rationale enforced at
  compile time (`D-08` module split), not merely documented.
- **Refresh failure**: `doRefresh()` catches any non-2xx response, timeout, or throw,
  clears the cookie, and throws `SessionExpiredError`. FastAPI's status text and body are
  never surfaced to the browser (`FR-5`, `AC-8`). Route Handlers translate the error to
  `401 {error: "session_expired"}` (proxy) or a redirect to `/login` (callback/page).
- **Timeouts**: every outbound fetch (`/login` relay, `/callback` relay, `/auth/refresh`,
  both proxy routes' upstream calls) carries an explicit `AbortSignal.timeout(5000)` —
  matches `.claude/rules/performance-baseline.md`.

### Input / data / crypto / logs

- **Input at trust boundary**: `/callback` allow-lists `code`/`state`/`error` — no
  attacker-controllable header or cookie is echoed into an upstream URL. Proxy routes take
  their `program_id` from Next.js's typed dynamic segment; `X-Program-Switch-From` is
  passed as an opaque request header, not interpolated into a URL or SQL.
- **Data / PII**: no PII stored client-side — only opaque `{accessToken, refreshToken,
  expiresAt}` inside the httpOnly cookie. No PII in the proxy response bodies.
- **Crypto**: no homegrown crypto. Cookie integrity relies on transport (HTTPS in prod) +
  `HttpOnly` server ownership. The story does not introduce any hashing/encryption of its
  own.
- **Logs**: `tokenStore.ts`, `/login`, `/callback`, and both proxy routes emit no log
  output whatsoever (module docstrings state this deliberately; verified — no `console.*`
  hit in production files). NFR-security "no token in logs" invariant enforced end-to-end
  by `tokenStore.security.test.ts`, which spies all six `console` methods across every
  failure branch.
- **Error surface**: `/login` returns a generic 502 `"Sign-in is unavailable."` plain-text
  for any upstream failure. Proxy routes return `{error: "session_expired"}` (401) or
  `{error: "upstream_error"}` (502). No stack traces, no upstream body forwarded.

### Stack-pattern (Next.js 15 App Router)

- Route Handlers use `NextResponse` correctly; no `unsafe-inline` CSP or
  `dangerouslySetInnerHTML` introduced.
- `next/headers` `cookies()` correctly awaited (Next 15 async cookies API).
- `page.tsx` places `redirect("/login")` inside the `catch`, deliberately outside the `try`
  to let `NEXT_REDIRECT` propagate — noted correctly in the source docstring.
- No secrets referenced in a `"use client"` component.
