## Manual OWASP checklist + stack-pattern pass

### Input / trust boundary

### Fail-closed contract (item 1) — **verified, no defect**

Traced every path in `_resolve_uncached`/`resolve`/`_resolve_tier3`:
- All three tiers miss → `raise PersonaNotFoundError(role)` (`persona_resolver.py:181`) — never a default persona.
- Tier-3 timeout → `wait_for` raises `TimeoutError` → wrapped as `PersonaResolutionError`, a **different** exception class from `PersonaNotFoundError`, so a DB outage cannot present as "no persona for this role" (item 7's ask). `rbac.py`'s docstring confirms downstream catches the two in separate `except` clauses, `PersonaNotFoundError` first (it subclasses `PersonaResolutionError`), both denying 403 — zero default-permit paths.
- Malformed/missing Tier-2 YAML → raises uncaught inside `PersonaResolver.__init__`, called synchronously and unguarded in `create_app()` (no lifespan try/except, D-07) → `app = create_app()` fails at import time → Uvicorn exits non-zero. The extreme case of fail-closed: the service never starts serving requests rather than serving one with a wrong persona.
- Only a **successful** resolution is cached (`resolve()` assigns to `self._cache` only after a non-raising `_resolve_uncached`); a raise is never cached, so a transient Tier-3 failure cannot poison the cache into steady-state authorization bypass or steady-state denial-of-service beyond the failure's own duration.
- Test evidence: `test_all_tiers_empty_raises_persona_not_found_error_tc04`, `test_tier3_query_timeout_raises_persona_resolution_error_tc11` (`tests/unit/test_persona_resolver.py:364,524`) exercise both raise paths directly.

**Verdict: fail-closed contract holds on every path checked, including the three named in the brief.**

## Escalation-path assessment (items 2 and 4)

**Item 2 — Tier-1 fail-open parse behaviour: not abusable for escalation.** Traced `Settings._parse_persona_role_map` (`app/core/config.py:108-141`): any parse failure — invalid JSON, non-dict JSON, or a dict with a non-string value — returns `None` unconditionally. `None` Tier-1 is then treated as **empty** by the resolver (`if tier1_map and role in tier1_map`), which falls through to Tier-2 then Tier-3 — the *more* authoritative layers, including the system-of-record. A malformed `PERSONA_ROLE_MAP` cannot fabricate a mapping, cannot partially match, and cannot shadow a restrictive Tier-3 row with anything other than "nothing" (i.e., deferring to that same Tier-3 row). There is no parse-error code path that produces a persona value at all. **No escalation vector.**

## Addendum — CVE-2024-37568 empirically tested (out of AUTH-02 scope, cross-cutting)

Recorded by the `/arh-security-review` orchestrator, not the assessing agent. Out of AUTH-02's
`file_plan`; included because this dependency finding has now been raised and deferred twice
(`docs/features/ING-01/SECURITY-20260903-0724.md` §§ 31-34, 97, and referenced again in this run's
dependency scan) with **no owner and no empirical test**, and the deferral rationale was inaccurate.

### What the prior reports claimed

ING-01's report states that `authlib==0.15.6` carries `CVE-2024-37568` (JWT algorithm confusion:
HMAC verification accepted against an asymmetric public key when `algorithms` is not pinned), and
that `app/core/auth.py:217` and `app/auth/oidc.py:191` both call `jwt.decode(token, signing_key, ...)`
without an `algorithms=` allow-list — "the vulnerable call shape". Neither report tested it.

### What is actually true

**The attack does not work against this codebase's call shape.** `JwksCache.get_signing_key` is typed
`-> dict[str, Any]` (`app/auth/jwks.py:130`) and returns a **JWK dict** carrying `kty: "RSA"`, not a PEM
string and not raw key bytes. Tested directly against real `authlib` 0.15.6 by minting an HS256 token
whose HMAC secret is the public modulus (`n`) — public knowledge, served at the JWKS endpoint — and
decoding it with no `algorithms=`:

| Key form passed to `jwt.decode` | Result |
|---|---|
| JWK dict with `kty: "RSA"` — **the real call shape** | **rejected**: `ValueError: Missing required field: "k"` |
| raw modulus string — the classic exploit shape | **ACCEPTED**, `sub='attacker'` |

authlib resolves HS256 to an `oct` key type; the RSA JWK dict has no `k` member, so the import fails
before any signature comparison. The `kty` member is doing the work an explicit `algorithms=` would do.

### Why it is still worth fixing

This is **protection by accident, not by construction** — nothing in the code, tests, or docs states
that safety depends on `get_signing_key`'s return type. Changing it to return a PEM string or raw key
bytes is an ordinary-looking refactor (`get_dev_signing_key() -> Key`, `app/auth/jwks.py:92`, already
returns a different type), and it would make the CVE live with **no test detecting it**. The fix is
one argument at each of two call sites:

```python
claims = jwt.decode(token, signing_key, algorithms=["RS256"], claims_options=_claims_options(kid, settings))
```

`_claims_options` (`app/core/auth.py:121`) constrains `iss`/`aud` but not `alg`, so it provides no
cover here.

### Corrected severity and ownership

- **Not** an authentication bypass on current `main` — the two prior reports' implied severity was too
  high, and this addendum supersedes their characterisation of the call sites as vulnerable.
- Still a genuine **defense-in-depth gap** plus an unpatched dependency (`authlib>=0.15,<1.0`,
  `services/api/pyproject.toml:26`; CVE fixed in `1.3.1`+). `starlette==0.46.2` carries 9 further
  advisories, likewise unowned.
- **Owner: AUTH-01 / AUTH-04**, whose files these are. Not AUTH-02's and not ING-01's — which is
  precisely why it has survived two reviews unactioned. It needs its own dependency-upgrade story,
  not a third carry-forward entry.
