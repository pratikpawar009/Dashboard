### Failed (bug blocks)

### Contract-conformance — `persona-resolver` contract: missing `tier3_latency_ms` field  (Priority: Must)

- **Contract**: `docs/requirements/auth.md` § `persona-resolver` (`produced_by: AUTH-02`), `shape.observability`:
  > "every `resolve()` call (cache hit or miss) emits `logger.info('persona_mapping_loaded', extra={role, persona, tier, timestamp})` ... **a tier-3 hit additionally carries `tier3_latency_ms`**."
- **Recorded elsewhere, same requirement**:
  - `docs/features/AUTH-02/REQUIREMENTS.md` § C-4 ("Latency baseline & monitoring setup") mitigation: *"add log field `tier3_latency_ms` to `persona_mapping_loaded` event when tier=3. Post-launch monitoring: alert if `tier3_latency_ms` p95 > 200ms."*
  - `docs/features/AUTH-02/REQUIREMENTS.md` § Performance (cache miss): *"Post-launch monitoring: alert if `tier3_latency_ms` field in `persona_mapping_loaded` events exceeds 200ms p95."*
  - `docs/features/AUTH-02/tasks.json` T-05 notes: *"persona_mapping_loaded log event per resolution incl. tier3_latency_ms on Tier-3 hits ..."*
- **Shipped**: `services/api/app/core/persona_resolver.py::_log_resolution` emits exactly `{role, persona, tier, timestamp}` on every call, cache hit or miss, tier-1/2/3 alike — no `tier3_latency_ms` field on any code path. `_resolve_tier3` does not measure or pass through a latency value at all.
- **Corroboration this is not a stray doc typo**: `services/api/README.md`'s own "Reading the logs" section (added by T-10, same feature) independently documents the field set as *"exactly `{role, persona, tier, timestamp}`"* — the implementation and its own ops docs agree with each other, both diverging from the upstream contract/REQUIREMENTS/task-notes spec. `AUTH-02-TC-15`'s `test_data.allowed_fields` allowlist also omits `tier3_latency_ms`, so the existing regression suite cannot catch this gap either.
- **`grep -rn "tier3_latency_ms" app/ tests/`**: zero matches anywhere in `services/api/`.
- **Impact**: the REQUIREMENTS.md-specified post-launch alert ("alert if `tier3_latency_ms` p95 > 200ms") has no field to key on — Tier-3 latency degradation is currently unobservable via logs, undermining the C-4 mitigation this field exists to satisfy.
- **Likely cause**: `_resolve_tier3`/`_log_resolution` were implemented without wiring a latency measurement around the Tier-3 query and threading it into the `tier == "tier-3-postgres"` log call.
- **Fix is one of** (per `validation-execution` contract-conformance rule): (a) add the `tier3_latency_ms` measurement + field to `_log_resolution` for tier-3 hits, matching the contract/REQUIREMENTS spec, and extend `AUTH-02-TC-15`'s allowlist/add a TC asserting its presence on a tier-3 hit (regression-tag per the fix-loop protocol); or (b) if the field is deliberately being deferred, update `docs/requirements/auth.md`'s `persona-resolver` shape and `REQUIREMENTS.md` § C-4/Performance to drop the promise, and record the decision in `docs/features/AUTH-02/DECISIONS.md`. Do not silently drop the contract text without a decision entry.
