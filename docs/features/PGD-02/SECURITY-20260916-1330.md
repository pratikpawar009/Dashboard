## Medium findings

### F-001 — `program_id` path param not URL-encoded before proxying (`apps/web/src/lib/programTokenTrendApi.ts:49`, `apps/web/src/lib/programTokenTrendApi.client.ts:46`)

- Source: checklist/input
- Category: input
- `program_id` (Next.js dynamic route segment `[program_id]`) is interpolated directly into a
  template-literal fetch URL with no `encodeURIComponent()`, both in the server module hitting
  FastAPI directly and in the client module hitting the same-origin proxy.
- Risk is low in practice: Next's router already URL-decodes a single path segment before handing
  it to the handler, and the FastAPI side treats `program_id` as an opaque bind parameter in a
  parameterized `WHERE` clause (no SQL injection). A value containing `?`/`#`/`&` could still alter
  the constructed request's query string (e.g. append a bogus extra query param, or truncate the
  path at a literal `#`), which is a request-smuggling/parameter-pollution smell rather than an
  exploitable vuln today, since the backend range validation and program_visibility gate still run
  against whatever `program_id` actually arrives.
- Not introduced by PGD-02 as a new pattern — `apps/web/src/lib/programDetailApi.ts:56` (pre-existing
  PGD-01 sibling) has the identical unencoded interpolation. PGD-02 replicates an existing codebase
  pattern (`.claude/rules/pattern-consistency.md` — new code in a file with no local precedent should
  follow the dominant existing pattern, which this does).
- Fix: wrap `programId`/`program_id` in `encodeURIComponent()` at both call sites, ideally alongside
  the sibling `programDetailApi.ts`/`.client.ts` so the fix is consistent across both endpoints
  rather than PGD-02-local.
- Recommendation: track as backlog item against the shared `program-detail` fetch modules rather than
  fixing PGD-02 in isolation (`.claude/rules/surgical-changes.md`).
