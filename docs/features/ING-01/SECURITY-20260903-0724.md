**M-01 — No compensating detection control for unscoped/non-expiring ingest tokens (Medium, accepted-with-ADR, non-blocking)**

- Source: `checklist/auth`
- Severity: Medium (my independent assessment; ADR-0006 records the gap but doesn't score it)
- Files: `app/core/ingest_auth.py`, `scripts/mint_ingest_token.py` (no code defect — this is an absence)
- Issue: the most-permissive credential the system can issue (every program, forever) is also the default produced by omitting a mint flag, and nothing lists, ages, or flags such tokens once minted (ADR-0006 § Flagged gaps).
- My judgment (requested explicitly): **I do not elevate this to blocking.** Reasons: (a) minting requires prior possession of `DATABASE_URL` credentials + local shell — an operator who already has that can bypass the CLI entirely via a direct `INSERT`, so the CLI's default doesn't itself expand the attacker's reachable surface; (b) containment exists today via `revoked_at`, even though detection doesn't; (c) this is a fully-informed, signed-off ADR decision, not an oversight the gate exists to catch. It stays Medium because the blast radius (unbounded scope, unbounded time, silent) is genuinely large if a token *does* leak downstream (e.g. pasted into a log aggregator, committed accidentally by an ingester script) and there is zero automated way today to notice.
- Fix: prioritize ADR-0006 § Flagged gaps' "candidate follow-up story" — a token-inventory report (age, scope-breadth, last-used) — ahead of the next story that mints tokens in a shared/team environment. Not a blocker for ING-01 itself.

## Independent-judgement findings (Low)

**L-01 — Mint script's `user_email` is self-reported, not an authenticated actor identity (Low, advisory)**

- Source: `stack-pattern/fastapi` (CLI trust-boundary variant)
- File: `services/api/scripts/mint_ingest_token.py:52-53,112`
- Issue: `--user-email` records who the token is *for*, not who *ran* the mint command — anyone with `DATABASE_URL` access can attribute a mint to an arbitrary email. ADR-0006 §2 already accepts "no audit trail... beyond the `user_email` column" as a known limitation; this finding is narrower: the column that exists isn't even a reliable audit signal, since it's free-text CLI input.
- My judgment: defensible for v1 given the same operators already hold DB write access (so this doesn't gate anything a determined operator couldn't route around), but cheap to improve.
- Fix (non-blocking, low effort): capture the actual OS/shell identity (e.g. `getpass.getuser()` or an env var the ops runbook sets) into a second column, or note in `label`, so `user_email` and "who minted it" become distinguishable once the token-inventory follow-up (M-01) lands.

**L-02 — `token_hash` unique-index lookup: theoretical timing side channel, not material (Low, informational, no fix required)**

- Source: `checklist/crypto`
- File: `app/core/ingest_auth.py:71-73` (`SELECT ... WHERE token_hash = :hash`)
- Analysis: unlike a password/HMAC compare on a low-entropy secret, `token_hash` is `SHA-256(secrets.token_hex(32))` — the compared value is a hash of a 256-bit CSPRNG value. Any index-scan or memcmp early-exit timing variance leaks information only about *hash-digest* prefixes, and an attacker cannot turn that into a reduced-cost brute force of the pre-image (the raw bearer token) because SHA-256 destroys any correlation between raw-token content and digest content — guessing digest bytes doesn't help guess token bytes. Combined with FastAPI/Postgres/network jitter, this is not a practically exploitable channel. No `hmac.compare_digest`-style constant-time lookup is warranted here (that mitigation matters for direct secret comparison, not indexed-hash-of-CSPRNG-value lookups).

**L-03 — Forward risk: `get_ingest_token()` returns the raw `IngestToken` ORM row as principal; a future route must not serialize it directly (Low, advisory for ING-02)**

- Source: `stack-pattern/fastapi`
- File: `app/core/ingest_auth.py:45-49,91` (D-01: "no separate DTO... the model already carries every field a caller needs")
- Issue: `IngestToken` includes `token_hash`. ING-01 itself wires no HTTP route that returns this object (confirmed: no route in this diff imports `get_ingest_token`; `app/main.py` router list unchanged), so there is no live leak today. But per `fastapi-patterns` idiom ("`response_model` strips sensitive fields"), any of the seven downstream stories (ING-02 first) that returns this row on a response path must declare an explicit `response_model`/schema that omits `token_hash`, not rely on FastAPI's default `IngestToken`-shaped serialization.
- Fix: no ING-01 code change; flag for ING-02's implementation/review to define a response schema explicitly.
