### 2. Authentication / authorization — improved by this diff

`get_current_user` (`services/api/app/core/auth.py:236-263`) now discriminates the roster-skip branch **exclusively** on `kid == DEV_BYPASS_KID`. The two rejected alternatives — presence of a `programs` claim, and `payload.email` — are called out inline as security regressions, not refactor candidates (FR-3 durable-regression guard). Concretely:

- A Keycloak-issued token forging `programs: [...]` on a non-dev `kid` is now silently overridden — `programs` on the returned `CurrentUser` is the roster result, not the claim. Enforceable via AUTH-06-TC-02, which signs exactly such a token.
- `DEV_BYPASS_KID` resolves to a signing key only when `settings.dev_bypass_enabled` is True (`services/api/app/auth/dev_bypass.py:33-49` D-01 fail-closed allow-list) — the same gate that keeps the `/auth/dev-bypass` router unregistered in production. So the roster-skip is reachable only in environments where dev-bypass is itself reachable.
- JWT verification path is unchanged: `jwt.decode(..., claims_options=_claims_options(kid, settings))` runs signature check + `claims.validate()` (`services/api/app/core/auth.py:266-273`), which enforces `exp`/`nbf`/`iat`/`iss`/`aud` — the missing-`.validate()` regression risk (REVIEW round-1 F-1 in AUTH-05) does not apply.

Net auth posture: **strictly stronger than main pre-AUTH-06.** The old `_parse_programs(groups, prefix)` path admitted any string in the `groups` claim matching the prefix — a Keycloak realm admin (or an IdP token forgery on a compromised realm key) could self-assign program membership. That surface is deleted.

## Low findings

### F-001 — Per-worker `ProgramRosterResolver` cache is unbounded (TTL-only eviction)

- Source: checklist/data
- Severity: Low
- File: `services/api/app/core/program_roster_resolver.py:83-88`
- Issue: `self._cache: dict[str, tuple[list[str], float]]` grows on every distinct authenticated `email` and evicts entries lazily only on the next lookup for the same key past its TTL. There is no size cap, no LRU, no periodic sweep. An adversary able to authenticate with many distinct valid tokens (or a legitimate long-lived worker serving many rare users) grows the process's resident set without bound within a 300 s window.
- Reachability: to inflate the cache an attacker must present tokens that pass full JWT signature + `iss`/`aud`/`exp` validation. In production, that means possessing valid Keycloak-issued access tokens for many distinct emails — a high bar. In dev-bypass environments, dev-bypass tokens can carry any `email`, but those environments are already allow-listed away from production.
- Precedent: `PersonaResolver` (`services/api/app/core/persona_resolver.py:83-88`) uses the same unbounded shape; the resolver docstring names PersonaResolver as its precedent (D-04) and inherits the trade-off deliberately. AUTH-06 does not diverge; it extends the pattern.
- Fix: track as backlog rather than in this feature — introduce a shared bounded/LRU cache primitive that `PersonaResolver`, `ProgramRosterResolver`, and future in-process caches all adopt. Not blocking this PR.
- Rule: `.claude/rules/performance-baseline.md` § "Cache invalidation is explicit. Document TTL and the invalidating event." — TTL is documented; the size bound is not.
