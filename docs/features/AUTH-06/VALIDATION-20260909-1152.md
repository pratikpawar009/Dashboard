## Focus item 1 — can a default regression still slip past the suite?

**No. CF-1 can be closed.**

### Method, and the fidelity trap in it

The experiment must simulate *a source edit to `config.py`*, and the pin now derives from the shipped default at **conftest import time**. That makes hook timing load-bearing: `pytest_configure` fires **after** initial conftests load, so patching there would leave the derived pin holding the *original* value while the "shipped default" reads as regressed — a state a real source edit can never produce, and one that would manufacture a false "the suite misses it" result. The probe therefore patches at plugin **module import** time (`-p` plugins import before initial conftest loading) and then asserts the pin actually tracked the patch. Every run below reports `FIDELITY: pin tracks default = True`; without that line the numbers would be meaningless.

Read-only throughout: the plugin lives in the scratchpad on `PYTHONPATH`, never in `testpaths`. `config.py` was not written to at any point (verified — see Proof of run).

## Focus item 2 — hermeticity: did the derived pin trade isolation for documentation?

**No. Hermeticity is preserved, exactly.** This was the finding that would have made the round a FAIL; it does not.

Precedence in pydantic-settings is `init kwarg > env > .env > field default`. The pin is still a constructor kwarg — only the *provenance of its value* changed, not its tier — so the prediction is "no change". Predictions of no-change are the easy thing to assert and not check, so it was measured on both leak channels, with the leak channels **proven live first**. Without that positive witness, "the pin wins" would pass just as happily if the `.env` mechanism were broken and nothing could leak at all.

Probe run from a scratchpad cwd with its own `.env` — the repo's real `services/api/.env` was never read (governance deny set) or touched.

| Check | Result |
|---|---|
| **witness:** `.env` DOES leak into an UNPINNED `Settings()` → `'DOTENV_LEAK'` | PASS — channel live |
| **witness:** env var DOES leak into an UNPINNED `Settings()` → `'ENV_LEAK'` | PASS — channel live |
| derived pin shadows `.env` | PASS → `'openid profile email'` |
| derived pin shadows env var | PASS → `'openid profile email'` |
| literal pin shadows `.env` *(control)* | PASS → `'LITCTL'` |
| literal pin shadows env var *(control)* | PASS → `'LITCTL'` |
| `model_fields[...].default` is itself immune to env/`.env` | PASS → `'openid profile email'` under both leaks |

That last row is the one genuinely *new* risk the derivation introduces, and the reason it was probed rather than reasoned about: if the derivation source could itself be moved by the environment, the pin would launder an env leak into a value that looks like a shipped default. It cannot — `model_fields[...].default` is the class-level field default and reads clean under both poisoned channels.

**In-situ confirmation**, through the real conftest rather than synthetic `Settings` calls:

```
OIDC_SCOPE="openid profile email groups ENVLEAK" uv run pytest tests/unit/test_auth_oidc_login.py -q
  -> 15 passed
```

The real wire test is unmoved by a poisoned ambient `OIDC_SCOPE`. The `oidc_redirect_uri` incident documented in that same conftest block — a real `.env` value silently breaking a derived-fallback assertion — remains defended against.

**Residual scope limit (unchanged, by design, not a defect):** because the pin shadows env and `.env`, the suite cannot witness a *deployment-config* regression (someone adding `groups` back via `OIDC_SCOPE` in a real `.env`). That is the intended purpose of the pin and was equally true of the literal. It is a different thing from the default regression CF-1 was about, and no new gap.

### Methodology note — a near-miss worth recording

The first execution of the focus-item-1 experiment passed both test paths as a single argv entry (zsh does not word-split unquoted parameter expansions the way bash does). pytest reported `ERROR: file or directory not found` on line 1 and `no tests ran in 0.00s` at the end — but the probe's own `pytest_collection_finish` hook still printed its `FIDELITY: pin tracks default = True` line, because collection *finished*, having collected nothing. Reading only the tail, the run looked like a clean "0 failures under a faithfully regressed default" — i.e. exactly the conclusion "the suite misses the regression", produced by a suite that never ran. Caught by requiring an explicit non-zero pass count rather than accepting the absence of failures. Same "green for the wrong reason" family this story has already produced twice (AF-11's shared test DB, the vacuous log-absence assertion behind CF-3).
