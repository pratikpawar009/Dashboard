### AF-04 — `conftest.py:663-664` pins the retired settings — **NOT an AC-6 coverage hole; carry-forward as test-fidelity drift**

The flag's factual claim is correct: `_HERMETIC_SETTINGS_DEFAULTS` still contains `"oidc_scope": "openid profile email groups"` and `"program_group_prefix": "program-"`. I ran it rather than reasoning about it:

```
Settings fields containing 'program' : []
oidc_scope SHIPPED default           : 'openid profile email'
model_config extra                   : ignore
Settings(oidc_scope="…groups", program_group_prefix="program-")
  -> NO ERROR (silently accepted)
  -> hasattr(s, "program_group_prefix") : False
  -> effective oidc_scope               : 'openid profile email groups'
```

Two separate consequences, and the flag conflates them:

1. **`program_group_prefix` is inert, not dangerous.** `model_config extra="ignore"` drops the kwarg outright; the attribute does not exist on the instance. It cannot resurrect the retired behaviour or mask its deletion. This is dead-reference rot with no runtime effect.
2. **`oidc_scope` genuinely takes effect** — every `build_app()`-based test boots with the retired scope string.

**AC-6 is nonetheless adequately verified,** because the canonical assertion does not go through `build_app()` at all. `test_auth_config.py::test_settings_default_field_list_matches_fr1` builds its own `_HermeticSettings` with **no** `oidc_scope` override and asserts `settings.oidc_scope == "openid profile email"` (line 95). That is a direct assertion against the shipped default, and it passes. AC-6's other three sub-assertions are structural deletions I verified by grep and runtime introspection above; no fixture can fake them.

What the flag *does* correctly expose is a fidelity problem worth carrying: `test_auth_oidc_login.py:81` asserts `query["scope"] == ["openid profile email groups"]` under the trailing comment `# settings.oidc_scope default`, and that comment is now **false** — the value only appears because conftest pins it. The assertion itself remains behaviourally valid (the route reflects whatever `settings.oidc_scope` holds, and the very next test proves that tracking explicitly), but no `build_app()` test exercises the actually-shipped scope string end-to-end, and anyone who later removes the conftest pin will see that assertion break for a reason unrelated to their change. **Recorded as CF-1. Does not block the gate.**
