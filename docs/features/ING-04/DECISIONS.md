# ING-04 — Decisions

Decision log for the MCP server exposing `push_activity` / `push_artifacts`. Header slugs (`blast:` / `rev:` / `adr:`) are machine-greppable per the `decide` skill. PLAN.md §1 is a one-line pointer to this file — decisions are not duplicated there.

### D-01: `services/mcp-server/` is a separately-deployed sibling service · blast:system · rev:medium · adr:ADR-0014

**Context**: `services/mcp-server/` is a headless local Python service exposing two MCP tools that POST into the already-shipped ingest API. Two topologies exist: (a) fold the package into `services/api/` (share pyproject, share preflight, one deploy pipeline), or (b) ship it as a sibling package with its own `pyproject.toml`, its own tests, its own deploy pipeline. (a) contaminates the FastAPI backend's dependency graph with `fastmcp` and a second entry point, and drags every MCP-tool test into the API's pytest run (slowing every backend PR). (b) is what the PRD § Constraints ("Deployment topology") and § Open questions → Resolved (D-01) already fix — the developer's laptop is the deploy target for the MCP server, and the FastAPI backend has no reason to know it exists at build time. This is a system-level topology decision because it fixes how a second deployable relates to the existing one, and it is what downstream ING-05 (Copilot-Chat bridge) will bind against as its host process.

**Decision**: Ship `services/mcp-server/` as a sibling package to `services/api/`. Own `pyproject.toml` (F-01), own `tests/` tree, own console script (`agentrise-mcp`), own module-entry (`python -m agentrise_mcp`). MUST NOT be wired into the main API's `docs/config/project-commands.yaml::preflight` (see D-07). The main API stays unaware of the MCP server; the MCP server is a plain HTTP consumer of the frozen `POST /api/ingest/{kind}` contract. Promoted to ADR-0014 because it changes the repository's service topology (`blast:system`) and downstream stories (ING-05 in particular) will describe their host runtime relative to this choice; the ADR captures the sibling-package layout, the no-wiring-to-main-preflight guarantee, and the reversibility posture.

### D-02: `fastmcp` (jlowin/fastmcp) v2.x is the MCP framework · blast:service · rev:mechanical · adr:—

**Context**: PRD § Constraints resolves C-01 to the standalone `fastmcp` PyPI package (`jlowin/fastmcp`, v2.x — https://pypi.org/project/fastmcp/). The two ruled-out options are `fastapi-mcp` (a FastAPI plugin — pulls FastAPI into the MCP-server dep graph, defeating D-01's sibling isolation) and Anthropic's low-level `mcp` SDK (no `@server.tool()` decorator, no streamable-HTTP transport out of the box — reinvents FastMCP's own surface). `fastmcp` provides both, matching AC-1 verbatim.

**Decision**: `services/mcp-server/pyproject.toml` (F-01) pins `fastmcp>=2,<3` under `[project].dependencies` (exact minor version chosen at implementation time from the current 2.x release; recorded in the PR body). `FastMCP("agentrise-mcp")` is the constructor; `@server.tool()` is the registration decorator; streamable HTTP transport is the invocation surface at `0.0.0.0:3010` path `/mcp`. No `fastapi-mcp`, no low-level `mcp` SDK. Not promoted to ADR — it is a library pick inside one service; swapping to a different MCP framework is a mechanical rewrite of `server.py` + tool wiring (`rev:mechanical`), no data migrated under the choice.

### D-03: Endpoint URLs match ADR-0013 verbatim: `/api/ingest/activity` + `/api/ingest/artifacts` · blast:feature · rev:mechanical · adr:ADR-0013

**Context**: The story text (AC-2 / AC-3) still references `POST /api/ingest/files` — pre-ADR-0013 wording. ADR-0013 retired that URL under the generic `POST /api/ingest/{kind}` router; the live routes are `/api/ingest/activity` (kind = "activity") and `/api/ingest/artifacts` (kind = "artifacts"). URL path `{kind}` and body-envelope `kind` MUST agree (mismatch → 400 `unknown envelope kind` BEFORE bearer auth — router-tier check). The MCP tool has no leeway to invent a different URL.

**Decision**: `push_activity` POSTs to `/api/ingest/activity` with envelope `kind="activity"`. `push_artifacts` POSTs to `/api/ingest/artifacts` with envelope `kind="artifacts"`. Both URLs are declared as module-level constants (never string-formatted from `kind`), tied to a docstring citing ADR-0013. The URL constants are unit-tested against the tool's actual POST target via `respx` (T-08, T-09). No `/api/ingest/files` string appears anywhere in the mcp-server source tree. `adr:ADR-0013` because that is the settling upstream contract; nothing here promotes a new ADR — this decision is a downstream binding.

### D-04: YAML source-of-truth is `.harness/program.yaml` only · blast:feature · rev:mechanical · adr:—

**Context**: The story text (AC-2 / AC-3) reads `.harness/profile.yaml` for both `files[]` and `artifacts{}`. Filesystem reality (checked in the state.json risks R-04 resolution): `.harness/profile.yaml` is identity-only (email / name / role, gitignored, per-machine) and holds no `files[]` or `artifacts{}` block; `.harness/program.yaml` is committed and holds `files[]` (line 84) + `artifacts{}` (line 110). A dual-source fallback (try `program.yaml`, fall back to `profile.yaml`) invites a silent mis-read: the tool would find zero activity or artifacts and report success, and the dashboard's panels stay empty for real work.

**Decision**: Both `push_activity` and `push_artifacts` read `<workspace_root>/.harness/program.yaml` and `.harness/program.yaml` only. `.harness/profile.yaml` is never read by either tool at any code path. A missing `program.yaml` yields `{success: false, error: "program_yaml_not_found", path: "<...>"}` before any HTTP attempt. Enforced structurally: `core/profile.py` (F-11) hard-codes `program.yaml` in the path join; there is no branch that consults `profile.yaml`. Unit tests (T-06) assert the missing-file path never falls back. Not promoted — swapping the source path later is a one-line change to `core/profile.py` (`rev:mechanical`).

### D-05: MCP batch cap is 500 rows per `push_activity` HTTP POST · blast:feature · rev:mechanical · adr:—

**Context**: PRD § Solution sketch and FR-2 pin the MCP-tier batch to 500 rows per POST. This is UNRELATED to the backend's internal 2730-row per-INSERT chunk (`activity_ingest._MAX_ROWS_PER_INSERT`, ING-02) — that's a DB batch size, not an HTTP one. The backend's outer router cap is 5000 rows / request (413 before DB work); 500 stays well below. Choosing 500 keeps a per-batch payload small enough that a 30 s HTTP timeout comfortably covers a batch, and lets a `push_activity` run against a 3000-row NDJSON file settle in 6 POSTs.

**Decision**: `services/mcp-server/src/agentrise_mcp/tools/push_activity.py` (F-07) declares a module-level `_MCP_BATCH_SIZE: int = 500` constant; every HTTP POST from that tool carries at most that many rows. Module docstring pins the "unrelated to backend's 2730-row DB chunk" note explicitly (per PRD § Documentation requirements). Unit test (T-08) asserts a 750-row two-file fixture produces exactly 2 POSTs of sizes 500 + 250. Not promoted — reducing / raising the cap is a one-constant edit + a test update (`rev:mechanical`).

### D-06: Bearer-token env-var is `AGENTRISE_INGEST_TOKEN` · blast:feature · rev:mechanical · adr:—

**Context**: FR-6 pins the env-var name to `AGENTRISE_INGEST_TOKEN`. Downstream ING-05 will read the same env-var from the same process when the Copilot bridge boots inside the same MCP server. Pinning the name prevents drift between the two stories and makes MCP client config snippets copy-pasteable across `services/mcp-server/README.md` (F-02) and ING-05's future docs.

**Decision**: `services/mcp-server/src/agentrise_mcp/core/config.py` (F-10) reads exactly `os.environ["AGENTRISE_INGEST_TOKEN"]` at process start (module import time is acceptable; per-invocation re-reads are not required since token rotation via restart is the operational model — a running local process ⇒ token loaded). Missing or empty → the tool returns `{success: false, error: "missing_ingest_token", message: "Set AGENTRISE_INGEST_TOKEN before invoking this tool."}` before any HTTP client construction (F-25, F-28 unit tests, TC-23 / TC-24). Env-var name is the only source; no `.env`-file fallback, no `.agentrise-mcp/config`-file fallback in this story (ING-05 may add one later). Not promoted — swapping the env-var name later is a one-line change; no data migrated under it (`rev:mechanical`).

### D-07: Root `docs/config/project-commands.yaml` gets no `mcp_server:*` namespace; `docs/config/stack-smoke.md` gets a `# mcp-server` section · blast:feature · rev:mechanical · adr:—

**Context**: D-01 fixes `services/mcp-server/` as a separately-deployed sibling and forbids wiring it into the main API's `preflight`. That answers "what MUST NOT be edited" (`docs/config/project-commands.yaml preflight:`). It does NOT answer "what MAY be added" (an optional `mcp_server:*` namespace at the root, plus / or a `# mcp-server` section in `docs/config/stack-smoke.md`). Two constraints settle this: (a) `docs/config/project-commands.yaml` is consumed by `harness preflight` (the main-API boot check); adding an `mcp_server:*` namespace there without wiring it into `preflight` produces dead keys that a future reader would try to run. (b) `docs/config/stack-smoke.md` is per-stack documentation of the smoke-boot command; every stack currently gets a section, and the MCP server is a new stack surface (new port 3010, new run command).

**Decision**: `docs/config/project-commands.yaml` is UNTOUCHED — no `mcp_server:*` namespace, no additions of any kind. `docs/config/stack-smoke.md` (F-45) gains one new `# mcp-server` section documenting the sibling service's boot: `Run:` (`cd services/mcp-server && uv run python -m agentrise_mcp`), `Env:` (`AGENTRISE_INGEST_TOKEN=<token>` required), `Check:` (`curl http://127.0.0.1:3010/mcp` returns MCP handshake or a 400; port is reachable). No `Deps:` (the mcp-server has no DB); no `Migrate:` (no schema). This satisfies the `plan-validation` § Config drift C2 / C3 checks (new service + new port both documented) without violating D-01's "no wiring into main API preflight" constraint. Not promoted — `rev:mechanical`; adding the namespace later is a purely-additive edit.

### D-08: MCP tool bodies are sync (not async) · blast:feature · rev:mechanical · adr:—

**Context**: PLAN.md §3 sketches the tool functions with an `async` signature. The concrete implementation ships them as sync bodies. Two options exist. (a) Async tools + `httpx.AsyncClient` — required if any real fan-out concurrency is possible inside a single tool call. Neither `push_activity` nor `push_artifacts` has such fan-out: `push_activity` POSTs batches sequentially (a 401 mid-batch must halt further POSTs, so batches cannot race), and `push_artifacts` sends exactly one POST. (b) Sync tools + `httpx.Client`. `fastmcp` v2 accepts sync-bodied tools registered via `@server.tool()` (Client / FastMCP call the sync function directly; async is not required by the transport). The sync path is what shipped: `HttpClient` (F-08) wraps `httpx.Client`, tool bodies iterate batches with a plain `for` loop, retry uses `time.sleep`. Round-2 review raised this as F-6 MEDIUM ("sync tool bodies vs PLAN §3's async pin — either refactor to async or record new DECISIONS entry"). This entry records the choice.

**Decision**: `push_activity` and `push_artifacts` bodies stay sync. The PLAN sketch's `async def` is superseded by this decision; no async refactor is scheduled. Rationale: (i) sequential batch semantics forbid concurrency inside a single tool call (halt-on-auth-failure requires ordering); (ii) `fastmcp` v2's `@server.tool()` accepts sync callables (verified against v2.x — the Server's tool dispatcher awaits async and calls sync directly); (iii) the sync `HttpClient` is simpler to reason about for retry + timeout policy and matches the mental model of "one HTTP request per batch". If ING-05 (Copilot bridge) introduces a code path that benefits from `asyncio.gather` across tool calls, the tool bodies can switch to `async def` at that point without changing the tool contracts — signature stays `(program_id, workspace_root) -> dict`. Enforcement: `test_push_activity` and `test_push_artifacts` use plain (non-async) test functions and call `push_activity()` / `push_artifacts()` directly — running these under `asyncio.run` is unnecessary. Not promoted — flipping sync↔async is a mechanical rewrite of two files with no cross-module contract change (`rev:mechanical`).
