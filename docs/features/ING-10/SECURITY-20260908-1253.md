## Headline — D-10/AF-01 (`admin` → `cio` removal)

**1. Is the removal complete?** Yes, verified independently across every path, not just `role_map.py`:

- `app/core/role_map.py`: `_ROLE_SLUG_TO_PERSONA` is now 6 keys (`dev, arch, pm, em, cxo, board_member`); `admin` absent; `map_role_slug("admin")` → `None` → row-level rejection. `test_map_role_slug_admin_is_deliberately_unmapped_af01` (tests/unit/test_role_map.py) pins this.
- `services/api/config/persona_role_map.yaml` (Tier-2 Keycloak path): no `admin: cio` entry — pre-existing from PR #235, unchanged by ING-10, still consistent.
- Tier-1 (`PERSONA_ROLE_MAP` env var): not code, nothing to grep; not a factor unless an operator sets it.
- Tier-3 (`persona_config` Postgres table, `app/core/persona_resolver.py`): `001_initial_schema.py` creates the table empty — no seed migration inserts `admin`/`cio` rows.
- `/auth/dev-bypass` (`app/auth/dev_bypass.py`): caller-supplied `role` is embedded in a `realm_access.roles` JWT claim and resolved through the **same** three-tier `PersonaResolver` as the real OIDC path — no separate mapping, no default. It only ever grants `cio` if an operator's Tier-1/2/3 config maps a role to `cio`; none of the three does for `admin` today.
- **Load-bearing fact not stated in the brief, found by grep**: `role_map.py`/`manifest_ingest.py` write their mapped value only into `user_roles` (and the raw slug into `program_roster.role`) — grep across `services/api/app` shows **no consumer reads `UserRole`/`user_roles` anywhere** except `manifest_ingest.py` itself (write-only). `docs/requirements/api.md:272` confirms this by contract: *"`user_roles` stays reference/audit on the session path (ING-08 AC-4 unchanged); program membership is read from `program_roster`, not `user_roles`."* Session persona (`current_user.persona`, the value `app/api/programs.py:118`'s `if persona == "cio":` bypass actually branches on) is resolved exclusively by `PersonaResolver` from an IdP role claim — it never touches `program_roster`/`user_roles`. **So today, nothing written by this endpoint can reach the `cio` bypass at all** — D-10 is a pre-emptive fix for the day `ING-08` wires `user_roles`/`program_roster.role` into session resolution, not a fix for a currently-live path. That doesn't make it premature — closing it now, before a consumer exists, is the cheaper time to do it — but the report should say plainly that the exploit window is not yet open, rather than imply it was.

**2. Should `cxo`/`board_member` → `cio` also be a finding?** I agree with the engineer's `accept`, for a reason beyond "unambiguous executive titles": since `program_roster`/`user_roles` are provably inert for authorization today (above), the fold is currently inert too — it cannot grant anything yet either way. The recommendation I'd add: when `ING-08` scopes its Keycloak-writer work, re-litigate this exact fold as a *security* question (not only the persistence/architecture question `R-03-role-map-persistence` currently frames it as), and check whether any `program_roster`/`user_roles` rows already carry a stale `admin`-derived `cio` value from before this fix that would need a data cleanup, not just a code fix.

**3. Keycloak vs. roster path consistency.** Both now decline `admin → cio` by omission — consistent in outcome. Structurally asymmetric though: `persona_role_map.yaml` feeds a **live, consulted-per-request** control (`PersonaResolver`, gating the real `cio` bypass); `role_map.py`'s output currently feeds a **dormant, unread** table. Worth naming explicitly so a future reader doesn't assume the two mechanisms carry equal present-day risk weight — they don't, yet.

## Medium findings

### F-1 — Unbounded `aliases[]` amplification (resource exhaustion)

- Source: checklist/input + stack-pattern/fastapi (performance-baseline.md)
- Severity: Medium
- CWE-770 (Allocation of Resources Without Limits or Throttling); OWASP API4:2023 Unrestricted Resource Consumption
- Files: `services/api/app/schemas/manifest.py:77-79` (`aliases: list[str]`, no `max_length` on the list or its string entries), `services/api/app/api/manifest.py:162-163` and `services/api/app/services/manifest_ingest.py:100-120` (`_TEAM_ENTRY_CAP` checks only `len(raw_team)` — the top-level array — before alias expansion), `services/api/app/services/manifest_ingest.py:220-235` (`expanded_rows` built as `sum(1 + len(aliases_i))`, then issued as one `pg_insert(...).values(expanded_rows)`), `services/api/app/main.py` (no request-body-size-limiting middleware anywhere in the app).
- Issue: the FR-5/AC-8 500-entry cap bounds `team[]`'s outer array length only. Nothing bounds `aliases[]` length per entry. `DATA-DESIGN.md` §8 and a comment in `manifest_ingest.py` ("R-05: expansion is bounded by `_TEAM_ENTRY_CAP` above, not a separate per-person limit") both assert the cap bounds total expansion — it does not: 500 entries × unbounded aliases each = an unbounded `expanded_rows` list built in Python memory and issued as one batch `INSERT`. There is also no global max-body-size guard in `app/main.py`, so `await request.json()` (`app/api/manifest.py:134`) fully parses an arbitrarily large body *before* the 500-entry check ever runs — a payload with only 10 `team[]` entries but millions of aliases each sails past FR-5 entirely. This is exploitable by anyone holding a valid ingest token for any single program (not a fully anonymous surface, but the trust boundary this router explicitly names as "the whole request body is untrusted input").
- Fix: (1) add `Field(..., max_length=<N>)` to `TeamMemberIn.aliases` (and a sane max string length on `email`/`aliases[]` entries); (2) make the FR-5 cap check post-expansion (`len(raw_team) + sum(len(aliases_i))`) rather than pre-expansion only, or add a second explicit cap; (3) add a request-body-size limit (ASGI middleware or reverse-proxy config) as a blanket parsing-safety control per `.claude/rules/security-baseline.md`'s "size caps at HTTP layer (413); bounded-reader pattern" — this gap is app-wide, not ING-10-specific, but ING-10 is the first endpoint where an attacker-shaped payload actually amplifies through it.
- Not previously caught: research risk #5 (MED) flagged the *cardinality* concept but its own suggested mitigation text ("document that alias expansion is bounded by AC-8's cap") is the same incorrect claim that shipped; REVIEW.md never revisits it. Not a duplicate of any existing carry-forward.

### F-2 — Test-only SQL identifier built via f-string (CF-10, already tracked)

- Source: checklist/input
- Severity: Medium (test-only scope)
- CWE-89-adjacent (SQL/identifier injection pattern), not the SAST regex's literal `SELECT` form so it did not auto-hit the grep pass — flagged manually.
- File: `services/api/tests/conftest.py:176-178` — `_ensure_database_exists()`: `conn.execute(f'CREATE DATABASE "{dbname}"')`, no bind parameter (Postgres doesn't parameterize identifiers, but no quoting/escaping of an embedded `"` either), and no connect timeout on the maintenance connection.
- Assessment: `dbname` derives from `settings.database_url` (`DATABASE_URL` env, a deploy-trusted value per this project's docs) with a `_test` + discriminator suffix. The one attacker-adjacent input in the derivation, `HARNESS_TEST_DB_SUFFIX`, **is** sanitized (`re.sub(r'[^A-Za-z0-9_]', '_', suffix)`) before use — that half is fine. The unsanitized half is the base path taken directly from `DATABASE_URL`, which this project's own `.env` contract treats as trusted config, not user input. Genuinely test-only (`services/api/tests/`), never shipped/executed in a request path.
- Already recorded: `state.json .pending_carry_forward[8]` id `CF-10`, `kind: finding`, no compliance tag — correctly triaged MEDIUM-non-blocking by review/validation, and this assessment concurs. Not double-counted as a new gap; flagged here only because the task asked for an independent read, not a rubber stamp.
- Fix (when picked up): parameterize via `psycopg.sql.Identifier` instead of an f-string, and add a `connect_timeout` to the maintenance connection per `.claude/rules/performance-baseline.md`.

## Low findings

### F-3 — Rejected `team[]` entry preserves a pre-existing roster row (AF-07, accepted)

- Source: checklist/data + manual review of D-06/soft-delete logic
- Severity: Low (informational — accepted design, not overturning it)
- File: `services/api/app/services/manifest_ingest.py:170-179, 308-329` (`_collect_present_emails` runs on every raw entry regardless of validation outcome; the soft-delete `UPDATE` only removes rows whose email is absent from `all_present_emails`)
- Issue: if an operator pushes a manifest where an existing member's entry fails validation (bad role slug, malformed alias) but their primary `email` is still literally present in the payload, that member's existing `program_roster` row is neither updated nor soft-deleted — it stays exactly as it was from the last successful push. This is the shipped, reviewed behavior (`AF-07`, triaged `reject` — i.e. the proposal to soft-delete on rejection was rejected in favor of fail-open retention), and I agree it's defensible: full omission (the documented removal path) still soft-deletes correctly and immediately.
- Why Low, not Medium: `program_roster.role`/`user_roles.role` have no read-side authorization effect today (same fact as the headline item) — the only thing retained is *program visibility* (via `removed_at IS NULL`), not an elevated role. The 200 response's per-entry `rejected` status also tells the operator exactly which entries need fixing, so this isn't a silent gap.
- Recommendation: no code change; consider a one-line note alongside `data.md`'s existing `role_semantics` field stating that a rejected entry's *membership* (not just its role) is unaffected, so a future reader doesn't conflate "rejected" with "revoked."

## Manual OWASP checklist highlights

- **Input**: `program:` block validated as one unit (400, zero writes on failure); every `team[]` entry validated independently via its own `TeamMemberIn.model_validate()` so one bad entry never 422s the whole request (D-05/D-09) — sound. Gap: alias-count/length unbounded (F-1).
- **Auth**: `get_ingest_token()` is called imperatively (not `Depends()`) because `programId` lives in the body — reviewed the wiring: `program_id` is resolved exactly once from the body and passed unchanged to both the scope check and the write path (`manifest_ingest.py`'s own docstring: "never re-derived from `payload.get('programId')` a second time"). No TOCTOU between what's authorized and what's written. The `"*"`/empty-list allow-all scope semantics are ING-01's pre-existing, documented, accepted design (ADR-0006) — unchanged by this story, not re-litigated here.
- **Data (PII)**: traced every branch — happy path, row-level rejection, `program:`-block 400 abort, and the router's 413 branch — `log_ingest_manifest_write()`'s field allowlist never carries `email`/`name`; `_classify_team_entry_error()` inspects only `loc`, never `input`/`ctx` (which pydantic's `ValidationError.errors()` would otherwise expose); the raised `ValueError` messages in the email format validators never interpolate the value. No PII reaches a log line or an error response at any level. `roster_detail[].email` reflecting a caller's own submitted (possibly malformed) email back in the 200 response is the caller's own data returned to the same authenticated caller, not a cross-tenant leak.
- **Crypto**: no new crypto in this diff; ingest-token hashing (SHA-256 lookup) is ING-01's pre-existing, unchanged code.
- **Logs/errors**: all router-level 400s use fixed, generic `detail` strings; no stack traces or internal identifiers reach the client.
