#### F-2 — checklist/auth: sign-out uses `GET /logout` — logout-CSRF exposure remains via top-level navigation

- Source: checklist/auth
- Severity: Low
- File: `apps/web/src/components/PersonaDashboardShell.tsx:143`, `apps/web/src/app/logout/route.ts:52`
- Issue: sign-out is a `<form method="get" action="/logout">` control, and the handler is `export async function GET(...)`. Because the `dashboard_session` cookie is `sameSite: "lax"` (`apps/web/src/lib/tokenStore.ts:132`), a cross-site subresource fetch (`<img>`, `fetch`, XHR) will NOT include the cookie, so an image-tag CSRF is blocked. However, a top-level cross-site navigation to `/logout` (e.g. `<a href="…/logout">` or `window.location = "…/logout"` from a malicious page) DOES send the lax cookie and will forcibly end the user's session. Impact is limited to nuisance forced sign-out, not data exfiltration — logout does not alter application state beyond terminating the session.
- Design context: recorded design trade-off. `PersonaDashboardShell.tsx:141-149` documents the choice: "Zero-JS GET form: a `<button onClick>` would force `use client` on this Server Component." `logout/route.ts` D-08 fixes the read-then-clear-then-relay call order but does not address CSRF hardening. `DECISIONS.md` for OVW-05 does not enumerate this trade-off; the AUTH-07 story owns the endpoint.
- Fix (any one of):
  1. Convert to `POST /logout` (Route Handler + form `method="post"`); acceptable for a Server Component if wrapped in a `<form>` — no `use client` needed.
  2. Tighten cookie to `sameSite: "strict"` on the session cookie (project-wide impact — reject if any cross-site OAuth callback flow depends on lax semantics).
  3. Add a same-origin `Sec-Fetch-Site` / `Origin` check inside `GET /logout`.
- Rule: `security-review-checklist` § Authentication and authorization ("Sessions invalidated on logout and password change"); logout invalidation itself is correct — the finding is on the trigger surface, not the invalidation.

## What passed

- **Sign-in page — no credential leakage in HTML/JS.** `apps/web/src/app/login/page.tsx` is a Server Component with a zero-JS SSO submit form (`action="/login/start"`) — no password field, no client script, no `dangerouslySetInnerHTML`. Static values and Next `Image`-free brand markup only. `page.module.css` carries no secrets.
- **Session invalidation on sign-out.** `logout/route.ts:52-53` reads the session token BEFORE clearing the cookie, then calls `clearSession()` unconditionally (idempotent, tolerates read-only jar via `tryMutateCookie`), then relays to Keycloak's end-session endpoint with the just-read bearer so backend audit logs resolve `user_id` rather than logging `"unknown"`. The AC-16 caveat (issued access token survives until its own natural expiry) is documented and matches OAuth2 semantics; not a finding.
- **Cookie hardening.** `dashboard_session` set with `httpOnly: true`, `sameSite: "lax"`, `path: "/"`, `secure: process.env.NODE_ENV === "production"` (`tokenStore.ts:132-136`). Token never crosses to client — `tokenStore.ts` imports `next/headers`, unreachable from a `"use client"` component.
- **Open-redirect prevention on both flows.**
  - `login/page.tsx:33`: `redirect(ADOPTION_OVERVIEW_ROUTE)` — string constant from `lib/routes.ts`, no request-derived target.
  - `login/start/route.ts:61`: `NextResponse.redirect(location)` where `location` is the `Location` header from a server-to-server fetch to `${API_BASE}/auth/login` (trusted FastAPI upstream, not attacker-controlled). Failure modes (missing `Location`, non-3xx status, throw/timeout) all produce a generic opaque 502 with no upstream text.
  - `logout/route.ts:82`: same trusted-upstream relay pattern for `${API_BASE}/auth/logout`. Same opaque 502 fallback.
  - `overview/page.tsx:99`: `redirect("/login")` — string constant, in `catch` only, only on `SessionExpiredError`, correctly placed to avoid swallowing `NEXT_REDIRECT`.
  - No user-controlled `?returnTo=` / `?next=` parameter is read anywhere in the diff.
- **Fetch hardening.** Every network call in the new modules pins `signal: AbortSignal.timeout(FETCH_TIMEOUT_MS)` (5 s) — `meApi.ts:47`, `login/start/route.ts:44`, `logout/route.ts:58` — per `.claude/rules/performance-baseline.md`.
- **PII / secret logging.** `composeSignedInUser.ts`, `meApi.ts`, and `overview/page.tsx` contain no `console.log`/`console.error`/`log.*` calls. `tokenStore.ts:26-30` explicitly documents "no line in this module logs a token, cookie value, refresh response body, or upstream error body." Grep confirmed clean.
- **JWT/TLS/crypto.** No `algorithm: "none"`, no `rejectUnauthorized: false`, no `verify=False`, no MD5/SHA1/DES/ECB references introduced.
- **Input/injection.** No SQL string concat, no `eval`/`new Function`/`exec`/`child_process.exec`/`subprocess(...shell=True)`. No `innerHTML =` or `document.write(` sinks.
- **XSS surface — `PersonaDashboardShell.tsx`.** Inline `style` bindings feed only computed brand-token colours (`personaAvatarColor` → `formatPersonaTag(persona).color/.background`, whitelisted by the persona-tag registry) — no user string reaches a `style` prop. `signedInUser.name` and `signedInUser.jobTitle` render via `{...}` (React auto-escaping); `jobTitle` is derived from `PERSONA_DISPLAY`, never from wire (composeSignedInUser.ts by construction), which independently closes research risk #2.
- **Persona-resolution error path.** `PERSONA_RESOLUTION_ERROR = "persona-resolution-error"` sentinel (D-03) reuses the shell's existing `PersonaTagError` neutral badge — no new error UI, no leakage of upstream `/api/me` status codes to the browser.
- **Server-only isolation.** `tokenStore.ts`, `meApi.ts`, `overview/page.tsx`, and both `route.ts` files import `next/headers` / `next/server` or otherwise sit in a server-only path; no client bundle exposure of session material.
