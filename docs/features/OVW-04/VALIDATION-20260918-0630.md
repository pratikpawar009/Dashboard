## Failed (bug blocks)

### BUG-OVW04-01 — `/overview` 500s in the real app: event handler on a Server Component `<a>` (Priority: Must — blocks the entire Overview page for every persona)

- **AC/NFR affected**: AC-3 (card navigation), AC-4 (no hardcoded values, real render), and transitively every AC on this story plus OVW-01's own page, since `/overview` now 500s outright.
- **Where**: `apps/web/src/components/ProgramCard.tsx` — no `"use client"` directive, yet the component defines `handleClick` (line ~39) and attaches it via `onClick={handleClick}` on the root `<a>` (line ~53). Its parents (`ProgramLeaderboard.tsx`, `AdoptionOverview.tsx`, `apps/web/src/app/overview/page.tsx`) are all Server Components too — `AdoptionOverview.tsx`'s own docstring states it is "Deliberately a plain component with **no `"use client"`**" (DECISIONS.md), so nothing in the render tree above `ProgramCard` is a Client Component boundary either.
- **Steps executed** (real stack, not mocked):
  1. Started the real FastAPI server (`uv run uvicorn app.main:app --port 8010`) against the repo's real ephemeral Postgres on 5442, migrated to head.
  2. Confirmed `GET /health` → 200.
  3. Started the real Next.js dev server (`pnpm dev --port 3012`, `NEXT_PUBLIC_API_URL=http://localhost:8010`).
  4. Confirmed `GET /login` → 200 with real branded markup.
  5. Minted a CIO session via the repo's local `/dev-login` helper (backed by `/auth/dev-bypass`, itself real, not mocked).
  6. Requested `GET /overview` with that session cookie.
- **Expected**: 200, with the Program Leaderboard section rendering (as OVW-04-TC-01's live equivalent — see the direct API call below — items ordered tokens DESC: dashboard 3220.9M > beta 2.4M > gamma 1.9M > alpha 244.4K, no CSS-key leakage).
- **Actual**: `GET /overview 500` every time. Next.js dev log (`tmp/smoke-nextjs.log`):
  ```
  ⨯ Error: Event handlers cannot be passed to Client Component props.
    <a href=... className=... style={{...}} aria-label=... onClick={function handleClick} children=...>
                                                                     ^^^^^^^^^^^^^^^^^^^^^^
  If you need interactivity, consider converting part of this to a Client Component.
  ```
  The response body itself streamed the correct data server-side first (the RSC payload embeds `program_id":"alpha"|"beta"|"dashboard"|"gamma"` and the literal "Program board" / "— all programs using Harness" heading text before the render aborts), confirming the backend/data-fetch half of the feature is correct — the failure is purely the client-boundary violation.
- **Failure reason**: `ProgramCard.tsx` needs `"use client"` (it owns real interactivity: the `onClick` → `program_drilldown` log call per D-06), but nothing in its render chain declares one. This is a real Next.js App Router constraint (Server Components cannot receive function props), not a test-environment artifact.
- **Why unit/component tests missed it**: `ProgramCard.test.tsx` renders `ProgramCard` directly via `@testing-library/react`'s `render()`, which uses jsdom and has no concept of the RSC serialization boundary — a function prop passes through untouched. The story's own test-case JSON deliberately maps TC-06/07/12 to `type: integration` using "Testing-Library against a mocked fetch boundary" (per the manifest's `generation_note`) precisely because no e2e runner is wired yet — but that substitution is exactly what let this defect through: it validates the component's own render logic, not its legality inside the real App Router tree it ships into.
- **Fix options** (do not implement — this is a report, not a patch):
  1. Add `"use client"` to `ProgramCard.tsx` (simplest — the whole card is already a small, self-contained leaf with one interactive affordance).
  2. Split: keep `ProgramCard` a Server Component, extract the `onClick`-bearing wrapper into a tiny new Client Component that composes around the server-rendered content — mirrors the "Client Component boundary" note already present (unused) in `next-patterns`' Error handling section for `error.tsx`.
  3. Either fix needs a regression TC per the regression-tag protocol: a real Playwright/e2e or an RSC-aware render test (not plain Testing-Library) that would have caught this, tagged `regression-OVW-04-TC-06`.
- **Artefact**: `/Users/pratik.pawar/Desktop/dashboard/tmp/smoke-nextjs.log`, `/Users/pratik.pawar/Desktop/dashboard/tmp/overview.html` (both left in place for the fix-loop; not cleaned up since Phase 2b's smoke verdict is FAIL for this stack).
