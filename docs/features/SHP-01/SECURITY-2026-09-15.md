## Manual OWASP checklist + stack-pattern walk

Applied against the four surface areas the assignment named:

### 1. Client-side session/token exposure

- No `localStorage`, `sessionStorage`, `document.cookie`, or `window.*` access anywhere in the SHP-01 diff (verified with `grep -nE 'localStorage|sessionStorage|document\.cookie|window\.'` — 0 matches across `Persona*.tsx`, `ProgramContext.tsx`, `lib/*.ts`, `types/persona.ts`).
- No `fetch` / `XMLHttpRequest` / `axios` in any SHP-01 file — the shell is fully prop-driven (`docs/features/SHP-01/DATA-DESIGN.md § 9`). Session/persona resolution lives upstream (AUTH-02) and is passed in.
- No `"use client"` directive on any SHP-01 component — everything is a Server Component. Zero risk of session props being serialised into the client bundle by mistake.
- `SignedInUser = { name, jobTitle }` (both display strings). No email, phone, SSN, token, or other credential material crosses the prop boundary. **PASS**.

### 2. Programs list scoping (open-aggregate model per AUTH-04 review)

- SHP-01 does not fetch, list, or filter programs. `ProgramContext` renders a single, caller-supplied `program: ProgramContextData` (`{ icon, name, type, description }`) verbatim.
- The open-aggregate scoping decision from AUTH-04's review is inherited unchanged — SHP-01 introduces no new list endpoint, filter, or aggregation to reopen it. Out of scope for this review, no finding.

### 3. Persona resolution trust boundary

- `Persona` is deliberately typed `string` (`types/persona.ts:44`), with the runtime allow-list `VALID_PERSONAS` (5 entries) enforced by `formatPersonaTag()` (`lib/formatPersonaTag.ts:88-93`).
- The trust boundary itself sits at the backend (`services/api/app/core/persona_resolver.py`, out of scope). SHP-01 provides display-layer defense-in-depth: any persona value outside the allow-list throws `PersonaTagError` and renders the neutral "Persona unavailable" badge (`PersonaHeader.tsx:31-42`), never a fabricated tag. This is the intended fail-loud behaviour (D-03).
- `signedInUser.jobTitle` is composed frontend-side from `PERSONA_DISPLAY[persona].jobTitle`, never read off the wire (`types/persona.ts:11-16`) — a tampered persona value can only redirect the displayed job title to one of the 5 documented display strings, all of which are inert display text with no privilege implication.
- `PersonaHeader`'s `try/catch` catches only `PersonaTagError` and re-throws every other error, so an implementation bug that raised (e.g.) a `TypeError` cannot be silently swallowed as "invalid persona". **PASS**.

### 4. No secrets in JS bundle

## Info findings (non-blocking, informational)

### I-1 — `PersonaTagError` message embeds the offending persona string verbatim

- Source: `checklist/logs`
- Severity: Info
- Path: `apps/web/src/lib/formatPersonaTag.ts:89` (`throw new PersonaTagError(persona)`)
- Issue: `PersonaTagError` extends `Error` and passes the untrusted persona string as the error `message`. When the caller catches only `PersonaTagError` (`PersonaHeader.tsx`, `PersonaDashboardShell.tsx personaAvatarColor`) the value is inert — it renders a neutral badge and never surfaces the raw string. If a future caller lets this error escape uncaught, the untrusted value will appear in React's default console output / error boundary. The persona value's provenance is AUTH-02's resolver output (server-controlled today), so the practical exposure is nil — this is a hardening note, not a defect.
- Fix (optional): if the message is ever logged unconditionally, sanitise or redact it at the log call site (e.g. `String(persona).slice(0, 32)`). No code change required today; the two current callers already catch and swallow the message.
- Rule id: `security-baseline.logs-and-errors`
