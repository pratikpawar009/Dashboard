# SHP-01 — Decisions

Non-trivial technical choices made while planning SHP-01's persona header/context shell. Header slugs (`blast:`/`rev:`/`adr:`) are machine-greppable per the `decide` skill.

### D-01: Signed-in-identity field names isolated behind one type file, not threaded through every component · blast:feature · rev:mechanical · adr:—

**Context**: FR-1's `signedInUser: { name: string; jobTitle: string } | undefined` shape depends on an AUTH-01 `session`-contract amendment that is decided but has not landed (AUTH-01 is at `phase=review`) — the field names, or the shape itself, may change when that amendment actually ships. `.claude/rules/reusability-baseline.md` and the story's own binding constraint both require that a later rename not become a wide refactor across every component that touches identity data.

**Decision**: `apps/web/src/types/persona.ts` is the single source of the `SignedInUser`, `ProgramContextData`, and `Persona`/`VALID_PERSONAS` shapes. Only two files reference `signedInUser.name`/`.jobTitle` directly: this type file and `PersonaDashboardShell.tsx` (the identity block is inline in the composing shell, not a separate component, per the story's own 3-file Test mapping) — `PersonaHeader.tsx` and `ProgramContext.tsx` never see `signedInUser` at all. A field rename when the AUTH-01 amendment lands is a two-file change, not a wide refactor.

### D-02: `formatPersonaTag()` returns one `{ tag, subtitle, color, background }` object per persona, not four separate lookup functions · blast:feature · rev:mechanical · adr:—

**Context**: FR-2 names a single function, `formatPersonaTag(persona)`, mapping each of the 4 valid personas to its tag string and throwing for `cio`/any invalid value. The Scope section separately asks for a subtitle-literal map (C-4) and a persona-to-color map for both the tag pill and the initials-avatar background (FR-2's second Scope bullet) — all three keyed off the same 4-valued persona enum and sharing one fail-loud invariant. Four separate exported functions would duplicate the enum validation and the `PersonaTagError` throw site four times.

**Decision**: one internal `PERSONA_DISPLAY` map and one exported `formatPersonaTag(persona): { tag: string; subtitle: string; color: string; background: string }`, backed by a single `PersonaTagError` class thrown once, in one place, for `cio` or any value outside the 4 valid personas. `PersonaHeader.tsx` reads `.tag`/`.subtitle`/`.color`/`.background` from the one call; the identity-avatar circle in `PersonaDashboardShell.tsx` reuses the same `.color` value for its background, so the tag pill and the avatar can never disagree on a persona's color.

### D-03: Single `persona` prop — every value outside the 4 valid personas (including `cio` and a resolver-error sentinel) drives the same neutral-badge path · blast:feature · rev:mechanical · adr:—

**Context**: FR-5's error state has two distinct triggers per the PRD text — "the persona-resolver raised (i.e. `PersonaNotFoundError`), or a `cio` value reaches the shell" — that must render identically (same badge, same copy, same `aria-live` announcement), while C-7 asks for a minimal, single-purpose prop interface with "no persona conditionals." A second boolean/status prop (e.g. `personaError?: boolean`) would duplicate the invalid-value branch `formatPersonaTag()` already has to have for `cio`, and would need its own precedence rule against the `persona` value.

**Decision**: the shell exposes exactly one persona-related prop, `persona?: string`. `undefined` means session/persona-resolver output has not yet resolved (FR-5's loading gate — suppresses the identity bar, tag, subtitle, and program context). Any defined value is passed to `formatPersonaTag()`; one of the 4 valid personas renders normally, and every other value — `'cio'`, or whatever sentinel the composing page passes after catching a `PersonaNotFoundError` from AUTH-02's resolver — throws `PersonaTagError`, which `PersonaDashboardShell` catches and renders as the one neutral "Persona unavailable" badge plus the `aria-live="assertive"` announcement. No second prop, no branching beyond this one gate.

### D-04: Persona and program-type color pairs are added to `docs/design/tokens.md`, sourced from the decoded mockups, not left only as code comments · blast:feature · rev:mechanical · adr:—

**Context**: FR-2 ("sourced from `docs/design/tokens.md`") and FR-4 ("a lookup table sourced from `docs/design/tokens.md`") both point at `tokens.md` as the source for two color tables — but `tokens.md`'s existing `## Color` section lists only generic named roles (Primary, Success, Accent-purple, Accent-terracotta), not the 4 persona tag/avatar pairs or the 4 program-type pairs the mockups actually bind. Both tables were cross-checked byte-exact against the decoded ARC/DEV/PMD/EMD markup (persona pairs: `docs/research/SHP-01.md` § Design Mockup Analysis) and EMD's `tMap` literal (program-type pairs, not previously extracted into any doc).

**Decision**: extend `docs/design/tokens.md` with two new tables — `## Persona colors` (architect/developer/product-manager/engineering-manager → tag color + tag background + avatar background, the same value) and `## Program type colors` (Migration/Greenfield feature development/Brownfield feature development/Maintenance → color + background, sourced from the EMD mockup's `tMap`) — using the verified literal hex values. This makes FR-2/FR-4's tokens.md-sourcing claim literally true and gives any future story needing the same program-type colors (e.g. PGD-01) one canonical place to read them, instead of re-deriving from mockup source a second time.

### D-05: Identity-bar neutral fallback (when `signedInUser` is `undefined` post-resolution) renders an empty gray circle with no name/job-title text, not a suppressed region · blast:feature · rev:mechanical · adr:—

**Context**: FR-5 defines the *loading* fallback (suppress the identity bar entirely) and the *error* fallback (a "Persona unavailable" badge) in concrete markup, but the identity block's own neutral state — reached whenever `signedInUser` is `undefined` while `persona`/`program` have already resolved, which is the normal, expected case for the whole of Phase 1 before the AUTH-01 amendment lands — has no PRD-specified markup. `SHP-01-TC-02`'s fourth scenario requires this state to be distinct from both loading (nothing renders) and populated (real name/jobTitle render), and FR-1 requires "never a placeholder name or blank field."

**Decision**: when `signedInUser` is `undefined` and the shell is not in its outer loading state, the identity block renders a single 34×34px circle in a neutral border-ramp gray (`#e4e7ec`, `docs/design/tokens.md` § Border and surface ramp) with no initials inside and `aria-hidden="true"` (it conveys no information), and omits the name/job-title text lines entirely rather than rendering them empty. This is a real, asserted render — not a suppressed region — distinguishing it from the loading state, and it never fabricates a name or job title.

### D-06: Static styling lives in the CSS Module; only the data-driven color pair crosses as a minimal React `CSSProperties` object · blast:feature · rev:mechanical · adr:—

**Context**: D-02/D-04 put the persona and program-type hex pairs in `formatPersonaTag()`/`getProgramStyle()` return values — they are per-render data, so they cannot be static rules in a `.module.css` file. PLAN.md does not pick a binding mechanism, and three components (T-07, T-08, T-10) all needed the same one; left unspecified, each worker would have chosen differently on first contact. Two mechanisms were available and both are wrong here: the mockups' own (a whole inline style string per element, `style="{{ prog.avatarStyle }}"`) is exactly what `docs/design/README.md` § "The templates also bind presentation" warns against copying, and it is not applicable in React, where `style` takes an object; hardcoding the hexes into the CSS Modules would break FR-2/FR-4's "sourced from `docs/design/tokens.md`" single-source claim and D-02's guarantee that the tag pill and the identity avatar can never disagree on a persona's color.

**Decision**: every static value — padding, font size, weight, radius, border and neutral-ramp colors, the geometry the mockup carries in the same style string — is a literal rule in the component's own `.module.css`, following `next-patterns` § Design system (CSS Modules per component; no CSS/component framework in this repo). Only the *data-driven* color pair crosses the boundary, as a minimal React `CSSProperties` object holding nothing but `color`/`background`, applied via the element's `style` prop: `style={{ color, background }}` in `PersonaHeader` (from `formatPersonaTag()`), `style={avatarStyle}` / `style={typeChip}` in `ProgramContext` (from `getProgramStyle()`). No component composes or applies a full CSS declaration string, and none reads a style value off a prop (FR-4/C-5 already forbids the latter).

**Deviation from PLAN.md, recorded deliberately**: `getProgramStyle()` keeps its planned name and its two planned keys (`{ avatarStyle, typeChip }`, per `tasks.json` T-06 and `docs/requirements/api.md#persona-shell`), but each is typed `React.CSSProperties` rather than the plan's `string`. A `string` return would have forced either a raw-CSS-string parser or `dangerouslySetInnerHTML`-adjacent handling, since React's `style` prop does not accept a CSS declaration string — the plan's `string` typing carried over from the mockup's template mechanism, which this decision declines. Key names, call site, and the "the shell composes the style, the prop carries data only" intent are all unchanged.
