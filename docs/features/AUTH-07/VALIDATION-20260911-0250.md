## AC-7 determination — round 2: **MET**

Independently re-derived from the code, not taken on the fix agent's word.

**What changed** (`services/api/app/core/persona_resolver.py`):

- New private `_cached_lookup(role)` (lines 322–365): same double-checked-locking shape as
  `resolve()`'s inline cache handling — lock-free fast read of a warm entry, then acquire
  `self._lock`, re-check, and only then run `_lookup_tiers`. Reads and writes the **same**
  `self._cache` dict, the **same** `role.casefold()` key, and the **same** `_CACHE_TTL_SECONDS`
  (300s) `resolve()` uses — confirmed by direct read: no second cache/lock/TTL exists anywhere in
  the file (`grep -n "self._cache\|self._lock\|_CACHE_TTL_SECONDS"` returns only the one instance of
  each, shared across `resolve()`, `_cached_lookup()`, and `_resolve_precedence_order()`).
- `resolve_precedence()` (line 308) now calls `await self._cached_lookup(role)` per candidate,
  replacing the round-1 call to `self._lookup_tiers(role)` directly.
- A miss is still never cached (line 359–361 returns `None` without writing `self._cache` — AC-26
  preserved, verified by reading the method body, not just its docstring).
- `resolve()` itself is byte-for-byte unchanged (lines 223–265) — the task brief's claim holds.

**Test evidence** (both independently re-run, not just read):

- `test_resolve_precedence_bounded_tier3_queries_live_db` — single cold call to
  `resolve_precedence(["qa", "architect"])` against a live migrated Postgres: 2 `persona_config`
  SELECTs (one per surviving role) + 1 `persona_precedence` SELECT. **PASS.**
- **New** `test_resolve_precedence_repeated_call_reuses_warm_cache_auth07_ac07` — two consecutive
  calls to `resolve_precedence(["qa", "architect"])` (now both Tier-3-mapped, unlike the miss-role
  `"qa"` in the test above) sharing one query-counting context: asserts the **second** call adds
  zero additional `persona_config` SELECTs and zero additional `persona_precedence` SELECTs (
  `role_counter.count == 2` not 4, `order_counter.count == 1` not 2). **PASS.** This is the literal
  "repeated call while cache is warm → no additional Tier-1/2/3 lookup" scenario AC-7 describes —
  round 1 found no test exercised it; this one does, and it passes against the real fix.

**Net conclusion**: for the live regression scenario (`realm_access.roles =
['Architect','Developer','developer']`), a second `GET /api/me` call within the 300s TTL now hits
the warm `self._cache` entry for every surviving candidate role via `_cached_lookup`, issuing zero
additional Tier-1/2/3 lookups — matching AC-7's text exactly. `get_current_user`
(`app/core/auth.py:311-317`) was correctly left untouched per the task brief; the fix is entirely
contained in `persona_resolver.py`, closing T-05's file scope as the round-1 report's suggested fix
option (a) anticipated.
