## AC-7 determination (the substantive finding)

**AC-7 is NOT MET**, for any token surfacing 2 or more surviving roles.

> AC-7 (verbatim): *Given `GET /api/me` is called repeatedly for the same session while
> `persona-resolver`'s 300s cache is warm, then no additional Tier-1/2/3 lookup runs — this route
> owns no cache of its own, it only calls the existing resolver.*

**Code evidence** (`services/api/app/core/persona_resolver.py`):

- `resolve_precedence()` (lines 267–317) calls `self._lookup_tiers(role)` (line 305) for **every**
  surviving role, on **every** invocation. `_lookup_tiers()` (lines 340–370) reads
  `self._tier1_map`/`self._tier2_map` directly and falls through to `self._resolve_tier3()` — it
  contains **zero** references to `self._cache`, confirmed by direct read of the file (`resolve()`
  itself references `self._cache` six times; `resolve_precedence`/`_lookup_tiers` reference it zero
  times).
- The method's own docstring (lines 293–295) states this explicitly: *"Bypasses `resolve()`'s own
  per-role cache entirely: this is a fresh tier lookup per candidate role, same as
  `_resolve_uncached` — only `resolve()` itself is cached."*
- `app/core/auth.py:311-317` — `get_current_user` (a per-request FastAPI dependency, recomputed on
  every request, no request-to-request memoization of its own) calls
  `persona_resolver.resolve_precedence(surviving_roles)` whenever `len(surviving_roles) > 1`. This is
  the **only** path that determines `CurrentUser.role` for a multi-role token, and it runs before
  `GET /api/me`'s own (correctly cached) `persona_resolver.resolve(current_user.role)` call ever
  executes.

Net effect: for the live 2026-09-10 regression scenario itself
(`realm_access.roles = ['Architect','Developer','developer']`), every single `GET /api/me` call —
however many times it is repeated, however warm `resolve()`'s 300s cache is — re-runs the full
Tier-1/Tier-2/Tier-3 fallthrough for `Architect`, `Developer`, and `developer` inside
`get_current_user`, before the route even runs. When the winning persona is Tier-3-resolved rather
than Tier-1/2, this is a fresh Postgres query per request, not per 300s — the exact cost the cache
exists to bound.

**Test evidence confirms the gap is real, not just theoretical**: the only test that measures Tier-3
query counts against `resolve_precedence`
(`test_resolve_precedence_bounded_tier3_queries_live_db`, `tests/unit/test_persona_resolver.py:1248`)
issues a **single** call to `resolve_precedence(["qa", "architect"])` and asserts one query per
surviving role *for that one call*. No test in the suite issues a **second** call to
`resolve_precedence` with the same role set and asserts the query count does not increase — the
warm-cache-repeat scenario AC-7 actually describes is never exercised. `test_me.py`'s own AC-7 test
(`test_no_route_owned_cache_every_call_reinvokes_resolve_ac7`) uses a **stub** resolver and a
**single-persona** stub — it proves the route itself has no cache, which is true, but does not
exercise the multi-role `resolve_precedence` path at all.

**Mitigating factors, accurately scoped, not overstated:**
- T-06 narrows the blast radius correctly: 0 or 1 surviving roles (every `/auth/dev-bypass` token,
  and any real token with exactly one product role) never call `resolve_precedence` at all — they use
  the cached `resolve()` path exclusively. The gap is real only for 2+-role tokens.
- Both formal TCs (AUTH-07-TC-01/TC-02) pass; neither one asserts AC-7, and neither claims to (their
  `requirement_id`s are AC-19 and AC-25/26 respectively per `docs/test-cases/AUTH-07.json`) — their
  passing does not contradict this finding.
- This is not a newly-discovered defect: it is `AF-04` in `docs/features/AUTH-07/FLAGS.md`, raised by
  T-05, verified there in the same terms ("zero references to `self._cache`"), and explicitly
  deferred to this gate with the disposition *"If review rules AC-7 unmet, this becomes a
  CRITICAL/HIGH finding."* This report is that ruling: **unmet**, on a literal reading of the AC text,
  which contains no carve-out for "except when 2+ roles survive."

**Bug block:**

### AC-7 — `resolve_precedence` bypasses the 300s cache on every multi-role request (Priority: Must)

- AC: AUTH-07-AC-7 (`docs/stories/AUTH-07.md:27`) — "no additional Tier-1/2/3 lookup runs" while the
  cache is warm.
- File/line: `services/api/app/core/persona_resolver.py:267-317` (`resolve_precedence`),
  `:340-370` (`_lookup_tiers`); call site `services/api/app/core/auth.py:311-317`
  (`get_current_user`).
- Failing assertion (none exists — this is the gap): no test asserts
  `session_factory.call_count` stays flat across a **second** `resolve_precedence` call with the same
  role set within the 300s TTL. Manually reasoning through the code: it would not — `_lookup_tiers`
  has no cache read on either call.
- Expected: a second `GET /api/me` (or any second authenticated request) for the same multi-role
  session, within 300s of the first, performs zero additional Tier-1/2/3 lookups.
- Actual: every request performs a fresh 3-tier fallthrough for every surviving role, unconditionally.
- Likely fix (not applied — GATE MODE is read-only on source): either (a) have `resolve_precedence`
  consult/populate `self._cache` per candidate role using the same casefolded key `resolve()` uses, or
  (b) have `get_current_user` call `resolve()` per role first (cached) and feed only the resulting
  `(role, persona)` pairs into a pure in-memory ranking step, never re-touching a tier. Either closes
  T-05's file scope; `app/core/auth.py` (T-06) does not need to change either way.
