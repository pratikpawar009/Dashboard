## High findings

### F-SEC-1 — `generate_rollup_golden_snapshots.py` truncates all seeded tables via ambient `DATABASE_URL`, with no confirmation, no `--yes`, no environment allow-list

- Source: checklist/input (trust-boundary) + `.claude/rules/security-baseline.md` ("Treat environment variables as untrusted unless the deploy contract documents otherwise")
- Severity: **High**
- CWE-284 (Improper Access Control) / OWASP A04:2021 Insecure Design, A05:2021 Security Misconfiguration
- File: `services/api/scripts/generate_rollup_golden_snapshots.py` (new, 265 lines)
- Issue: `_truncate_all()` (line 144) unconditionally issues `DELETE FROM` (functionally a full-table wipe; the module docstring itself calls it "TRUNCATE") against `usage_events` and all 10 rollup tables, then `session.commit()` — irreversible the instant it runs. The target database comes solely from `SessionLocal`/`app.core.db.engine`, which reads `settings.database_url`, itself sourced from the ambient `DATABASE_URL` env var (`app/core/config.py`). There is:
  - no confirmation prompt,
  - no `--yes`/`--force` flag gate,
  - no `ENVIRONMENT` allow-list (contrast `/auth/dev-bypass`, which this same repo already gates behind an explicit allow-list of `local`/`development`/`dev`/`test`/`ci` and fails closed — README.md, `app/auth/dev_bypass.py`),
  - no hostname/connection-string sanity check (e.g. refusing a non-`localhost` host).

  The module docstring's own warning ("never point this at a real dev/prod database; it truncates every seeded table between sizes") is the *only* control — a comment, not an enforced guard. A developer who exports `DATABASE_URL` for another task and forgets to unset it before running this script (or a CI job that later wires it into a scheduled/automated step) would silently and irreversibly destroy the entire ingest history and every rollup table, org-wide. This is a genuinely new, previously-unflagged risk: code review's own AF-03 on this same file addressed only fixture-determinism ("harmless artifact... seed skew cancels exactly"), not the destructive-operation-without-guard question.
- Fix: add an explicit safety gate before `_truncate_all()` runs — at minimum, an `ENVIRONMENT` allow-list check mirroring `/auth/dev-bypass`'s pattern (fail closed outside `local`/`development`/`test`/`ci`), plus a `--yes` flag or interactive confirmation naming the target host/database before truncating. Consider also refusing to run if the resolved host is not `localhost`/`127.0.0.1`/a container-network hostname.
- Not previously caught: AF-03 (state.json `agent_flags[]`) triaged a different concern (fixture determinism) on the same file and was rejected on that basis; the operational-safety gap was never raised or triaged by code review or implementation.

### F-SEC-2 — Org-singleton `ON CONFLICT DO UPDATE` staleness window re-raised as a data-integrity control gap (already carry-forward `F-1-residual-risk`)

- Source: checklist/data (integrity, not confidentiality)
- Severity: Medium
- Files: `services/api/app/services/rollup_rebuild.py:575-666` (`_upsert_org_summary`, `_upsert_month_series`, `rebuild_org_rollups`)
- Assessment (per the specific ask to judge this independently of code review's F-1): code review correctly identified F-1 as a correctness/architecture gap (HIGH there, for integration-points reasons) — the `ON CONFLICT DO UPDATE` convergence claim only holds for a static `usage_events` read-set, not genuinely concurrent cross-program ingest. From a security lens this is a **data-integrity** issue (a stale aggregate can silently overwrite a fresher committed one, with no exception and no log signal) rather than a confidentiality or availability breach: no unauthorized party gains access to data, no privilege boundary is crossed, and the system self-heals on the next full re-derive (every rebuild call is a complete re-derivation). There is no attacker-controlled trigger — the race requires two legitimate, concurrently-authorized ingest callers, and the ingest-token auth boundary (`ingest-token-auth`, ING-01) is unaffected either way.
- Verdict on severity: Medium, not High/Critical, for a security-specific report — it is a silent-corruption risk on internal aggregate/reporting data (not PII, not auth state, not a financial ledger), already disclosed and accepted as residual risk in `DECISIONS.md` D-01 § Scope correction and tracked as `F-1-residual-risk` in `state.json` `pending_carry_forward[]`.
- Compliance tag: **none** — `F-1-residual-risk`'s `kind` is `finding` with no `hipaa`/`pci`/`sox`/`gdpr` tag, and the active governance profile is `standard` only. Per the carry-forward enforcement rule this does **not** independently force `BLOCKED` (that rule only fires for compliance-tagged carry-forward under an active overlay). It is recorded here as a security-dimension confirmation of an already-tracked item, not a new blocker.
- Fix: as already recorded — scope a `pg_advisory_xact_lock` around only the three org-scope write statements if a stronger read-then-write atomicity guarantee is wanted later; not a merge-blocker on its own.

## Low findings

### F-SEC-3 — Hardcoded statement/connect timeouts leave no operational lever to tighten bounds during an incident without a redeploy

- Source: stack-pattern/fastapi + `.claude/rules/performance-baseline.md` ("I/O has explicit timeouts")
- Severity: Low
- File: `services/api/app/core/db.py` (`_STATEMENT_TIMEOUT_MS = 5_000`, `_CONNECT_TIMEOUT_S = 10`)
- Assessment: as an availability/DoS control, 5000ms is well-reasoned and measured, not guessed — D-02 pins it against a measured worst-case single-statement duration of 97.9ms (~51x headroom), and it is deliberately set above `app/services/freshness.py`'s existing 3.0s call-site `asyncio.wait_for` so that tighter caller-side bound fires first (avoiding two competing exceptions for one slow query). This is a genuine improvement over the prior state (no engine-level timeout at all — an unbounded rebuild could previously hold a pooled connection indefinitely). The one residual risk: both values are module constants (D-03, deliberate — "properties of the schema and query shapes, not of a deployment"), so tightening the bound during a live incident (e.g. a runaway query pinning connections) requires a code change and redeploy rather than an env var flip. `_CONNECT_TIMEOUT_S = 10` is a reasonable, unremarkable connect bound.
- Fix: not blocking — D-03's rationale is sound and reversible at low cost ("a future story needing per-environment tuning can promote it to `Settings` then"). Worth revisiting only if an incident actually needs faster iteration than a deploy allows.
