### Answering the specific questions

1. **Is `main()`-only enforcement unbypassable?** Not absolutely — `_truncate_all()`/`_run()` remain importable module-level functions, so a hypothetical future caller that imports and calls them directly (rather than invoking the script via `main()`/CLI) would skip the guard. But there is no such caller today (grep above), and this repo has an explicit, tested precedent that `scripts/` holds CLI entry points, not an importable library surface: `test_mint_ingest_token.py` exercises `mint_ingest_token.py` exclusively via `subprocess.run(...)`, never by importing its functions. Given that precedent and the absence of any in-repo bypass, this is a defense-in-depth suggestion (assert inside `_truncate_all()` itself, not just `main()`), not a live gap — recorded as F-SEC-4 (Low).
2. **Does reading `settings.environment` introduce a new failure mode?** Yes, one worth naming: `Settings.environment` defaults to `"development"` (`app/core/config.py`), and `"development"` **is** a member of `NON_PRODUCTION_ENVIRONMENTS`. So an operator who never sets `ENVIRONMENT` at all gets a pass from layer 1 by coincidence of the default, not by an explicit check — layer 1 degrades to a no-op in exactly the scenario the original finding described ("developer exports `DATABASE_URL` for another task and forgets to unset it," typically without also exporting `ENVIRONMENT=production` on a local shell). I verified this directly: `ENVIRONMENT` unset still reaches layer 2 rather than layer 1 refusing anything. The finding is not fatal to the fix, because layer 2 is unconditional — `--yes` is required on every invocation regardless of what layer 1 decided, and it prints the exact destructive action before requiring assent — so the "forgot to unset `DATABASE_URL`" accident is still caught by layer 2 even when layer 1 silently passes. Recorded as F-SEC-5 (Low): document this reliance explicitly in the module docstring so a future reader doesn't assume layer 1 alone protects the unset-environment case.
3. **Is exit code 2 + stderr the right shape?** Yes — matches this repo's own established CLI-boundary idiom: `mint_ingest_token.py::_run` catches and returns an int rather than letting an exception surface (`# noqa: BLE001 — CLI boundary: any mint/usage failure must exit 1, print nothing to stdout`). Raising here would dump a Python traceback (file paths, internal call stack) to stderr for what is a deliberate, expected refusal — worse, not better. Using `2` instead of mint's `1` to distinguish "refused by a safety gate" from "generic runtime error" is a reasonable, self-consistent choice for this script. Not a finding.
4. **Any other destructive/sensitive operation round 1 did not reach?** None found. Re-audited the full `origin/main...HEAD` diff for other DELETE/TRUNCATE-shaped operations: `rollup_rebuild.py`'s `DELETE WHERE program_id = :pid` and the month-series `DELETE ... NOT IN (:computed_months)` are both pre-existing (BED-03) or org/program-scoped, unchanged in shape by this diff, and already covered by round 1's assessment (F-SEC-2). `conftest.py`'s new `four_program_concurrent_sessions` fixture runs only against the test-managed `migrated_db` (ephemeral Alembic-migrated test database per `pytest-patterns`), never the live Postgres on 5442. Migration 004 is additive-index-only with a symmetric `downgrade()`.
