## Manual OWASP + stack-pattern pass

### Input (OWASP A03)

- `range` (query param) — validated ahead of the handler body by `validate_range` (dependency),
  which runs before RBAC because FastAPI resolves `Depends()` before executing the handler;
  invalid values 400 with a fixed `invalid_range` message and no echo of the rejected value
  into the response body (`app/dependencies/range.py:45-64`).
- `range` in warning logs is capped at 64 chars via `_capped_rejected_value` with an explicit
  `...<truncated>` marker (`app/dependencies/range.py:37-42`) — bounds hostile input size and
  keeps `security-baseline`'s "no unbounded user content in logs" invariant intact.
- `user_id` (path param) — used exclusively as a SQLAlchemy bind parameter in `.where(col ==
  user_id)` (three call sites in `personal_usage.py`). No string concatenation into SQL, no
  f-string interpolation of SQL. Confirmed by inspection.
- No file upload, no shell exec, no `eval`/`exec`. **No findings.**

### Authentication and authorization (OWASP A01)

- `get_current_user` (`Depends`) supplies `CurrentUser`; every route hit is authenticated
  before the handler body runs.
- **Own-data scoping (task focus):** `individual_usage_visibility(current_user, user_id)`
  is called before ANY DB read (`api/personal_usage.py:77`, ahead of the three fetch calls).
  Its logic (`app/core/rbac.py:116-142`): `return None` when `target_user_id ==
  current_user.user_id` (self path, no persona resolution); otherwise resolve persona and
  allow only `persona == "cio"`; every other combination raises `HTTPException(403)` after
  logging `individual_view_denied`. **Cross-user access is impossible without the `cio`
  persona.** Verified by re-reading `rbac.py:116-142` and the RBAC unit tests referenced in
  REVIEW.md.
- **No cross-user leakage (task focus):** each of the three query functions
  (`fetch_card_totals`, `fetch_daily_token_series`, `fetch_commands_breakdown`) takes the
  same validated `user_id` and filters `.where(UserSessions.user_id == user_id)` /
  `.where(UsageEvent.user == user_id)` respectively. No JOIN across users, no fallback to
  a broader scope on empty rows (`SUM` NULL → coerced to 0 in the same user's row set),
  no leakage vector. **Verified by direct read of `app/services/personal_usage.py`.**
- Denial response is a bare `HTTPException(status_code=403)` with no data body — routed
  through `app/core/errors.py` to `{"error": {"code": "http_403", "message": "Forbidden",
  "details": null}}`. No user, program, or session identifier leaks in the error path.
- **No findings.**

### Data (OWASP A02/A04)

- **PII handling in usage series (task focus):** the response envelope is aggregate counts
  and pre-formatted display strings (see `app/schemas/personal_usage.py`): card values,
  daily token totals, command counts. No `email`, `phone`, `ssn`, IP, or other PII field is
  read or emitted. `user_id` is opaque (an OIDC subject-style string), only echoed back to
  the requesting user's own path and never fanned out to a third party.
- Structured logs (`_log_event` / `logger.warning`) carry `user_id`, `target_user_id`, and
  route path — opaque identifiers only; no PII, no secrets.
- Response validated via Pydantic `response_model=PersonalUsageResponse` on the router, which
  strips any accidentally-added fields at serialization — enforces schema-shape as the wire
  contract.
- **No findings.**
