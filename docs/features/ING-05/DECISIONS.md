# ING-05 — Decisions

Decision log for the Copilot Chat activity-hook bridge. Header slugs (`blast:` / `rev:` / `adr:`) are machine-greppable per the `decide` skill. PLAN.md §1 is a one-line pointer to this file — decisions are not duplicated there.

### D-01: `JOURNAL_CODEC_VERSION = "1"` pin + unknown-kind skip-and-log-once policy · blast:feature · rev:mechanical · adr:—

**Context**: VS Code Copilot Chat's chat-session JSONL journal is a reverse-engineered, undocumented Microsoft storage format (research risk R-01 / R-04). The shipped `copilot-activity.mjs` handles kinds `0` (snapshot), `1` (set), `2` (push). A future Copilot / VS Code release can introduce a new numeric kind without any deprecation warning, and today's replayer would silently branch-drop the record — worse, an unexpected shape could throw inside `setAtPath` / `pushAtPath` and abort the whole batch (all valid rows for that session-end lost). The hook has one shot per `sessionEnd`; retry is forbidden by AC-2, so a batch-abort turns into a permanently missing row on the dashboard.

**Decision**: `copilot-activity.mjs` declares a module-level `const JOURNAL_CODEC_VERSION = "1";` immediately below the file header. The known-kind set is `{0, 1, 2}` literal; any other numeric or string `kind` value is (a) silently skipped for the purpose of row assembly (no exception, no `pushAtPath` call), (b) logged exactly once per session-end to `docs/activity/.mcp-push.log` as `{"event":"journal_codec_unknown_kind","kind":<value>,"codec_version":"1","ts":<iso>}`, and (c) does NOT count as a rejection in any downstream metric. Rows for the surrounding valid kinds still emit. The constant makes any future schema break traceable via a single grep. `rev:mechanical` — bumping the codec version and adding a new kind branch is a one-file edit; no data migrated under the choice. Not promoted — the choice lives entirely inside one hook file.

### D-02: MCP push single-attempt discipline · blast:service · rev:mechanical · adr:—

**Context**: AC-2 makes fire-and-forget contractual: `copilot-activity.mjs` spawns `harness-mcp-push.mjs` detached and returns without waiting. AC-5 requires "push failure never surfaces as an error to the Copilot Chat hook". If `harness-mcp-push.mjs` retried on timeout / non-2xx / network error, the detached child's wall-clock would extend past the Copilot Chat `Stop` event window; a stalled MCP server would keep the child alive across the user's next command, and a user-visible "stuck Copilot Chat" would follow. Retry logic here is not a robustness feature — it is a direct violation of AC-2. Research resolution C-4 already pinned the policy to "single attempt, no retry"; this entry records why the entire retry primitive is forbidden inside the hook, not merely bounded.

**Decision**: `harness-mcp-push.mjs` runs each of the four MCP RPC calls (`initialize`, `notifications/initialized`, `tools/call push_activity`, `DELETE`) as a SINGLE `fetch()` attempt bounded by one `AbortController` with `setTimeout(controller.abort, TIMEOUT_MS)` where `TIMEOUT_MS = 10_000` (reduced from the drifted `15_000` in the current draft). No retry loop, no exponential backoff, no jitter — the primitives are absent from the file. On timeout / non-2xx / network error, the script writes exactly one summary line to `.mcp-push.log`, calls `process.exit(0)`, and never re-attempts. `rev:mechanical` — re-introducing retry later is a code addition, not a data migration; the row for the missed session-end is permanently lost, and that trade-off is explicit in the fire-and-forget contract. Not promoted — the choice binds only this one script; upstream MCP tool (ING-04) already carries its own bounded 3-attempt retry over network failures for its own POST to the backend (D-05 of ING-04), so at-least-once semantics live one hop upstream where they belong.

### D-03: `program_id` sourcing precedence: `HARNESS_PROGRAM_ID` env → `.harness/program.yaml → program_id` (fallback legacy key `programId`) · blast:data · rev:mechanical · adr:ADR-0015

**Context**: `services/api/app/schemas/ingest_files.py::ActivityRowIn` declares `program_id: str = Field(...)` — **required**, and the service layer additionally enforces envelope↔row match, emitting `program_id_mismatch` on drift. During ING-04's live E2E (2026-09-14, PR #323, commit `7e2b8c6`), 141 rows were rejected with `missing_required_field` because the shipped `copilot-activity.mjs` writes rows to `activity.jsonl` with no `program_id` field. The MCP tool `push_activity` (frozen contract, ING-04) does not patch per-row `program_id` — it sends the envelope `program_id` alongside a rows array whose rows are expected to already carry one. Ambiguity in the shipped hook (env var read at push time only, no row-level write) is the exact cause of the 141× regression. Two independent sources exist locally: `HARNESS_PROGRAM_ID` env (deployment-time override, matches ING-04's env-var pattern) and `.harness/program.yaml` (committed, single source of truth per ING-04 D-04). A third option — silently defaulting to a placeholder like `unknown` — would trip `program_id_mismatch` at the envelope check and produce the same 141× rejection under a different reason code.

**Decision**: `copilot-activity.mjs` populates `program_id` on every emitted row at row-assembly time (BEFORE the NDJSON append/upsert). Resolution order: (1) `process.env.HARNESS_PROGRAM_ID` when non-empty; (2) parse `<workspace_root>/.harness/program.yaml` and read top-level `program_id`, falling back to the legacy key `programId` when only that is present; (3) if neither source resolves, the hook writes `{"event":"program_id_unresolved","ts":<iso>}` to `.mcp-push.log` and SKIPS the NDJSON append for that session-end — NO row with an empty or placeholder `program_id` is ever written. Promoted to `docs/adr/0015-program-id-sourcing-precedence.md` because it touches durable-state alignment (`blast:data` — the row's PK is `(program_id, session_id, cmd_ts)` per `usage_events` unique constraint; a wrong precedence corrupts every downstream aggregation the dashboard shows) and downstream tooling (a future harness-side or Claude-Code-side hook) must bind against the same precedence to avoid re-introducing the 141× regression. `rev:mechanical` — the precedence is a two-line edit in `copilot-activity.mjs`, no data migrated under the choice; but the ADR captures the rationale so the next story reading `.harness/program.yaml` does not silently reverse the order.

### D-04: Test-case cap = 3, uncovered IDs gap accepted (7 IDs, exercised by manual E2E per AC-5) · blast:feature · rev:mechanical · adr:—

**Context**: The Product Gate (2026-09-15) approved a deliberate 3-TC cap on `docs/test-cases/ING-05.json` (tracker keys #324 / #325 / #326) covering FR-1, FR-5, and AC-5. Seven ids remain uncovered by automated TCs — `AC-1, AC-3, AC-4, FR-2, FR-3, FR-4, NFR-security` — and are recorded as `coverage_audit.uncovered[]` in the test-case JSON. The alternative — writing seven more `node:test` TCs to hit every uncovered id — is technically feasible but delivers marginal value: (i) AC-3 / AC-4 are protocol constants (URL default, RPC sequence order) whose regression would show up as a total ingest outage detected by the manual E2E's row-visibility check; (ii) FR-2 / FR-3 / FR-4 are covered inline as fixture assertions inside `copilot-activity.test.mjs` (§ 7 below) even though the JSON audit does not credit them to a distinct TC id; (iii) NFR-security is a code-review-tier assertion (loopback default constant, no bearer read) that a runtime TC cannot prove more strongly than a grep. AC-5's Manual entry in `docs/stories/ING-05.md` § Test mapping already binds the uncovered ids to the live-run walkthrough — CI is `none` per `CLAUDE.md`, so a Copilot Chat lifecycle event cannot be simulated by automation anyway.

**Decision**: Keep the 3-TC cap. Do NOT author further automated TCs for the 7 uncovered ids. Cover them via inline fixture assertions inside the two `node:test` files (T-04 exercises FR-2 unknown-kind, FR-3 cache-token literal, FR-4 feature parse parametrised table; T-05 exercises AC-3 RPC sequence order via fetch-stub call-order capture and AC-4 default URL constant) PLUS the manual E2E walkthrough documented in `docs/how-to/copilot-chat-setup.md § Troubleshooting → Manual E2E walkthrough` (T-08). `rev:mechanical` — adding TCs later is a JSON-append edit; no data migrated under the choice. Not promoted — the gap is a story-local scoping call, not a cross-story precedent.
