## Manual OWASP checklist + stack-pattern pass

### 1. Identity data exposure — CLEAR

- `GET /api/me` backend contract (`services/api/app/schemas/me.py`) is `MeResponse(name: str|None, persona: str)` with `model_config = ConfigDict(extra="forbid")` — a runtime guarantee, not just convention; no `email`/`groups`/`programs`/`jobTitle` can ever be serialized.
- `services/api/app/api/me.py::get_me` constructs the response from `current_user.name` and `persona_resolver.resolve(...)` verbatim — no additional field assembled.
- Frontend `meApi.ts::fetchMe` types the response as `MeData {name, persona}` and performs no other parsing; `composeSignedInUser.ts` derives `jobTitle` **only** from `formatPersonaTag(persona).jobTitle` — an internal static map (`PERSONA_DISPLAY`), never from any field on the `me` argument. A unit test (`composeSignedInUser.test.ts`, added in this diff, "PGD-07-TC-C1") explicitly injects a decoy `jobTitle: "DECOY TITLE"` key on the input and asserts it never reaches the output (`expect(JSON.stringify(result)).not.toContain("DECOY TITLE")`).
- No other identity source exists in the diff: no client-side JWT decode, no second identity endpoint, no server-prop spillage of the full session object. `page.tsx` passes only `persona` (string) and `signedInUser` (`{name, jobTitle}`) as props into the Client Component `ProgramDetailView`.
- Conclusion: only `name`+`persona`-derived `jobTitle` reach client JS / rendered HTML. No PII beyond what `/api/me` contractually returns.

### 2. Token handling (ADR-0008) — CLEAR

- `tokenStore.ts` (`accessToken`/`refreshToken`/`dashboard_session` cookie) imports `next/headers` — server-only; not importable from a `"use client"` module (Next.js enforces this at build time).
- `page.tsx` (Server Component) calls `callWithAuth(...)` to fetch both `programDetail` and `meResult`, but only ever forwards the derived `persona`/`signedInUser` props to `ProgramDetailView` — never `accessToken`, `refreshToken`, or the raw `MeData`/`ProgramDetailResult` token fields (there are none in either payload).
- `app/logout/route.ts` reads the session server-side (`readSession()`), forwards the access token only as an `Authorization` header in a server-to-server `fetch` to FastAPI, and never returns the token value to the browser (only a `302` redirect or a generic `Sign-out is unavailable.` text body on failure).
- Sign-out control in `PersonaDashboardShell.tsx` is a zero-JS `<form action="/logout" method="get">` — no token, no handler, no client JS touches auth state at all on this surface.
- Conclusion: no access token, refresh token, or cookie value reaches client JS, a serialized prop, a `data-` attribute, or the DOM anywhere in this diff.

### 3. XSS — CLEAR

- SAST grep confirms no `dangerouslySetInnerHTML`, `innerHTML=`, or `document.write` in the diff.
- `signedInUser.name` (IdP-sourced) is rendered via plain JSX interpolation (`<div className={styles.name}>{signedInUser.name}</div>`) — React escapes by default.
- The only value written into an inline `style` prop is `personaColor`, sourced exclusively from the internal `PERSONA_DISPLAY` map's static hex strings (`formatPersonaTag(persona).color`) — never from `name` or any other user/IdP-controlled string. `persona` itself is validated against `VALID_PERSONAS`/`PersonaTagError` before any lookup; an unrecognized value never reaches the `style` prop, it throws and is caught to a neutral fallback.
- Conclusion: no XSS sink present; identity values pass through only text-node interpolation.

### 4. Auth-state handling — CLEAR

- Both `fetchProgramDetail` and `fetchMe` are wrapped in the SAME `try/catch` via `Promise.all` inside `page.tsx`; a `SessionExpiredError` from either call triggers the identical `redirect("/login")`. This is a deliberate, documented coordination (Condition C-4) rather than each call racing to redirect independently.
- A non-fatal `/api/me` failure (isolated 401/403 that survives its own retry, i.e. `meResult.status !== "ok"`) does **not** redirect and does **not** render a partial identity — `persona` falls back to the `PERSONA_RESOLUTION_ERROR` sentinel, `signedInUser` stays `undefined`, and `PersonaDashboardShell` renders the neutral "Persona unavailable" badge + `aria-live="assertive"` announcement (AC-5) rather than any name/avatar. This does not leak whether a user "exists" — it's the same generic badge regardless of cause.
- `/login` is the branded page per README; `redirect("/login")` behavior is unchanged from the pre-existing `SessionExpiredError` pattern this story reuses verbatim.
- Conclusion: expired/unauthenticated sessions fail closed to `/login`; a persona-only resolution failure degrades to a neutral, non-identifying badge — never a partial identity leak.

### 5. Persona-driven rendering — CLEAR

- `PersonaDashboardShell.tsx`'s own docstring and structure confirm: persona branching selects only **presentation** (tag/subtitle/color/jobTitle text, and which header variant mounts) — it performs zero authorization decisions. No route/data access is gated by a client-read `persona` value anywhere in this diff; `program-detail` data comes from `fetchProgramDetail`, gated server-side by the bearer token via `callWithAuth`, independent of persona.
- The added AF-01 guard (`personaColor === null && program === undefined && pageTitle === undefined`) only decides whether to show a neutral badge — it does not hide or reveal any sensitive data, and is mutually exclusive by construction with the other two header-region branches (verified structurally and by the existing regression suite, per REVIEW.md).
- Conclusion: persona-driven rendering here is presentation-only, consistent with `.claude/rules/security-baseline.md`'s "client-side checks are not authorization" principle — no violation found.
