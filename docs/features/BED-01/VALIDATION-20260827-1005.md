**2. Is the new constraint check real, or does it pass vacuously? Does the parser silently skip real entries?**
Read `_parse_fixture_constraints` (`test_models.py:102-118`): regex `^(unique|index)\(\s*([^)]+?)\s*\)` anchored at string start. It skips exactly one class of entry by design — prose-only notes with no `unique(...)`/`index(...)` prefix (there is exactly one such entry in the whole fixture: `ingest_tokens`'s "no column stores the raw token..." note, which is a security assertion already covered by a separate test class, `TestIngestTokensNoRawTokenColumn`). Every other constraint entry across all 18 tables (18 `unique(...)`/`index(...)` strings, including multi-column ones like `unique(org_id, program_id, member_id, date)` and 5-entry lists like `usage_events`) matches the regex correctly — confirmed by the real 59/59 pass plus a direct mutation check below.

To directly rule out "parser skips everything" (the exact failure mode the instructions asked me to check): I monkeypatched `_CONSTRAINT_PATTERN` in-process to a regex that matches nothing, then re-ran `_compare_constraints` for all 18 tables against the real models:

```
With all-skipping parser: 15 tables would FAIL, 3 would still pass
(expected: only the 3 tables with zero real constraints: system_metadata, persona_config, user_roles)
```

This is the correct, expected result — 15/18 tables carry a real `UniqueConstraint`/`Index` in `__table_args__` (verified by reading `app/models/rollup.py`, `governance.py`, `ingestion.py` directly), so an all-skipping parser would report `actual - expected` as non-empty ("unexpected unique/index not in fixture") and fail loudly on all 15. The real (non-broken) parser passes on all 18 only because it correctly recognizes the fixture's `unique(...)`/`index(...)` strings, not because it drops everything. Not vacuous.
