# BED-01 — Decisions

Decision log for the data model & Alembic migrations story. See `docs/features/BED-01/PLAN.md` §1 for the pointer from PLAN.md.

### D-01: SQLAlchemy 2.0 `DeclarativeBase` subclass, not legacy `declarative_base()` · blast:service · rev:mechanical · adr:—

**Context**: `app/models/base.py` needs one shared base class for all 18 models. SQLAlchemy 2.0 supports both the legacy `declarative_base()` factory (used by every pre-2.0 codebase) and the new `class Base(DeclarativeBase): pass` style with native `Mapped[]`/`mapped_column()` typing. `sqlalchemy>=2.0` is pinned (`services/api/pyproject.toml:12`) but no models module exists yet to set a precedent, and `postgres-patterns`/`alembic-patterns` skill bodies are unfilled scaffold TODOs (per research's Pattern Skills Status caveat) — there is no team convention to defer to, only the two framework-canonical options.
**Decision**: Use the SQLAlchemy 2.0-native `class Base(DeclarativeBase): pass` in `app/models/base.py`. All 18 models subclass it using `Mapped[...]` + `mapped_column(...)` annotations rather than the legacy `Column(...)` class-attribute style. This is the framework's own current best practice (declarative_base() is maintained for backward compat only) and gives mypy-checkable column types for free, matching `services/api/pyproject.toml`'s `[tool.mypy]` section already being wired in. Every downstream story's model additions (BED-02/03/04, AUTH-02/04, ING-01/02/03/07/08) inherit this same base.

### D-02: Models grouped into 3 domain files, not 1 flat file or 18 per-table files · blast:feature · rev:mechanical · adr:—

**Context**: 18 tables need to live somewhere under `app/models/`. A single `models.py` would exceed 500+ lines and mix unrelated concerns (rollups vs governance vs ingestion/auth); one file per table (18 files) fragments the small governance group (3 tables) unnecessarily and multiplies import boilerplate in `app/models/__init__.py`.
**Decision**: Group by the `db-schema` contract's own 3 named groups (`docs/requirements/data.md`): `app/models/rollup.py` (10 tables), `app/models/governance.py` (3 tables), `app/models/ingestion.py` (5 tables) — matching research's Implementation Planning Notes file layout exactly. `app/models/__init__.py` re-exports `Base` plus every model class so callers (migrations/env.py today; routers in later stories) import from `app.models` without knowing the internal grouping.

### D-03: JSON-typed columns use `postgresql.JSONB`, not plain `sqlalchemy.JSON` · blast:data · rev:medium · adr:ADR-0003

**Context**: PRD §8.4's type-mapping rule allows either `JSON`/`JSONB` for Prisma `Json` fields (`program_summary.monthly_token_sparkline`, `usage_events.models`) — it does not pick one, and `BED-01-TC-13` explicitly accepts both. These two columns are read by 13 downstream stories' dashboard/chart code (`db-schema` `consumed_by` list in `docs/requirements/data.md`), so the encoding choice is a durable-schema decision with cross-story reach, not a private implementation detail of this story.
**Decision**: Use `sqlalchemy.dialects.postgresql.JSONB` for both columns. JSONB is Postgres-native binary storage — supports future GIN indexing/containment queries (`@>`, `?`) without a schema change, and is materially cheaper to query than text-based `JSON` at read time, which matches this story's read-heavy rollup access pattern. The write-time parse cost JSONB adds is irrelevant here since these columns are only written by the rollup-rebuild path (BED-03), not on any request-serving hot path (this story's NFR section already scopes out request-path latency). Promoted to `docs/adr/0003-json-columns-jsonb.md` because the choice's `blast:data` (touches durable schema consumed by 13 stories) triggers the `decide` skill's mandatory-promotion rule regardless of its `medium` reversibility.
