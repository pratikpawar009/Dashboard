## Manual OWASP checklist

### Input

- **SQL injection in aggregation queries** — every query in `rollup_rebuild.py`
  is built through SQLAlchemy Core (`select(...)`, `delete(...)`, `func.*`,
  `.where(Column == value)`, `func.date_trunc("day", UsageEvent.ts, "UTC")`,
  `func.to_char(..., "YYYY-MM")`, `pg_insert(model).values(row)`,
  `on_conflict_do_update(index_elements=[...], set_={...})`). All values arrive
  as bound parameters through the ORM's `_expression.BindParameter` machinery.
  No `text(...)`, no `.execute("SELECT ...")` string, no f-string carrying a
  SQL literal, no `%`-format on a statement string. The only string literals
  passed into SQL API are hardcoded column names / bucket units (`"day"`,
  `"month"`, `"UTC"`, `"YYYY-MM"`, `_ORG_ID = "org-1"`) — none derived from
  caller input.
- `db.py` builds the engine timeout via
  `f"-c statement_timeout={_STATEMENT_TIMEOUT_MS}"` — `_STATEMENT_TIMEOUT_MS`
  is a module-constant `int` literal (`5_000`), not settings/env-driven; the
  f-string can only ever produce `-c statement_timeout=5000`. Not a SQL
  injection surface.
- **No user-supplied input path** — `rebuild_program_rollups(session,
  program_id)` and `rebuild_org_rollups(session)` are internal service
  functions. REVIEW.md confirms via AST + grep that no router references
  either function today; DATA-DESIGN.md § 3 places authz enforcement on the
  future calling ingest routes (ING-02/ING-06, out of BED-03 scope). No shell,
  no filesystem, no deserialisation of untrusted input in the diff.

### Authentication and authorization

- No new endpoint added — no authn/authz surface to gate. `program_id`-bounded
  DELETEs (verified in REVIEW.md AC-4 test coverage) mean a caller with
  authority over program `P` cannot corrupt program `Q`'s rollup rows through
  this module even if a future caller mis-scopes; the SQL enforces the
  boundary independently of any caller-side check.

### Data

- **PII in logs** — the two `logger.info("rollup_rebuild_completed", extra={...})`
  call sites emit only: `scope`, `program_id`, `duration_ms`, `event_count`
  (program scope) plus `contention_wait_ms` (org scope). No `user`, `email`,
  `name`, `session_id`, or `cmd_ts` value is passed. Verified end-to-end

  aggregation `WHERE` / `GROUP BY` / `func.min(...)` clauses but never

- **PII in the persisted rollup rows** — `program_members.user_id`,

- **Encryption / retention** — no change (DATA-DESIGN.md § 4). Backups,
  key management, retention TTL are all inherited from BED-01's data
  classification and unchanged by this diff.

## Transaction / locking correctness (data integrity — CIA)

Explicitly called out in the assignment. Walked in depth:

- `_rebuild_transaction()` (rollup_rebuild.py:91-108) is the only transaction
  seam. It uses `session.begin()` when the session is idle (the shape from
  `get_db()`) and `begin_nested()` (a Postgres `SAVEPOINT`) when the caller
  already holds a transaction on the same session — the exact shape the
  idempotency-verification callers need (D-04/D-08). Either branch guarantees
  scope-atomic rollback (the second branch is proved by REVIEW.md's
  two-branch savepoint test).
- Program scope: every DELETE is `WHERE program_id = :pid` (7 explicit
  DELETE-by-`program_id` statements, rollup_rebuild.py:449-461). No blanket
  `DELETE FROM <table>` exists on any program-scoped table. Verified by
  reading the source directly.
- Org scope: `org_summary_rollup` uses `pg_insert(...).on_conflict_do_update(
  index_elements=["org_id"], set_={...})` — a race-free singleton update
  under Postgres row-level locking. `token_series` / `mau_series` use
  `DELETE ... WHERE org_id = :oid AND month NOT IN (:computed_months)` followed
  by `INSERT ... ON CONFLICT (org_id, month) DO UPDATE` — preserves the
  full-re-derive invariant and eliminates the race that would otherwise fire
  on `org_summary_rollup`'s `unique(org_id)` under AC-1's four-concurrent-program
  case.
- No advisory locks are taken, and none are required: DATA-DESIGN.md § 5's
  order-independence audit (proved in the module docstring) shows every org
  aggregate is a commutative reduction (`SUM`, `COUNT`, `COUNT(DISTINCT)`,
  `MIN`, `MAX`), so concurrent writers converge on the identical final row
  regardless of scan order.
- Engine timeouts: `_STATEMENT_TIMEOUT_MS = 5_000` and `_CONNECT_TIMEOUT_S =
  10` are applied at the engine level via `connect_args`. A hung statement
  cannot indefinitely hold a pooled connection — closes the
  `.claude/rules/performance-baseline.md` "explicit I/O timeout" requirement
  at the engine seam, replacing the previous unbounded default.

Integrity posture: **strong**. No data corruption vector introduced; the
race the shipped code had (blanket DELETE+INSERT vs `unique(org_id)`) is
actively closed by this rewrite.
