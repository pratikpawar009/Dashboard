## Scope verified

**1. `GET /api/overview/program-detail/{program_id}/team/{member_id}/usage` RBAC** (the highest-risk surface flagged):
- `member_in_program_visibility` (`services/api/app/core/rbac.py:144-193`) runs `program_visibility` first (open-aggregate, confirmed non-scoping — never reads `current_user.programs`, never branches on `program_id`), then requires `target_member_id == current_user.user_id` OR persona `cio`. A non-self, non-cio requester is denied 403 with no bypass found via route params, proxy, or `member_id`/`program_id` manipulation.
- Route handler (`services/api/app/api/overview.py:397-423`) calls the gate at line 415, **before** any of `fetch_card_totals`/`fetch_daily_token_series`/`fetch_commands_breakdown` (lines 419-421) — denial and data fetch are mutually exclusive by construction. Confirmed by test `test_denied_response_body_has_no_personal_usage_fields_tc13` (`services/api/tests/unit/test_program_team_member_usage_route.py:394-420`), which asserts the 403 body carries none of `cards`/`daily_tokens`/`commands` at any nesting depth.
- Denial logs `member_view_denied` (not `individual_view_denied`), fields `{user_id, program_id, target_member_id, outcome, timestamp}` only — no email, no name, no persona value on the denial path (`rbac.py:182-193`). Confirmed against `_EVENT_REQUIRED_FIELDS`/`_EVENT_OPTIONAL_FIELDS` allowlist enforcement (`rbac.py:315-326`), which raises `AssertionError` on any unrecognized field.
- Proxy chain: `apps/web/src/app/api/proxy/personal-usage/[user_id]/route.ts` is reused (confusingly, by URL path) as the popup's proxy, but its internal `fetchMemberUsage()` (lines 116-155) correctly targets the backend's `/team/{member_id}/usage` sibling route — **not** SHP-02's `/api/personal-usage/{user_id}` route and its `individual_usage_visibility` gate. No cross-gate confusion found. `program_id` is a required query param; missing → 400 before any upstream call (lines 77-79). 403 is mapped to `{error:"denied"}` with no upstream body forwarded (lines 91-92) — no partial/malformed body leaks on the denial path. No response caching is applied at the proxy layer (each request re-invokes the upstream call scoped to the resolved `program_id`/`member_id`).
- Conclusion: `program_visibility`'s open-aggregate model is correctly treated as a non-scoping veto gate throughout — nothing in the new code relies on it for membership scoping. The self-or-cio branch is the sole and sufficient access control for this endpoint.

**2. PII/identity exposure (`member_id` = email)**:

PGD-05 does not introduce a new class of exposure — it extends the same pattern to a program-scoped audience (any authenticated session, since `program_visibility` doesn't scope by membership) rather than narrowing it.
- No new logging of `member_id`/email/name was found (grep of all new `logger.info`/`logger.error` calls in the diff — only `program_id`, `range`, `status`, `latency_ms` appear; `member_id`/`member_name` never logged).

- `member_id`/email is not `encodeURIComponent`-escaped when interpolated into the fetch URL path segment in `memberUsageApi.client.ts:34` and the proxy's upstream call (`route.ts:134`) — see Low finding L-001 below. ## Medium findings

### F-001 — `GET /program-detail/{program_id}/team` has no pagination bound

- Source: checklist/input (performance-baseline overlap, `.claude/rules/performance-baseline.md`: "Pagination on every list endpoint (default page size, max page size)")
- Severity: Medium
- File: `services/api/app/api/overview.py:349-390`, `services/api/app/services/program_team.py:35-94`
- Issue: `fetch_program_team()` returns every active-in-range roster member with no `offset`/`limit`. Sibling `/releases` paginates (`_releases_offset_limit`, `overview.py:237-245`, default `limit=20` clamped to `MAX_OFFSET_LIMIT`); `/team` does not. REQUIREMENTS.md's NFR only bounds query *count* (exactly two SELECTs, satisfied) — it does not address response row-count. A large program's roster returns an unbounded result set to any authenticated session (since `program_visibility` doesn't scope by membership), which is both a performance-baseline violation and a mild amplification of the PII exposure noted above (more rows of email+name per unscoped call).
- Fix: add `offset`/`limit` `Query()` params to `get_program_team`, matching `_releases_offset_limit`'s pattern, or document an explicit accepted-risk ADR if the team-table's realistic roster sizes make this a non-issue (e.g., a hard cap already exists upstream on roster ingestion).

## Low findings

### L-001 — `member_id` (email) not percent-encoded when built into a URL path segment

- Source: stack-pattern/nextjs
- Severity: Low
- File: `apps/web/src/lib/memberUsageApi.client.ts:34`, `apps/web/src/app/api/proxy/personal-usage/[user_id]/route.ts:134`
- Issue: `` `/api/proxy/personal-usage/${memberId}?...` `` and the upstream `` `.../team/${memberId}/usage` `` build URLs via raw template interpolation, no `encodeURIComponent`. An email containing `+`, `%`, or other reserved characters could be misrouted or misinterpreted. Pre-existing pattern across every fetcher in this codebase (not a PGD-05 regression) — carried forward as a codebase-wide observation, not a blocking defect.
- Fix: wrap path-segment identifiers in `encodeURIComponent()` codebase-wide; out of scope for a single-story surgical fix per `.claude/rules/surgical-changes.md`.

### L-002 — R-003 (`program_visibility` open-aggregate model) inherited, not newly introduced

- Source: compliance/architecture carry-forward (informational, not blocking)
- Severity: Low
- File: `services/api/app/core/rbac.py:100-113`, `services/api/app/api/overview.py:374` (`get_program_team`)
- Issue: `/team`'s list-level gate is the same open-aggregate `program_visibility` veto used by every PGD sibling route (already accepted at AUTH-03's security review, R-003 stays explicitly OPEN at the parent-PRD level per `docs/features/AUTH-03/DECISIONS.md` D-03). PGD-05 does not tighten or worsen this; it correctly does NOT rely on it for the one PII-sensitive per-member endpoint (that endpoint adds `member_in_program_visibility`'s self-or-cio check on top). Re-flagged here per R-003's own standing instruction ("flagged for `/arh-security-review` re-examination" on every review), not as a new PGD-05 defect.
- Fix: none required for PGD-05. R-003 remains a program-level (PRD) decision to revisit, tracked outside this story.
