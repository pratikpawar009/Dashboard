## Manual OWASP checklist + stack-pattern pass

**A01 Broken access control / IDOR (route: `GET /api/personal-usage/{user_id}/sessions`)**
- `individual_usage_visibility(current_user, user_id)` is called as the bare first statement in `get_personal_sessions`, before `fetch_sessions_paginated` or any DB access — verified by reading the route body; no code path reaches the service call without the gate having already returned.
- Self path (`target_user_id == current_user.user_id`) short-circuits with no persona resolution; non-self path resolves persona and requires `cio`, else raises `HTTPException(403)` with no body/data — confirmed in `app/core/rbac.py:116-141` (unchanged, pre-existing gate; SHP-03 only calls it).
- `user_id` is a FastAPI path parameter — the router match consumes the full literal path segment; no casing/encoding bypass is possible against a `str` path param compared for equality, and the gate does not attempt any lookup that path traversal or encoding tricks could subvert (it's a straight string comparison against `current_user.user_id`, not a filesystem or query-string based check).
- Denial path carries zero response fields — confirmed against `PersonalSessionsResponse`'s `extra="forbid"` schema not being constructed at all on the 403 branch (exception raised before the return statement executes).
- Test file `test_personal_sessions_route.py` structurally asserts denial-first ordering and a positive control for `individual_view_denied` firing on cross-user access while staying silent on self-access, guarding against a regression where the gate is silently skipped.

Verdict: no IDOR. Correctly implemented per the existing gate contract.

**Information disclosure — denial path**
- 403 responses carry no `items`/`total`/schema hints (frontend proxy explicitly returns `{error:"denied"}`, discarding the upstream body on the `denied` branch; backend never serializes `PersonalSessionsResponse` on the exception path).
- `individual_view_denied` logging is denial-only and logs only `user_id`/`target_user_id` (opaque identifiers) — no session content, no new PII surfaces introduced by SHP-03's call site.

**Injection** — confirmed above; parameterized ORM queries throughout, no raw SQL.

**Proxy / ADR-0008 token handling (`apps/web/src/app/api/proxy/personal-sessions/[user_id]/route.ts`)**
- Access token is resolved server-side via `callWithAuth`/`tokenStore` and attached only to the outbound FastAPI request; it is never included in the `NextResponse.json(...)` body on any branch (`ok`/`denied`/`unauthorized`/`error`) and never set as a response header. Client JS cannot observe it.
- Upstream 401/403 are preserved as distinct statuses (403 → `denied`, 401 → `session_expired`), not collapsed into a generic error — matches ADR-0008 intent.
- `page`/`page_size` are forwarded via `URLSearchParams` (properly encoded) and are not re-clamped in the proxy — this is safe because the backend's shared `get_page_params` dependency (`app/dependencies/pagination.py`) is the sole clamp authority and cannot be bypassed by any value the proxy forwards (clamps to `MAX_PAGE_SIZE=100` server-side regardless of what the client sends).

**Low finding — L-01: unencoded `user_id` in proxy upstream URL template**
- `apps/web/src/app/api/proxy/personal-sessions/[user_id]/route.ts:111` and `personalSessionsApi.ts:55` interpolate `user_id` directly into the upstream FastAPI URL (`` `${getApiBaseUrl()}/api/personal-usage/${userId}/sessions...` ``) without `encodeURIComponent`, unlike the query params which go through `URLSearchParams`.
- Not exploitable for path traversal or request-line injection today: `user_id` arrives via Next.js's `[user_id]` dynamic segment, which the framework already URL-decodes and cannot deliver a raw `/`-containing value into `params.user_id` for a single dynamic segment; a value containing other reserved characters (`?`, `#`) would malform the upstream URL but cannot reach a different upstream route class the RBAC gate wasn't designed for, since FastAPI's own `{user_id}` path param on the receiving end has the same shape constraints.
- Raised as Low (not blocking) because it is a codebase-wide pre-existing pattern — the sibling `apps/web/src/app/api/proxy/personal-usage/[user_id]/route.ts` (unedited by this story) has the identical unencoded interpolation, and SHP-03 correctly mirrored the existing pattern per `.claude/rules/pattern-consistency.md` rather than introducing a new one. Fix belongs to a dedicated cleanup across both proxies, not a silent unilateral change in this story's diff.
- Fix: wrap `userId` in `encodeURIComponent()` at both call sites (this proxy and its sibling) in a follow-up.

**Stack-pattern pass (fastapi/pydantic/nextjs)**
- `fastapi`: `Depends()`-based auth via `get_current_user` + `individual_usage_visibility` — consistent with existing idiom; `response_model=PersonalSessionsResponse` strips nothing sensitive since no sensitive field exists on the model.
- `pydantic`: `PersonalSessionEntry`/`PersonalSessionsResponse` both use `extra="forbid"` (session schema) locking the field set — matches the `ArtifactItem` precedent cited in the schema docstring.
- `nextjs`: no server action here (plain Route Handler); no secret in a client component (`SessionsTable.tsx` is `"use client"` and receives only pre-formatted display strings, no token, no API base URL construction). No CSP-relevant `unsafe-inline` introduced.

**Low finding — L-02: `title` renders the user's own identifier, not a session title (privacy angle on F-03)**
- Already flagged non-security in FLAGS.md F-03: `user_sessions.name` (rendered as `title`) is set to the raw `user` identifier (email) by the rollup producer, not a real session title.
- Security framing: this is not a cross-user PII leak — the endpoint is gated self-or-cio, so a self-viewer already knows their own email, and a `cio` viewer already has org-wide visibility into user identifiers via other endpoints (`/team`, `/program-detail`). No new exposure surface. Logged here as Low/informational only because it repeats a user-identifying string once per row rather than a single header field, which is a UX/data-quality issue (per F-03), not a new confidentiality boundary violation.
