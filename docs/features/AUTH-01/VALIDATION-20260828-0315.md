## Round-2 focus: independent re-verification of the fix

Per the invocation, ran a standalone script (`create_app(settings_override=...)`, own freshly-generated RSA keypair, own JWKS mock via `respx`, no reuse of the pytest suite's fixtures/mocks) to independently confirm every claim in REVIEW.md F-1's fix, in addition to the 296-test pytest re-run:

**1. Fix confirmation (wrong-iss / wrong-aud rejected; correct still accepted):**
- Correctly-signed token, `iss="https://evil.example.com/realms/Other"` → **401** (`invalid_token`)
- Correctly-signed token, `aud="some-other-client"` → **401** (`invalid_token`)
- Correctly-signed token, correct `iss`/`aud` → **200**, `{"user_id": "verify-user", "role": "qa"}`
- Confirms rejection comes from claim validation, not signature failure: the JWKS mock served the real signing key in every case, so signature verification genuinely succeeded before `claims.validate()` rejected the mismatched `iss`/`aud`.

**2. Dev-bypass regression (D-08 intact):**
- `POST /auth/dev-bypass` under `ENVIRONMENT=development` → 200, token issued.
- That token presented to a fresh `Depends(get_current_user)`-guarded route on the SAME app → **200**, `role="qa"`, matching the dev-bypass overrides.
- The identical token presented to a **separately-constructed** `ENVIRONMENT=production` app's guarded route → **401** (dev kid never resolves to a signing key when `dev_bypass_enabled=False`).
- `POST /auth/dev-bypass` on the production app → **404** (router never registered).
- TC-40 and TC-08 also re-ran green in the pytest suite (see grep output below) — corroborates this independent check rather than replacing it.

**3. Unconfigured-OIDC case:**
- App built with `environment="development"` and no `oidc_issuer`/`oidc_client_id`/`oidc_client_secret` → boots cleanly.
- `GET /auth/login` → **501**; `POST /auth/refresh` → **501**.
- `POST /auth/dev-bypass` → **200**, and that token authenticates on a guarded route → **200** (dev-bypass has no dependency on OIDC config).
- A "real" (non-dev-bypass) correctly-signed token, same freshly-generated keypair as above → **401**. Confirmed root cause: with no `oidc_issuer`, `JwksCache._fetch_and_cache` returns immediately without fetching, so any non-dev `kid` is permanently unrecognized and 401s via the existing fetch-once-then-fail path — `_claims_options` is never even reached for it. No real (non-dev) token can verify in this state.
