## OWASP checklist walk-through

### Input
Trust-boundary validation via Pydantic (`DevBypassRequest`, `_RefreshRequest`) and typed FastAPI query params (`code`, `state`, `error` in `/auth/callback`). `state` is deliberately `str | None` so a missing value returns 400 `invalid_state` via the standard envelope rather than FastAPI's 422 (`app/auth/oidc.py:270-287`). No SQL is built here. **No new finding.**

### Authentication and authorization
- Every protected route reaches `Depends(get_current_user)`, which verifies signature via the per-app `JwksCache` (`app/auth/jwks.py:120-160`) then calls `claims.validate()` with `_claims_options(kid, settings)` — the F-1 fix now enforces `iss`/`aud` as `essential: True` claims_options (`app/core/auth.py:195-234`), verified against the installed `authlib==0.15.6` source: `MissingClaimError` fires for absent claims, `InvalidClaimError` for wrong values. No route bypasses this dependency.
- Dev-bypass router registration is gated at `create_app()` by the fail-closed allow-list `NON_PRODUCTION_ENVIRONMENTS = {local, development, dev, test, ci}` (`app/core/config.py:16-19`, `app/main.py:120-121`). The token itself carries a reserved `kid = "dev-bypass-local"` that `JwksCache.get_signing_key` only resolves when `settings.dev_bypass_enabled` — verified there is no second trust path in a production deployment.
- OAuth `state` is issued and verified server-side via `OAuthStateStore` (`app/auth/state_store.py`) — single-use `pop`, 300s TTL, 10 000-entry bounded cap with oldest-eviction. PKCE (S256) is sent unconditionally, closing the authorization-code-injection gap the resolved carry-forward `AF-07-oauth-state-not-verified` named.
- Sessions are bearer-only, stateless; `/auth/logout` never touches a server session — a shipped design choice recorded as accepted risk in the ADR-0004 stanza.
- No new authz layer added; `role`/`programs` derive exclusively from verified claims or the `program_roster` DB query, never from client headers (durable regression comment at `app/core/auth.py:405-427` explicitly enumerates the two rejected widenings).

**No new finding.** F-02 (rate limiting on `/auth/*`) is cross-referenced below.

### Data
- `email` (PII) is embedded in issued tokens and returned to the caller, never emitted to logs. `_log_dashboard_login`/`_log_dashboard_logout` log only the verified `sub` claim as `user_id` (`app/auth/oidc.py:178-217`).
- Dev-bypass RSA private key is process-local, ephemeral, generated lazily under `threading.Lock`, and never persisted or logged (`app/auth/jwks.py:65-91`).
- `TokenResponse` uses `extra="ignore"` (Pydantic default) — Keycloak's `id_token`, `token_type`, `session_state`, etc. are dropped, so response shape is exactly `{access_token, refresh_token, expires_in}` (TC-16).
- `client_secret` is sourced from `Settings.oidc_client_secret` (env-driven), only ever placed into the outbound POST form body to Keycloak's token endpoint (`app/auth/oidc.py:310-320`). Not logged; not echoed.
- OIDC error descriptions from the IdP are deliberately not echoed to the caller (`app/auth/oidc.py:295-298`) — only the enumerated `error` code lands in the log.

**No new finding.**

### Crypto
- RS256 (2048-bit RSA) via `authlib.jose` for dev-bypass; Keycloak-issued tokens use the realm's own signing keys, verified via JWKS.
- `secrets.token_urlsafe(32)` for `state` (~256 bits entropy) and `secrets.token_urlsafe(64)` for PKCE `code_verifier` (~512 bits, well above RFC 7636 § 4.1's 256-bit floor).
- `hashlib.sha256` for PKCE `code_challenge` (RFC-mandated).
- No homegrown crypto, no MD5/SHA1/DES/ECB anywhere in the diff.

**No new finding.**

### Dependencies
- New/tightened runtime declarations: `httpx>=0.27`, `authlib>=0.15,<1.0`, `pyyaml>=6.0`.
- `authlib` version pin (`0.15.6` resolved) is pre-1.0 as ADR-0004 acknowledges, but `pip-audit` reports no advisories against the resolved graph.
- No lockfile drift beyond the touched dependencies.

**No new finding.**

### Logs and errors
- All auth failure paths raise `HTTPException(401, "invalid_token")` — one generic detail (`_INVALID_TOKEN_DETAIL`) shared across missing-header, malformed-token, JWKS-miss, signature-fail, and claims-invalid, so callers cannot distinguish failure modes (`app/core/auth.py:52`, `:263-267`, `:285-288`).
- `app/core/errors.py` registers the three-handler envelope; no new error handler is introduced.
- **[Info-01]** `_log_dashboard_login` / `_log_dashboard_logout` decode the freshly-issued/received access token specifically to extract a `sub` for the audit log; on any decode failure they fall back to `user_id="unknown"` and still emit the event. This is the shape the REVIEW carry-forward F-04 targets — see cross-reference below.

## Findings

### Low

#### F-SEC-01 — `DevBypassRequest.email` accepts any string; caller-supplied value lands verbatim in a signed token

- Source: `stack-pattern/pydantic`
- Severity: **Low**
- File: `services/api/app/schemas/auth.py:22` (schema), `services/api/app/auth/dev_bypass.py:98-101` (embedded in `claims["email"]`)
- Issue: `email` is typed `str | None` rather than `EmailStr | None`; a caller can put arbitrary content (whitespace, control chars, an oversized string) into the claim, which is then signed and returned. Impact is bounded because (a) the route only registers when `ENVIRONMENT` is in the fail-closed allow-list (`local`/`development`/`dev`/`test`/`ci`) and (b) the token verifies only inside the same allow-listed process. There is no cross-tenant blast radius.
- Fix: switch to `EmailStr | None` (already pulling in `pydantic[email]` transitively via `pydantic-settings` is not present — would add `email-validator` as a direct dep), OR bound `email` with a `Field(..., max_length=254)` and a lightweight regex; document explicitly in the route docstring that dev-bypass is untrusted-in-prod-by-configuration.
- Rule: `pydantic-patterns § Security (stack-specific)` — "trust-boundary validation control"; overlaps `.claude/rules/security-baseline.md § Input`.
- Override: none.

### Info

#### F-SEC-02 — `pip-audit` not on `PATH` (development machine); depends on `uv tool run` invocation

- Source: `deps-scan/pip-audit`
- Severity: **Info** (`tool_missing` — Low per skill; not a blocker)
- Fix: pin `pip-audit` under `[dependency-groups].dev` in `services/api/pyproject.toml` OR add a `make audit` target driving `uv tool run --with pip-audit pip-audit --strict`, so CI (once wired) does not need to re-derive the invocation.
- Note: the scan itself succeeded (28 packages inspected, no advisories); this Info entry only records the tool-provisioning gap so it is fixed once, in the right place.

#### F-SEC-03 — `OAuthStateStore` is per-process in-memory; multi-replica deployments will 400 with `invalid_state` on cross-replica callbacks

- Source: `checklist/data` (availability-adjacent; not an authz gap)
- Severity: **Info** (documented residual limitation, not a defect for the single-replica target)
- File: `services/api/app/auth/state_store.py:22-30` (module docstring names the limitation), consumed at `app/auth/oidc.py:242-254`
- Issue: `create_app` constructs one `OAuthStateStore` per FastAPI instance; a `/auth/login` served by replica A and a `/auth/callback` served by replica B cannot correlate. This is called out in the module docstring; recorded here so it does not silently drift from documented behaviour.
- Fix: migration path is a shared backing store (Redis) when the API is scaled out. Track under a separate story before horizontal scale-out lands.
