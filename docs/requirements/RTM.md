- 2026-09-04 (OPEN QUESTION, best judgment applied) Login/callback hand-off mechanism: `/auth/callback` returns a JSON body directly to whoever calls it — never a redirect, never a `Set-Cookie` (README, session contract) — and README's Keycloak-client section pins the registered redirect URI to the API's own origin (`http://localhost:8000/auth/callback`), not a frontend URL. Taken literally, a raw browser navigation ends the OAuth dance by rendering JSON, never reaching the frontend's server. Best judgment (not settled by any of the three named sources, so not decided silently): AUTH-05 implements the exchange via Next.js Route Handlers — `/login` calls FastAPI's `GET /auth/login` server-to-server with `redirect: manual` and relays the captured Keycloak authorization URL to the browser; `/callback` is the actual browser-facing landing point and itself calls FastAPI's `/auth/callback` server-to-server (forwarding `code`/`state`) before setting the httpOnly cookie and redirecting the browser onward — never a client-side page parsing the callback response directly. This likely requires the Keycloak client to register the frontend's own callback URL as an additional valid redirect URI (an IdP/ops config change, not application code) — flagged under OPEN QUESTIONS for confirmation, since a different answer (e.g. keeping only the API-origin redirect URI and having FastAPI itself 302 onward, which would be a backend change out of this story's stated scope) changes AUTH-05's mechanism materially.

- 2026-09-04 (RESOLVED, supersedes the "Login/callback hand-off mechanism" open question above) CONFIRMED by user: frontend-callback + backend `redirect_uri` parameterization. Keycloak redirects the browser to a Next.js Route Handler on the frontend origin; that handler relays `code`/`state` server-to-server to FastAPI's existing `GET /auth/callback` (same query-param signature, no method/route change), gets the JSON `{access_token, refresh_token, expires_in}`, sets the httpOnly cookie, then 302s the browser onward — no client-side page ever parses the callback response. Verified against shipped code, not assumed: `services/api/app/auth/oidc.py::_resolve_redirect_uri` (D-11/AF-08) **already** reads `settings.oidc_redirect_uri` when set, used identically by both `/auth/login`'s authorization request and `/auth/callback`'s token exchange; the `Settings.oidc_redirect_uri` field (`config.py:55`) and a blank `OIDC_REDIRECT_URI=` line (`.env.example:30`) already ship under AUTH-01. **Correction to the initial framing**: no `services/api` source change is needed — this is a config value (set `OIDC_REDIRECT_URI` to the frontend's callback URL), not "a small backend change" to make it configuration-driven; that already happened.
