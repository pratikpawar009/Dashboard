## Decisions

- 2026-09-11 **Sign-in page and sign-out control added to EXISTING stories, not new ones — user direction, and a recorded deviation from the design source.** Two gaps surfaced while exercising the merged AUTH-07 build against a live Keycloak session: (1) the product owns no sign-in screen — `/login` is a Route Handler that server-redirects straight to the IdP, so a visitor never sees dashboard branding; and (2) a signed-in user has no way to sign out from the UI, because AUTH-07 AC-15 deliberately shipped `/logout` as route-only. Both were correct under the rules at the time: all six exports in the design source contain no sign-in screen and no sign-out affordance (verified by grep across every file, 2026-09-11), and `CLAUDE.md` requires raising such a gap rather than designing it. It was raised; the user decided both are required. **Placement, per the user's explicit instruction ("whatever story we have left add this requirement into that dont create next story"):** **both** requirements go to `OVW-05` — the sign-in page was initially placed in `AUTH-05` (which owns `/login`) and then moved, because `AUTH-05` is already at `phase: review` with shipped code and would have been reopened, whereas `OVW-05` is still `story-validated` and is the story queued to run; the sign-out control goes to `OVW-05` too, which already owns the signed-in identity block and already modifies `PersonaDashboardShell`, with `PGD-07` carrying a matching assertion so Program Detail inherits rather than forks it. `ARC-01`/`DEV-01`/`PMD-01`/`EMD-01` inherit the control by composing the same shell. Neither addition invents a new mechanism: the sign-out control targets AUTH-07's shipped `/logout` handler, and the sign-in page wraps AUTH-05's existing authorization-code flow. **Consequence to plan around:** consolidating both into `OVW-05` keeps every amended story in pre-plan state — `AUTH-05` is untouched in scope (it keeps only a Decision-log pointer recording the move) and needs no reopening. The trade is that `OVW-05` now also owns the pre-authentication entry screen, which is neither CIO-specific nor a shell region, so its title under-describes its scope; recorded deliberately so no future reader infers sign-in UI belongs to an OVW shell story. All three stories gained acceptance criteria and Decision-log entries and should be re-run through `/arh-validate-story` before their next phase.

- 2026-09-04 (OPEN QUESTION, best judgment applied) Login/callback hand-off mechanism: `/auth/callback` returns a JSON body directly to whoever calls it — never a redirect, never a `Set-Cookie` (README, session contract) — and README's Keycloak-client section pins the registered redirect URI to the API's own origin (`http://localhost:8000/auth/callback`), not a frontend URL. Taken literally, a raw browser navigation ends the OAuth dance by rendering JSON, never reaching the frontend's server.
