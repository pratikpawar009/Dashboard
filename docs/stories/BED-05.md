## User story

As the ingest write path (`ING-02`/`ING-06` calling into the shipped rollup engine), I want rollup rebuilds to stop costing more as `usage_events` grows and to survive concurrent pushes from different programs, so that a rebuild kept synchronously inside the request holds its latency budget forever instead of degrading on every push and 500-ing on org-singleton collisions.

## Acceptance criteria

1. Given four concurrent ingest-triggered rebuilds on four **distinct** programs, each calling `rebuild_program_rollups(program_id)` then `rebuild_org_rollups()` on its own session with the org rebuild still inside the request, when they run against a shared Postgres, then all four complete successfully with zero `IntegrityError` on `org_summary_rollup_org_id_key` (today 2 of 4 fail — reproduced live, `docs/research/ING-02.md` § Risk register #2), and the resulting `org_summary_rollup`/`token_series`/`mau_series` rows equal what one serial rebuild over the same `usage_events` content produces.
2. Given a `rebuild_program_rollups` or `rebuild_org_rollups` call that fails after its DELETEs (injected error, statement timeout, or serialisation failure), when the exception propagates, then every rollup table in that scope is left exactly as it was before the call — full rollback, no partially-deleted rollup state — and the exception reaches the caller rather than being swallowed.
3. Given `ING-02` must define its own upsert-plus-rebuild boundary at the call site, when this story lands, then the caller ordering it must implement is written down against the `rollup-rebuild` contract (`docs/requirements/data.md` `commit_boundary_note`) and in the rollup module's `DECISIONS.md`, and the diff touches **no** call site: `services/api/app/api/ingest.py` and `services/api/app/services/manifest_ingest.py:355` (ING-10, shipped) are unchanged.
4. Given `usage_events` populated to 160,000 rows across programs (the largest size measured in `docs/research/ING-02.md`), when `rebuild_org_rollups()` runs, then every org rollup is derived by SQL `GROUP BY` aggregation with no per-event ORM row materialised — the bare `select(UsageEvent)` at `rollup_rebuild.py:470` (no `WHERE`, no `LIMIT`) is gone, closing the `.claude/rules/performance-baseline.md` "no unbounded fan-out reads" violation — and duration meets the pinned budget rather than tracking table growth (measured baseline: 417 ms @ 20k → 3,864 ms @ 160k).
5. Given the same populated table, when `rebuild_program_rollups(program_id)` runs, then its per-program aggregation is likewise pushed into SQL with no full-history row materialisation, and duration meets the pinned budget rather than tracking total history (measured baseline: 588 ms @ 20k total/5k in-program → 4,805 ms @ 160k total/40k in-program).
6. Given golden snapshots of every rollup table produced by the shipped implementation at each of the three measured table sizes (20k, 40k, 160k total rows — sourced, `docs/research/ING-02.md`; reuse per Decision log), when the rewritten functions rebuild from identical `usage_events` content, then every rollup row matches its snapshot — same row count, same values — **at every size**, excluding only the generated `id` and the `as_of_timestamp`/`created_at`/`updated_at` clock columns (see Decision log). Asserted directly, not implied by BED-03's existing unit tests.
7. Given an explicit statement timeout and connection timeout configured on the shared async engine (`app/core/db.py:17`, today a bare `create_async_engine`), when a rebuild query exceeds the statement bound, then it fails on that bound with a logged error instead of hanging, the surrounding scope rolls back per AC-2, and the gap `app/services/freshness.py:32` (BED-04) already flagged is closed by the same engine-level setting.
8. Given a rewritten `services/api/tests/perf/test_rollup_rebuild_perf.py` that seeds a **populated, growing** `usage_events` table, when it runs, then it asserts each function's duration against a pinned **table size** — never batch size — at ≥2 sizes (count per Decision log assumption) and fails on a growth-curve regression; the current empty-table constants `EVENT_COUNT = 5000` / `BUDGET_SECONDS = 2.0` are replaced, and it follows the in-repo perf convention (`perf_counter`, copied `_percentile`, a named budget constant, a "do not relax this budget" failure message).
9. Given the aggregate rewrite's `GROUP BY` queries need index support that `usage_events`' five existing named indexes do not provide (the four `program_id`-prefixed ones created in `001_initial_schema.py`, plus `ix_usage_events_user_ts` from `002_personal_usage_indexes.py`; none serves org-wide per-month aggregation, and the only other index is the one implied by the `uq_usage_events_program_session_cmd_ts` unique constraint), when the change ships, then any new index arrives as a single **additive, index-only** Alembic revision revising `003_program_roster` — no column, constraint, or data change, downgrade dropping exactly what it added — following `002_personal_usage_indexes.py`; `001_initial_schema.py` is not edited and no validated story is reopened.

## Non-functional requirements

- Performance: rebuild duration must stop tracking total `usage_events` size. Baseline to beat, sourced (`docs/research/ING-02.md` § Risk register, reproduced live against Postgres; PRD § Problem): `rebuild_program_rollups` 588 ms → 4,805 ms and `rebuild_org_rollups` 417 ms → 3,864 ms across 20k → 160k total rows. Replacement budget: **deferred to `/arh-plan-implementation`, measurement-derived** — see Decision log 2026-09-09 “Budget deferral”. No number is pinned here: the (budget, table size) pair is set by measuring the aggregate rewrite, which does not exist yet, and pinning one first would encode the pre-rewrite cost model — the same reasoning already recorded for the timeout values. Two bounds are fixed and sourced, and the plan-time value must satisfy both — (a) **ceiling**: the rebuild's share of ING-02's p95 ≤ 3s end-to-end for a 5000-row batch, alongside validation, upsert and HTTP (sourced from ING-02's own NFR, itself a logged assumption there); (b) **shape**: asserted against a pinned table size, never batch size (PRD expectation 4), and flat across sizes rather than tracking table growth. AC-8 is satisfied by the assertion existing with a named budget constant plus the growth-curve check, not by any particular constant. The curve is asserted across ≥2 table sizes — assumption on the count; PRD expectation 4 fixes the shape ("assert against table size, not batch size"), not how many points (see Decision log). Because the org rebuild stays in the request path (sourced, PRD § Decision), any serialisation wait lands inside that same budget, so the org-singleton fix must be cheap under concurrency, not merely correct. Mechanism: **`ON CONFLICT DO UPDATE` is the decision of record, `pg_advisory_xact_lock` the named fallback** — assumption, confirmation deferred to `/arh-plan-implementation` (Decision log 2026-09-09 “Org-singleton mechanism deferral”). The fallback is not a free preference: `ON CONFLICT` is viable only if the rewritten aggregate is genuinely order-independent, which is a property of the AC-4/AC-5 rewrite and so undecidable until it exists. Plan time must (a) establish order-independence or switch to the advisory lock, and (b) confirm the surviving mechanism's `contention_wait_ms` under the AC-1 four-program case fits the budget above. AC-1 as written is satisfied by either.
- Security: no external HTTP surface — both functions are reachable only from the ingest write paths, which are ingest-token-authenticated (`ingest-token-auth`, ING-01); this story adds no route and no new caller (AC-3). The explicit timeout (AC-7) is also the availability bound `.claude/rules/performance-baseline.md` requires: an unbounded rebuild is an unbounded hold on a pooled connection. Rollup input includes `usage_events.user`, which carries a raw git email (PII) — SQL-side aggregation must keep it out of logs; `rollup_rebuild_completed` stays identifier-free.
- Accessibility: N/A — backend service functions, no UI surface. `design: n/a` is legitimate: `docs/design/schema.json` maps mockups to OVW/PGD/EMD/ARC/DEV/PMD only and BED has no epic there.
- Observability: `rollup_rebuild_completed` keeps the fields BED-03 emits (`scope`, `program_id`, `duration_ms`, `event_count`) — part of the frozen `rollup-rebuild` shape, sourced. One added field, `contention_wait_ms` (time spent waiting on the org-singleton serialisation; 0 when uncontended) — assumption, no source names it; needed because the in-request org rebuild puts that wait inside ING-02's p95 and nothing else would attribute it (see Decision log).

## Dependencies

- Upstream: `BED-03` via `rollup-rebuild` (`docs/requirements/data.md#rollup-rebuild`) — this story rewrites the implementation *behind* that contract and must not move it: same `rebuild_program_rollups`/`rebuild_org_rollups` signatures, same `RebuildResult`, same full-re-derive invariant, output identical before and after (AC-6); see its `implementation_owner_note` and `commit_boundary_note`, which name BED-05 as the owner. `BED-01` via `db-schema` (`docs/requirements/data.md#db-schema`) — `usage_events` plus every rollup table rebuilt from it, including `org_summary_rollup`'s `unique(org_id)` singleton constraint that is the collision point in AC-1. Both upstreams are shipped and their contracts frozen, so this P1 is buildable against them as-is; `produced_by` for `rollup-rebuild` stays `BED-03` (RTM Decisions 2026-09-09) and BED-05 is a consumer, not a co-producer.
- Downstream: `ING-02` (activity ingest) is blocked on this story **in full**, not on a subset — RTM Decisions 2026-09-09, the cost of the one-story decision; its `Depends-on`/`Contract` already carry `BED-05`/`rollup-rebuild`. `ING-06` (manual CLI ingester) consumes the same contract and inherits the fix without changing.

## Decision log

- 2026-09-09 Four scoping decisions taken as given, **not re-litigated** (per `docs/prd/rollup-rebuild-scaling.md` § Decision and RTM Decisions 2026-09-09, `/arh-clarify ING-02` round 1 Q-03, answered by Pratik Pawar): (1) this new story owns the rollup fix and ING-02 does not edit `rollup_rebuild.py`; (2) the org rebuild stays in the request path — serialised, not relocated — so ING-02's AC-1 is unchanged and no staleness semantics are designed; (3) one story, concurrency and scaling together under one gate; (4) both `rebuild_program_rollups` and `rebuild_org_rollups` are in scope.
- 2026-09-09 Explicitly out of scope, recorded so it survives into planning (per PRD § Explicitly out of scope): the ING-02 endpoint itself (auth, validation tiers, response envelope, row upsert); the 65,535 bind-parameter chunking for a 5000-row batch; the intra-batch `CardinalityViolation` de-duplication on `(program_id, session_id, cmd_ts)` — both of those live in ING-02's own new code; changing *what* the rollups compute (this is how, not what); and the `usage_events` additive migration for `source`/`copilot_credits`, which rides with ING-02.
- 2026-09-09 Additive index-only Alembic revision folded into BED-05 (AC-9) — assumption, flagged by decomposition and not yet user-confirmed. Precedent is `002_personal_usage_indexes.py`, an index-only revision owned by the story that needed it (SHP-02) rather than a separate story or a BED-01 reopen. Rationale: a `GROUP BY` rewrite over 160k+ rows is unlikely to hold budget on today's five `usage_events` indexes, none of which serves org-wide per-month aggregation.
- 2026-09-09 Atomicity ownership split — assumption, flagged by decomposition and not yet user-confirmed: BED-05 owns atomicity **inside** the two rebuild functions (AC-2) and documents the caller ordering ING-02 must implement (AC-3); it does not touch `app/api/ingest.py` or ING-10's shipped `manifest_ingest.py:355`. Matches `rollup-rebuild`'s `commit_boundary_note`, which records the same split as best judgment pending confirmation.
- 2026-09-09 Output-identity comparison (AC-6) excludes the generated `id` (app-generated uuid4 hex per `db-schema`) and the `as_of_timestamp`/`created_at`/`updated_at` clock columns — assumption; the PRD requires identical rollup *values*, and those columns are random or wall-clock by construction, so a literal byte-for-byte comparison would fail on every run regardless of correctness.
- 2026-09-09 Golden-snapshot and perf sizes reuse the research table's three measured points (20k, 40k, 160k total rows) — assumption on the reuse; the sizes themselves are sourced from `docs/research/ING-02.md`. The curve is asserted across ≥2 of them — assumption, PRD expectation 4 fixes the shape (table size, not batch size) but not the number of points.
- 2026-09-09 Observability field `contention_wait_ms` added to `rollup_rebuild_completed` — assumption; BED-03's event set and the frozen contract name no contention field, but with the org rebuild in the request path (decision 2) queue time is inside ING-02's p95 and would otherwise be invisible.
- 2026-09-09 **Budget deferral** — the replacement rebuild budget and its pinned table size are deliberately not set in this story. Decision of record: `/arh-plan-implementation` sets them from a measurement of the aggregate rewrite, subject to two bounds fixed here (ceiling: the rebuild's share of ING-02's p95 ≤ 3s for a 5000-row batch, sourced; shape: table-size-indexed and flat, PRD expectation 4). Previously an open clarification; converted to this deferral on user decision at the `/arh-research` gate. Rationale: the value is a function of code that does not exist yet, so any number recorded now would encode the pre-rewrite cost model — identical reasoning to the timeout entry below, and the two move together.
- 2026-09-09 **Org-singleton mechanism deferral** — `ON CONFLICT DO UPDATE` is the decision of record, `pg_advisory_xact_lock` the named fallback; `/arh-plan-implementation` confirms or switches. Previously an open clarification; converted to this deferral on user decision at the `/arh-research` gate. Rationale: `ON CONFLICT` is conditional on the rewritten aggregate being order-independent — a property of the AC-4/AC-5 rewrite, hence undecidable before it exists — and the winner must also clear `contention_wait_ms` under the AC-1 four-program case. AC-1 does not depend on which one wins.
- 2026-09-09 Statement/connection timeout values are not fixed here — set from the pinned budget with headroom once it is measured, i.e. bound by the same open item as the budget itself. The source (`app/core/db.py:17`, PRD expectation 3, `.claude/rules/performance-baseline.md`) requires the bound to exist, not a specific value; inventing one before the rewrite is measured would pin it to the old cost model.
