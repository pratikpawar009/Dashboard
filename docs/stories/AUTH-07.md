## User story

As a signed-in dashboard user, I want an endpoint that tells me my display name and resolved persona, and a way to fully end my session everywhere (not just this browser tab), so that the frontend can render my identity and the correct persona-scoped dashboard, and "logout" actually signs me out of the app and Keycloak alike.

As the backend persona-resolution layer serving every persona-gated route, I want role matching to be case-insensitive and multi-role resolution to be deterministic via an explicit, config-driven persona precedence — with a distinguishable log signal when no role maps at all — so that a correctly-provisioned user reaches the same persona and dashboard on every login, and operators can tell "a role was present but matched no tier" apart from "no mapped role at all" in the logs.

## Acceptance criteria

1. Given a valid bearer token, when the client calls `GET /api/me`, then the response is `200 {name, persona}` — exactly these two fields, with no `email`, `groups`, `programs`, or `jobTitle` in the body (per `session-identity-api`, docs/requirements/api.md).
2. Given the verified token's OIDC profile claims contain `name`, when `GET /api/me` resolves the field, then `name` is that claim verbatim; given `name` is absent but `given_name`/`family_name` are present, then `name` is `"<given_name> <family_name>"`; given both are absent, then `name` falls back to `preferred_username`; given none of the three are present (e.g. a `/auth/dev-bypass` token, which carries no profile claims), then `name` is `null` — never a fabricated placeholder and never composed from `email`.
3. Given the session's `role` resolves successfully through `persona-resolver`'s `resolve(role)` (auth.md#persona-resolver), when `GET /api/me` is called, then `persona` is that resolver's output verbatim — never hardcoded by the route and never inferred by the caller from its own page/route (e.g. `/overview` must not assert `persona: 'cio'` on the caller's behalf).
4. Given `persona-resolver.resolve(role)` raises `PersonaNotFoundError` or `PersonaResolutionError`, when `GET /api/me` is called, then the response is `403` — never a `200` carrying a `null` or defaulted `persona`.
5. Given no bearer token, or a token that fails the existing `get_current_user` validation, when `GET /api/me` is called, then the response is `401` (auth.md#session `transport`'s existing shared dependency behavior) — this route introduces no new 401 logic of its own.
6. Given this story ships, when `docs/requirements/auth.md#session`'s `fields` set and `CurrentUser` are inspected, then a new `name: str | None` attribute is present, populated per AC-2 — additive only, no existing field removed or renamed.
7. Given `GET /api/me` is called repeatedly for the same session while `persona-resolver`'s 300s cache (auth.md#persona-resolver `cache`) is warm, then no additional Tier-1/2/3 lookup runs — this route owns no cache of its own, it only calls the existing resolver.
8. Given a signed-in session, when the browser is navigated to the frontend's new `GET /logout` Route Handler, then it clears the `dashboard_session` cookie via `tokenStore.ts`'s existing `clearSession()` before relaying any redirect.
9. Given the cookie is cleared (AC-8), when the Route Handler completes, then it relays the `302` returned by a new FastAPI `GET /auth/logout` to the browser — mirroring `apps/web/src/app/login/route.ts`'s shipped server-to-server `redirect: "manual"` relay verbatim; no shipped route (`/login`, `/callback`, `/auth/login`, `/auth/callback`) is modified.
10. Given `OIDC_CLIENT_ID`/`OIDC_CLIENT_SECRET`/`OIDC_ISSUER` are all set, when `GET /auth/logout` is called, then it 302s to `{issuer}/protocol/openid-connect/logout` (a new `_LOGOUT_PATH` constant in `services/api/app/auth/oidc.py`, alongside the shipped `_AUTHORIZE_PATH`/`_TOKEN_PATH`) carrying `client_id` and `post_logout_redirect_uri` query parameters — never `id_token_hint`, since `/auth/callback` returns `{access_token, refresh_token, expires_in}` and must not start returning an `id_token` (that would reopen shipped AUTH-01).
11. Given any one of `OIDC_CLIENT_ID`/`OIDC_CLIENT_SECRET`/`OIDC_ISSUER` is unset, when `GET /auth/logout` is called, then it returns `501` via the standard error envelope — the same `config_completeness_gate` `/auth/login`/`/auth/callback` already enforce (`session` contract).
12. Given `post_logout_redirect_uri` in AC-10, when it is constructed, then its value is the frontend's own `/login` route (absolute URL) — never `id_token_hint`-gated `/`, and never a new signed-out landing page (no mockup shows one).
13. Given AC-10's redirect reaches Keycloak, when Keycloak ends the SSO session and redirects the browser to `post_logout_redirect_uri`, then the browser lands on the frontend's `/login` and is shown Keycloak's own login form on the next hop — not silently signed back in, because the SSO cookie that would otherwise let `/login` auto-authenticate is gone.
14. Given logout has completed (cookie cleared + SSO session ended, AC-8/AC-13), when any of the six dashboard routes (the four persona dashboards — ARC-01/DEV-01/PMD-01/EMD-01 — Program Detail, and Adoption Overview) is requested afterward with no new sign-in, then each independently redirects through sign-in — `dashboard_session` is written at `path: "/"` and is the single session every route's `callWithAuth()` path reads; there is no per-page or per-persona exemption.
15. Given no visible entry point is added by this story, when the six mockups' brand bars are inspected, then none gains a link, button, or `cursor:pointer` affordance — `/logout` is reachable only by direct URL navigation, per the route-only decision (no mockup contains "logout"/"sign out" or a clickable affordance in its brand bar).
16. Given an access token was already issued before logout, when it is presented to a protected FastAPI route after logout completes, then it remains valid until its own `expires_in`-derived expiry (realm default `300s`) — a stated, accepted limitation of stateless bearer JWTs with no server-side session store (`session` contract's `transport`/`logout_note`), not a defect this story fixes.
17. Given this story ships, when `README.md`'s "Keycloak client requirements" section is inspected, then it includes an added bullet stating the frontend's `/login` route must be registered under the Keycloak client's **Valid post logout redirect URIs** — additive, alongside the existing Valid Redirect URIs bullets AUTH-05 documented.
18. Given a token's `realm_access.roles` contains `Architect` (any case variant) and Tier-2's shipped mapping is `architect: architect`, when the resolver runs, then it matches case-insensitively (casefolded comparison, per `persona-resolver`'s `case_insensitivity_note`) and returns `architect` — where today's case-sensitive match fails closed with `PersonaNotFoundError`.
19. Given a decoded token whose `realm_access.roles = ['Architect', 'Developer', 'developer']` (the live 2026-09-10 case), when `CurrentUser` is constructed, then `role` resolves deterministically to `architect` on every call — `architect` outranks `developer` in the default precedence `cio > architect > product-manager > engineering-manager > developer` — regardless of the roles' order in the token array.
20. Given the persona precedence order is itself sourced from the same 3-tier config mechanism as role→persona mappings (Tier-1 env → Tier-2 YAML → Tier-3 Postgres), when an operator changes the order in the highest-priority tier that defines it, then subsequent resolutions for a multi-persona-eligible role set pick the new winner without a code change or redeploy.
21. Given a role→persona mapping that resolves correctly today under exact-case matching, when this story's lookup-side normalization ships, then that mapping still resolves to the identical persona — no previously-working configuration regresses, and only strictly more roles gain a match (backward-compatibility invariant, per `case_insensitivity_note`).
22. Given a single config tier holds two keys that differ only by case (e.g. both `Developer` and `developer` are distinct keys in the same tier — a live condition in the Apexon realm), when a role case-folds to match both, then the resolver raises `PersonaResolutionError` rather than silently choosing one.
23. Given the resolver's per-role cache, when a role is resolved, then the cache is keyed on the casefolded role string, so `Architect` and `architect` share one cache entry and the same user's tokens never alternate between a cache hit and a cache miss purely due to casing.
24. Given a decoded token's `realm_access.roles`, when `CurrentUser` is constructed, then an additive `roles: list[str]` field holds every surviving entry after `_is_keycloak_system_role` filtering in the token's original order (for audit), while `role` holds the single precedence-selected winner used by every existing resolver/`rbac-checks` call site — `role` stays a `str` and no persona-set concept is introduced anywhere (one persona decides one landing page).
25. Given every one of a token's surviving roles fails to resolve in any of the 3 tiers, when resolution is attempted, then a distinct log event fires carrying the attempted role(s) and the tiers consulted, with no `user_id`/`email`/`name`/`groups`, and it is grep-distinguishable from both a successful `persona_mapping_loaded` line and the existing `rbac_check_org_access outcome=denied` denial — closing the 2026-09-10 observed gap where an unmapped role and a matched-but-still-denied role logged identically.
26. Given all 3 tiers are still empty for a role after case-folding, when resolution completes, then it still raises `PersonaNotFoundError` (fail-closed unchanged) — case-insensitivity and precedence never turn a genuinely unmapped role into a default persona.

## Non-functional requirements

- Performance: `GET /api/me` — one call per page render, no pagination applies (per `session-identity-api` `perf`, api.md), rides `persona-resolver`'s existing `300s` cache (sourced, auth.md#persona-resolver `cache`), no new latency budget. Logout — `GET /auth/logout` only string-builds the end-session URL from `issuer` + `_LOGOUT_PATH` (no discovery fetch, no server-side call to Keycloak, mirroring `/auth/login`'s shipped mechanism); the `/logout` Route Handler's only work is a cookie clear plus a manual-redirect relay; no new latency budget beyond ordinary page navigation. Persona resolution — no change to the shipped `300s` per-role cache TTL or `3s` tier-3 `asyncio.wait_for` timeout (`persona-resolver` contract); casefold comparison and precedence ranking run in-process against already-fetched tier data, adding no new query or I/O.
- Security: `GET /api/me` — authentication only, no persona or membership gate beyond a valid bearer token (per `session-identity-api` `rbac`, api.md); response excludes `email`/`groups`/`programs`/`jobTitle` (sourced, `excluded_fields`); `name` is PII and must never appear in a log line — assumption, mirrors `session`'s existing `dashboard_login` PII-only-`user_id` invariant (auth.md#session `observability`). Logout — token values never appear in a log line on this path, extending the same invariant; an already-issued access token survives until its own expiry (realm default `300s`, sourced from `session` contract `logout_note`/`transport`) even after cookie clear + SSO termination — accepted limitation, not a gap to close here. Persona resolution — fail-closed is preserved and extended: an all-tiers-miss still raises `PersonaNotFoundError` (AC-26), and a same-tier case-collision raises rather than default-picking (AC-22); the unmapped-role log event carries only role slugs and tier names, per the existing PII invariant — never `user_id`/`email`/`name`/`groups`. Multi-role precedence does not reduce authorization: `governance_visibility` (FR-AUTH-09, `rbac-checks`/AUTH-03) allows `architect | product-manager | developer` and excludes `cio`/`engineering-manager`, which mirrors the mockups exactly — the governance panels (`Compliance & guardrails`, `Organization Constitution`) appear only on the Architect, Developer and Product Manager pages and are absent from the CIO Portfolio and Engineering Manager pages. A user resolving to `cio` therefore lands on a page that carries no governance panels, so there is no dual-role access for this story to restore and `_GOVERNANCE_PERSONAS` is not widened (RESOLVED 2026-09-10, see Decision log).
- Accessibility: N/A across all three mechanisms — backend-only work, no UI surface in this story. `GET /api/me` — assumption, mirrors the AUTH-04/AUTH-06 precedent (the rendered identity block is OVW-05/PGD-07's concern). Logout — `design: n/a` is legitimate: `docs/design/schema.json` has no `AUTH` key (mirrors AUTH-05's own precedent), and this story adds zero rendered UI by explicit decision (AC-15). Persona resolution — `design: n/a` legitimate, no design epic covers this resolver, same as AUTH-02's precedent.
- Observability: `GET /api/me` — no dedicated log event for this route itself — assumption, no source names one; persona-resolution success/failure visibility is already covered by `persona-resolver`'s existing `persona_mapping_loaded` / unmapped-role events (auth.md#persona-resolver `observability`), and adding a second event would duplicate that signal (`.claude/rules/reusability-baseline.md`). Logout — assumption: emit one structlog JSON `dashboard_logout` event carrying `user_id` only (no email, no token value) from the `/auth/logout` route, mirroring `dashboard_login`'s existing PII invariant — no source specifies a logout-side event. Persona resolution — existing `persona_mapping_loaded` success event is unchanged, plus a new all-tiers-miss event, `persona_mapping_not_found` (role(s) attempted, tiers consulted) — assumption; the contract's `unmapped_role_observability_note` specifies the required fields and PII invariant but not a literal event name. Cache invalidation: none owned by `GET /api/me` or the logout route; the `300s` TTL is `persona-resolver`'s own (sourced), unchanged by this story.

## Dependencies

- Upstream: AUTH-01 via `session` (docs/requirements/auth.md#session) — `get_current_user`'s bearer-JWT validation and the `CurrentUser` fields this story reads (`role`) and extends (`name` per AC-2/AC-6, `roles: list[str]` per AC-24); the shipped `config_completeness_gate` this story's `GET /auth/logout` reuses; `/auth/login`'s manual-redirect pattern (`_AUTHORIZE_PATH`/`_TOKEN_PATH` sibling constants in `services/api/app/auth/oidc.py`) this story's `_LOGOUT_PATH` mirrors; and the confirmed absence of `id_token_hint` (`/auth/callback` never returns an `id_token`). AUTH-02 via `persona-resolver` (docs/requirements/auth.md#persona-resolver) — `resolve(role) -> persona`, the `PersonaNotFoundError`/`PersonaResolutionError` this route converts to `403`, and the tier-matching internals this story changes (case-insensitive lookup, deterministic precedence, casefolded cache key, unmapped-role observability). AUTH-05 via `session` — the frontend's shipped httpOnly-cookie store (`apps/web/src/lib/tokenStore.ts`) and its `clearSession()` function, and `apps/web/src/app/login/route.ts`'s shipped server-to-server `redirect: "manual"` relay this story's `/logout` handler mirrors verbatim. All three upstreams are shipped and frozen; this story is a co-producer (not merely a consumer) of both `session` and `persona-resolver` — it changes their semantics behind unchanged interfaces (`resolve(role: str) -> str`; `CurrentUser.role` stays a `str`) — per RTM Decisions 2026-09-10. `independent_test: true`.
- Downstream: OVW-05, PGD-07 via `session-identity-api` (docs/requirements/api.md#session-identity-api) — both build against this story's frozen `{name, persona}` shape (stubbed), not against this story's code, per RTM Decisions 2026-09-10. `session-identity-api`'s own `under_declared_edge` note records that `ARC-01`/`DEV-01`/`PMD-01`/`EMD-01` will need the same contract once next touched — not this story's downstream today, since their own `Contract`/`Depends-on` columns are unchanged validated rows. `AUTH-03` (`rbac-checks`, all 16 consumers) and `SHP-01` keep consuming `persona-resolver`/`session` through the same unchanged `role: str` interface, untouched by this story's internal semantic changes (backward-compatibility invariant, RTM Decisions 2026-09-10). Note (RTM Decisions 2026-09-10, "Cost of the merge"): OVW-05/PGD-07 are nominally gated on this story's larger (logout + resolver) scope though they consume only `{name, persona}` — mitigated, not eliminated, by the dependency being contract-based, so neither is actually blocked by the logout or resolver halves landing later.
