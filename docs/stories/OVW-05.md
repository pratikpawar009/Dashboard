## User story

As a CIO, I want the Adoption Overview page's brand bar to show who I'm signed in as and its header to show the "Adoption Overview" title with my CIO context, so that I can confirm my identity and that I'm viewing the org-wide CIO dashboard rather than a persona view.

## Acceptance criteria

1. Given `apps/web/src/types/persona.ts`, when `VALID_PERSONAS` is inspected, then it includes `"cio"` as a fifth entry alongside the existing four (`architect`, `developer`, `product-manager`, `engineering-manager`) (`persona-shell` `cio_persona_note`).
2. Given `apps/web/src/lib/formatPersonaTag.ts`'s `PERSONA_DISPLAY` map, when `formatPersonaTag("cio")` is called, then it returns `{ tag: "CIO / CXO", subtitle: "Organization-wide AI-in-SDLC adoption, spend & impact", color: "#0f1a2e", background: "#e6e9ef" }` instead of throwing `PersonaTagError` (sourced: decoded `dashboards/CIO Portfolio Dashboard.html` brand-bar pill/avatar and header subtitle; `persona-shell` `cio_persona_note`).
3. Given the `PersonaDisplay` shape, when any of the five `PERSONA_DISPLAY` entries is inspected, then each carries a `jobTitle` field with a plain role name — `cio`: "Chief Information Officer", `architect`: "Architect", `developer`: "Developer", `engineering-manager`: "Engineering Manager", `product-manager`: "Product Manager" — never the mockups' seniority-bearing literals "Principal Architect" (Architect mockup) or "Senior Developer" (Developer mockup), which this story deliberately supersedes because the system holds no seniority data anywhere (`persona-shell` `job_title_source_note`/`job_title_divergence_note`).
4. Given `formatPersonaTag.ts`'s `PersonaTagError` docstring and `formatPersonaTag`'s own docstring, when this story ships, then the premise "the CIO Portfolio mockup has no persona tag/subtitle region at all — so a `cio` value reaching this function is an invariant violation, not a fifth persona to render" is removed and replaced with text reflecting `cio` as a valid, renderable persona (`persona-shell` `cio_persona_note`; verified false against the decoded mockup — CIO's brand bar/header are structurally identical to Architect's).
5. Given a signed-in CIO session, when `AdoptionOverview` renders, then it calls `GET /api/me` (`session-identity-api`) server-side and passes the resulting `persona` to `PersonaDashboardShell` — never a hardcoded `persona="cio"` literal — which ends the shell's permanently-`isLoading` state that today's `persona`-omitting call produces.
6. Given `GET /api/me` returns a non-null `name`, when `AdoptionOverview` composes the shell's `signedInUser` prop, then it passes `{ name, jobTitle: PERSONA_DISPLAY[persona].jobTitle }` and the brand bar renders that name, that job title, and a 34×34 circular initials avatar (`border-radius:50%`) on `background:#0f1a2e` for a `cio` persona.
7. Given `GET /api/me` returns `name: null` (e.g. a `dev-bypass` token with no profile claims), when `AdoptionOverview` composes `signedInUser`, then it passes `undefined` rather than a fabricated name, and the shell's existing neutral fallback (a plain gray circle, no initials, `aria-hidden`) renders — the mockup's sample name `Elena Vasquez` never ships as fallback copy.
8. Given `PersonaDashboardShell.tsx`, when this story ships, then it exposes a new optional prop that carries the composing page's title (e.g. `pageTitle?: string`) and, when that prop is defined together with a resolved `persona` and `program === undefined`, renders a second header composition — the page title (`font-size:19px; font-weight:700; letter-spacing:-.3px`) plus the persona pill (`formatPersonaTag(persona).tag`) on one line, then the persona subtitle beneath (`font-size:12.5px; color:#7a828f; font-weight:500`) — selected purely by prop presence, mutually exclusive with the existing `program !== undefined` header-region variant, and with no `persona === 'cio'` (or any persona-literal) conditional added inside `PersonaDashboardShell.tsx` (`persona-shell` `org_header_region`).
9. Given a CIO session, when `AdoptionOverview` passes `pageTitle="Adoption Overview"` and omits `program`, then the header renders title "Adoption Overview", pill "CIO / CXO" (`font-size:11px; font-weight:700; color:#0f1a2e; background:#e6e9ef; padding:3px 9px; border-radius:20px`), and subtitle "Organization-wide AI-in-SDLC adoption, spend & impact" beneath — matching the decoded `HEADER` region of `dashboards/CIO Portfolio Dashboard.html`.
10. Given `persona === undefined` (not yet resolved), when `PersonaDashboardShell` renders, then neither the identity block nor either header variant renders — only the brand bar's static left half (logo tile + product name/tagline) — unchanged from the shell's existing FR-5 no-flash/no-skeleton rule.
11. Given `apps/web/src/types/persona.ts` and `PersonaDashboardShell.tsx`'s `SignedInUser`/`signedInUser` PROVISIONAL docstrings (pending "the AUTH-01 session-contract amendment"), when this story ships, then those docstrings are updated to reflect resolution without a rename: `name` arrives from `session-identity-api` under that exact field name, and `jobTitle` is composed frontend-side from `PERSONA_DISPLAY[persona].jobTitle` — the `SHP-01 D-01` field-name isolation adapter is left intact, not exercised.
12. Given the brand bar's signed-in identity block renders (AC-6/AC-7), when a signed-in user views it, then it also exposes a **sign-out control** — the identity block becomes the affordance (or carries a child control within it), reachable by keyboard, with an accessible name of "Sign out" — so a signed-in user can end their session from the UI without typing a URL.
13. Given the sign-out control is activated, when the browser follows it, then it navigates to the frontend's existing `GET /logout` Route Handler (AUTH-07, `apps/web/src/app/logout/route.ts`) — this story adds **no** new logout logic, no second cookie-clear path, and no direct call to `GET /auth/logout`; the shipped handler already owns the read-session -> clear -> relay-302 chain (AUTH-07 D-08).
14. Given `persona === undefined` (not yet resolved, AC-10), when `PersonaDashboardShell` renders, then the sign-out control does **not** render either — it is part of the identity block, and the block's existing all-or-nothing rule is unchanged.
15. Given this story ships, when the six mockups are inspected, then none of them contains a sign-out affordance — this control is a **deliberate, recorded deviation** from the design source (see Decision log), not a mockup-derived element; it reuses the shell's existing brand-bar tokens and introduces no new visual language.
16. Given an unauthenticated visitor reaches the frontend's `/login` surface, when it renders, then it presents a **branded sign-in page** carrying the same brand-bar identity the rest of the app uses — the logo tile, the product name "AgentRise Harness", and the "AI SDLC Governance" tagline — rather than immediately server-redirecting to the identity provider with no dashboard-owned screen.
17. Given the sign-in page renders, when the visitor views it, then it offers a single **SSO sign-in action** (accessible name "Sign in with SSO" or equivalent) that navigates to `GET /login/start`, and activating it begins the **existing** Keycloak authorization-code flow `AUTH-05` already shipped — the PKCE/`state` mechanics, the `/callback` hand-off and the server-side token store are wrapped, never modified or re-implemented. `/login/start` is the *same* relay handler that ships today at `apps/web/src/app/login/route.ts`, moved one segment down to `apps/web/src/app/login/start/route.ts` with its body unchanged, so that `apps/web/src/app/login/page.tsx` can occupy `/login` (Decision log 2026-09-11). No existing `redirect("/login")` call site changes.
18. Given the visitor already holds a valid session, when they reach the sign-in page, then they are not shown the sign-in action a second time — they continue to their destination, preserving `AUTH-05`'s current behaviour for an authenticated user.
19. Given AC-16's page and AC-12's sign-out control both ship, when the six exports in the design source are inspected, then none contains either a sign-in screen or a sign-out affordance — both are **deliberate, recorded deviations** (see Decision log), built only from the existing brand-bar tokens, introducing no new visual language.

## Non-functional requirements

- Performance: page render issues one additional `GET /api/me` call alongside the existing `GET /api/overview/summary` call; total render must still meet the page's existing ≤3s budget (NFR-001, per OVW-01) — no separate per-call budget is set for `/api/me` — assumption, no source gives one (Decision log). `session-identity-api`'s underlying `resolve()` is already process-cached 300s (sourced, `session-identity-api` `perf`), so repeat loads inside that window add no new backend latency.
- Security: `/overview` stays CIO-gated by `org_access` (AUTH-03, sourced OVW-01 AC-3) — this story adds no new route. `AdoptionOverview` must never hardcode `persona="cio"`; the value is always read from `session-identity-api`'s server-confirmed `persona` field (sourced, RTM Decisions 2026-09-10) — a page-side constant would assert an identity the server never confirmed.
- Accessibility: WCAG AA (NFR-008, per OVW-01 precedent) — the neutral-avatar fallback stays `aria-hidden="true"` (AC-7) and the new org-header composition adds no new interactive control, preserving the shell's existing FR-5 no-flash/no-skeleton behavior (sourced, `persona-shell` states).
- Observability: no new logging event is introduced — `rbac_check_org_access` (OVW-01) is unaffected by this story; `session-identity-api`'s own 401/403 logging is AUTH-07's concern, not this story's (sourced, contract `errors`).

## Decision log
- 2026-09-11 **Branded sign-in page takes `/login`; the OAuth relay handler moves to `/login/start`.** Resolves the sole open clarification from `/arh-research` (`docs/research/OVW-05.md` risk #5). A Next.js App Router segment cannot hold both `page.tsx` and `route.ts`, and `/login` currently holds the relay. Three facts forced the split in this direction rather than parking the page at `/sign-in`: (i) **AC-16 names the `/login` surface literally** and explicitly rejects "immediately server-redirecting to the identity provider with no dashboard-owned screen"; (ii) `FRONTEND_LOGIN_URL=http://localhost:3000/login` is Keycloak's registered `post_logout_redirect_uri` (AUTH-07, `services/api/app/auth/oidc.py:411`), so while `/login` auto-relays, **signing out bounces the user straight back into the IdP** and the branded screen is unreachable at the one moment it matters most; (iii) nothing pins the relay to `/login` — `login/route.ts:12-13`'s docstring claims `OIDC_REDIRECT_URI` "must exact-match this path", but that is **factually wrong**: `AUTH-05-FR-3` ties the exact-match constraint to `/callback`, and `OIDC_REDIRECT_URI` is `http://localhost:3000/callback`. Chosen over an `/api/auth/login` placement because `AUTH-05-FR-3` explicitly considered and rejected an `/api/auth/` prefix for these routes. All 7 shipped `redirect("/login")` call sites keep working unchanged and improve — an expired session now lands on a branded screen instead of a silent IdP bounce. **Carried into implementation:** correct that wrong docstring in the moved file, and give `login/page.tsx` the server-side `dashboard_session` check AC-18 requires. _Note: the research report originally offered relocating the handler to a `+api` segment; that option was invalid — `+api` is a SolidStart/Expo Router convention, not Next.js._
- 2026-09-11 **Branded sign-in page folded into THIS story (moved from `AUTH-05`), per user direction.** It was first placed in `AUTH-05`, which owns the `/login` surface — the thematically natural home. It moved here because `AUTH-05` is already at `phase: review` with shipped code, so hosting new UI there reopens a finished story, while this story is still `story-validated` and is the one queued to run. Consolidating both new UI requirements here means one pipeline pass delivers the sign-in page and the sign-out control together. **Scope note, recorded rather than glossed:** this widens the story beyond its title ("CIO shell regions") — it now also owns the pre-authentication entry screen, which is neither CIO-specific nor a shell region. That is a deliberate, user-directed trade of titular coherence for delivery speed, not an oversight; a future reader should not infer that sign-in UI naturally belongs to an OVW shell story. `AUTH-05` keeps its Decision-log pointer recording the move.
- 2026-09-11 **Sign-out control added to the signed-in identity block — deliberate deviation from the mockups, per explicit user direction.** None of the six exports in `dashboards/` contains a logout/sign-out affordance (verified by grep across all six on 2026-09-11), and `CLAUDE.md` forbids inventing UI the mockups do not show, requiring that such a gap be raised rather than designed. It was raised, and the user decided: a signed-in user must be able to sign out from their own page. The control therefore lands in the identity block this story already owns, rather than in a new story — per the user's instruction "whatever story we have left add this requirement into that dont create next story". It reuses the shipped `/logout` Route Handler (AUTH-07) and adds no new logout mechanism. `PGD-07` carries the matching assertion for Program Detail, and the four persona dashboards (`ARC-01`/`DEV-01`/`PMD-01`/`EMD-01`) inherit it by composing the same `PersonaDashboardShell`.
